# MISC review (SEC) consistency_ok=False

## Issues
- [high] CAPS-1/CAPS-2: Direct internal contradiction on whether consume-N runs for an over-cap len. CAPS-1 says on a len-over-cap rejection the terminal '(1) still transitions into consume-exactly-N mode and drains/discards exactly N bytes (or to the negotiated stall limit)' to keep framing aligned. CAPS-2 asserts the opposite as the load-bearing premise of its anti-drip-feed argument: 'a too-large len is already rejected at header parse (CAPS-1), so consume-N only ever runs for an under-cap len.' Both cannot hold. If over-cap DOES drain N (CAPS-1), then consume-N runs for an arbitrarily large attacker-chosen N and CAPS-2's bounded-progress proof collapses; if over-cap does NOT drain (CAPS-2), then CAPS-1's resync mechanism is undefined and the announced N raw bytes leak into the text grid (the WIRE-3/WIRE-8 desync vector). => FIX: Pick one model and state it in both. Recommended (matches WIRE-8): over-cap len DOES enter a bounded discard state but capped at an absolute hard ceiling (not 'the negotiated stall limit', which is never defined). Define the ceiling as an advertised cap (e.g. max_drain_bytes_session) above which the parser declares unrecoverable desync, returns to Ground, and emits a distinct code. Then CAPS-2's 'consume-N only runs for under-cap' must be reworded to 'the COMMIT/reassembly consume-N path only runs for under-cap; the DISCARD-and-resync path is separately bounded by the hard drain ceiling.'
- [medium] CAPS-1/CAPS-2: Both cite 'the negotiated stall limit' / 'an absolute hard ceiling' but neither defines it as a concrete advertised cap, and CAPS-9 (the unified closed cap set) does NOT list any drain/stall ceiling. So the one bound that actually prevents the over-cap-len DoS is left vague and is absent from the advertised vocabulary, violating CAPS-9's own rule 'the terminal MUST NOT enforce a cap it did not advertise' and principle 4 (app owns fallback). => FIX: Add the drain ceiling and the CAPS-2 inactivity bound K to CAPS-9's closed advertised set (e.g. max_drain_bytes_session, max_partial_frame_idle_reads). Cross-reference from CAPS-1/CAPS-2.
- [medium] CAPS-2: test_note (b) asserts 'pending budget accessor reads 0' after RIS abort, and (a) asserts parser back in Ground, but neither test asserts the deterministic inactivity bound K via the injectable clock seam the decision relies on — test (a) says 'call advance with empty/unrelated input N>K times' which is hand-wavy about what advancing the advance-call counter looks like through Parser::advance and never asserts the counter value or that K is the injected/configured value. The grounded clock today is RGP's real-Instant tick (scene.rs:198 tick_animations(now: Instant)); the decision invents an 'advance-call count' clock that does not yet exist and the test does not assert it is wired to an injectable seam. => FIX: Add an assertion that drives the abort by an EXPLICIT injected counter/clock value (e.g. set K=3, call advance 3 times with no bytes for the frame, assert truncated fires on exactly the 3rd) and assert a &self accessor exposing the pending-frame idle-read count, so the determinism claim is actually tested through the PTY seam rather than asserted in prose.
- [medium] CAPS-1: CAPS-1 mandates 'txn and len mandatory' and makes txn a u32 in the binary header, but does NOT address WIRE-7's ordering requirement (enc= must precede len= so the parser knows raw-byte mode vs base64-scan mode before acting on len). Since the parser must enter consume-N at TEXT-header parse time based on enc=bin, and the doc example (line 312) writes enc before len but never normatively requires that order, CAPS-1's 'validate len at header-parse time, before entering consume-N' is unimplementable when enc appears after len. => FIX: Add to CAPS-1 doc_changes: enc= MUST precede len= in the binary header (or default enc=b64 when absent), so the framer knows whether len means raw-bytes-to-follow (enc=bin) before it acts. Cross-reference WIRE-7. This is a precondition for the whole CAPS-1/CAPS-2 consume-N machinery.
- [medium] CAPS-3: CAPS-3 says an asset.add arriving for an id with a pending chunked upload 'follows §8.4s collision rule', but §8.4 (doc line 342-343) only defines collision for a COMMITTED immutable asset id (add-on-existing = error/dup_id). The in-flight-chunked-id case is a genuinely separate ambiguity that SCEN-9 raises explicitly (immutability vs in-flight reassembly buffer). CAPS-3 hand-waves it to a rule that does not actually cover the case, leaving it unresolved. => FIX: Either resolve it here (recommended: an asset.add for an id with an in-flight chunked upload is NOT a dup_id; it depends on the SCEN-9 resolution of begin/chunk/end vs add+more) or explicitly defer to SCEN-9 by id and stop calling it 'the §8.4 collision rule'. Note the dependency in cross_cluster_notes.
- [medium] CAPS-4: CAPS-4 computes net VRAM delta within a txn including 'minus bytes freed by node.remove/asset replacement within the same txn', and test (b) asserts a remove+add of equal size commits at-cap (net ~0). But this requires intra-txn ordering semantics (the remove must be accounted before the add) AND interacts with SCEN-1's cascade-delete rule (node.remove freeing a subtree frees referenced assets only if no other node references them — CAPS-4 itself says residency is per-asset, counted once). If the removed node was the LAST referencer the asset frees; if not, net delta is wrong. CAPS-4 does not state that the per-asset refcount is evaluated post-removal within the txn. => FIX: State that VRAM delta is computed against the txn's FINAL post-apply asset reference set (refcount each asset after all adds/removes/upserts in the txn are notionally applied), not op-by-op, so a remove that drops the last reference frees and a remove of a still-referenced asset frees nothing. Cross-reference SCEN-1 (cascade delete) and the per-asset-once counting rule.
- [medium] CAPS-9: CAPS-9 renames EVERY advertised cap field (max_verts -> max_verts_per_asset, max_vram_mb -> max_vram_mb_session, max_instances -> max_instances_per_buffer, etc.). The current §7.1 doc example (line 266) ships max_verts/max_instances/max_vram_mb/max_msg_mb with no suffixes. This is fine for a clean break (no RGP compat to preserve, F2), BUT CAPS-9 keeps max_msg_mb un-suffixed 'as the message-size cap' while suffixing everything else — an inconsistency in its own self-describing-scope principle (max_msg_mb is per-message/per-frame and should arguably be max_msg_mb_message or noted). More importantly, CAPS-5's detail= values and CAPS-7's detail= values (detail=max_verts, detail=max_texels) use the OLD un-suffixed names, while CAPS-9 test (b) asserts 'the detail= string equals the advertised field name'. So CAPS-5/CAPS-7 detail strings will NOT equal the CAPS-9 advertised names — a cross-finding vocabulary mismatch. => FIX: Make CAPS-5 and CAPS-7 detail= enums use the EXACT suffixed names from CAPS-9 (detail=max_verts_per_asset, detail=max_texels_per_texture, etc.), or explicitly state detail= uses the un-suffixed short form and drop CAPS-9 test (b)'s 'detail equals advertised field name' assertion. As written they contradict.
- [low] CAPS-6: CAPS-6 says a raw tgp;p from an un-queried (untrusted) writer is 'processed for safety (caps still enforced, scene still protected) but its errors are NOT emitted ... dropped silently like a dumb reader.' This is a security-relevant decision that lets untrusted PTY bytes MUTATE the shared scene (commit nodes/assets) with no token and no proven listener — it only withholds the error reply, not the mutation. Under F1 (tokenless/untrusted writers cannot address or retarget nodes owned by a different token) this is consistent for ADDRESSING existing nodes, but CAPS-6 does not say whether a tokenless writer may CREATE new (default-namespace) nodes. LIFE-3 raises exactly this cross-process scene-pollution/DoS. Left ambiguous here. => FIX: State explicitly whether a tokenless tgp;p may create/mutate default-namespace nodes at all, or whether scene mutation (not just error emission) requires a prior valid tgp;q. Recommended: tokenless writers may be processed for safety but their mutations land only in the default/global namespace they own (per CAPS-6's own 'default/global namespace it owns' wording for queries) — make that the same for raw patches. Cross-reference LIFE-3 and F1.
- [low] CAPS-10: CAPS-10 coalescing ('multiple node.instances for the same node within a single render frame collapse to the latest; one upload per node per frame, bumping scene_revision once') is asserted as testable, but the grounded dirty model bumps scene_revision PER MUTATION (term.rs / SCEN flags scene_revision per mutation), and there is no 'render frame boundary' concept in the GPU-free Parser::advance(&mut Term) seam — frames are a renderer concept, not a parser/Term-state concept. test (b) asserts 'scene_revision advanced by exactly one' across three patches, which is unobservable at the Parser->Term seam without a defined frame-boundary tick on Term. The coalescing rule conflates renderer-frame with txn-commit. => FIX: Define coalescing at a CPU-observable boundary: either (a) coalesce within a single txn (multiple node.instances ops for the same node in one patch collapse to the last — fully testable via one Parser::advance) and let the renderer's asset_revision/scene_revision dirty-split (principle 6) naturally collapse cross-txn redundant uploads, or (b) add an explicit Term::begin_frame()/composite tick accessor the test can call. As written, 'one upload per node per frame, scene_revision +1' is not assertable through the mandated PTY-to-internal-state seam.
- [low] CAPS-5: CAPS-5's closed enum omits a code for the CAPS-1/CAPS-2 hard-drain-ceiling / unrecoverable-desync case and for the WIRE-3 len-mismatch (len disagrees with actual CBOR length) case. ## Missed
- No resolution addresses what happens to in-flight binary/chunk state and the pending budget on a NAMESPACE-TOKEN level: under F1 caps are SHARED but addressing is isolated. CAPS-2/CAPS-3 say pending budget is 'per-session' but F1 makes namespaces the unit of isolation. Is the pending budget per-token or per-session-shared? A malicious token could exhaust the shared per-session pending budget and DoS another token's legitimate chunked upload (cross-token resource starvation). CAPS-3 says 'per-session total pending cap' — under F1 multi-token this is a shared-resource DoS surface that no SEC resolution flags. This is exactly the principle-3 safe-by-default threat for the multi-writer case LIFE-3 raised.
- CAPS-1/CAPS-5 mandate txn is a u32 in the binary header, but the design doc (line 380) says 'txn is an app-chosen correlation id' with no type, and the §8.6 CBOR example (line 362) shows txn:42 INSIDE the CBOR body too. No resolution reconciles the header txn (u32, framing-level) vs the CBOR-body txn (correlation, app-level) — are they required to match? If they can disagree, an error citing the header txn may not match the app's body-tracked txn. Should be pinned: header txn is authoritative and the CBOR body MUST NOT carry a conflicting txn (or omit it).
- CAPS-11 fuzz invariant says 'pending-bytes==0 when no upload is in flight (no leak)' and 'vram-used matches the committed scene', but there is no accessor named for the CONSUME-N partial-binary-frame buffer separate from the chunk-reassembly buffer — CAPS-2/CAPS-3 share 'one accountant' (the pending budget) but a fuzz oracle also needs to assert the consume-N remaining-byte counter is 0 at quiescence and that the parser ApcState/binary-read state returned to Ground. The grounded ApcState (parser.rs:5-17) has no binary-read variant yet; CAPS-11's oracle should assert parser state == Ground at quiescence, not only pending_bytes==0.
- No resolution covers the base64 (enc=b64) decode path for the expansion-bomb cap (CAPS-7) or the len cap (CAPS-1): a base64 payload expands ~4:3 and the b64 len is the encoded-char count (WIRE-7), so max_msg_mb and CAPS-7 expanded-output checks must account for the decode expansion of b64 BEFORE the CBOR/glTF expansion. CAPS-7 lists glTF/CBOR/texture loci but omits the base64->bytes expansion as a locus. A b64 frame just under the encoded-len cap still decodes to a larger byte blob fed to CBOR.
- CAPS-4 counts 'instance buffer footprint once per node' and CAPS-10 governs node.instances churn, but neither addresses the renderer grounding that today there is a SINGLE shared Depth32Float pass with no per-viewport offscreen targets, no MSAA, no instancing (grounding). VRAM accounting for instancing (CAPS-4) and the dirty-split coalescing (CAPS-10, principle 6) assume an instancing path and per-asset GPU residency that does not exist yet — these are net-new renderer subsystems. Not a blocker for the wire/parser rules, but the resolutions should note the GPU-side accounting is purely CPU-known-footprint bookkeeping (CAPS-4 says this) with no actual GPU residency to reconcile in v1, which is consistent but means CAPS-10's 'VRAM churn' framing is aspirational until instancing lands.
