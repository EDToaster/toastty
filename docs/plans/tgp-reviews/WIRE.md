# WIRE review (WIRE) consistency_ok=False

## Issues
- [high] WIRE-10: Opt-in mechanism for error reporting directly CONTRADICTS the cross-cluster owner. WIRE-10 gates emission on 'the app having negotiated error reporting (capability flag, e.g. feat=event/a dedicated errors flag)'. But CAPS-6/CAPS-7 (in SEC.md) and the register line 27 resolve the OPPOSITE: 'a completed tgp;q/tgp;r handshake IS the error-reporting opt-in' (no dedicated flag; dumb readers never handshake so stay silent, with an optional errors=0 opt-out). WIRE-10's 'feat=event' suggestion is also wrong on its face: feat=event is for INPUT events (tgp;e), not error replies (tgp;x) — conflating them. This is the load-bearing gate for WIRE-3/9/10/11 emissions, so getting it wrong silently breaks every other WIRE test that asserts an x reply. => FIX: Adopt the CAPS-6/7 resolution verbatim: error reporting is enabled for the rest of the session once the app completes a valid tgp;q (handshake = opt-in), with an explicit errors=0 opt-out; never gate on feat=event or invent a separate errors flag. Rewrite WIRE-10's gating clause and test (b) so 'not negotiated' means 'never handshook', and cite CAPS-6/CAPS-7 as the owner.
- [high] WIRE-3: The rule 'the decoded CBOR item MUST consume the ENTIRE buffer; trailing bytes after a complete item -> parse_error;trailing_bytes' collides with the forward-compat principle and §7.2/§8.6, which say unknown ops/fields inside a patch are SKIPPED not fatal, and bulk fields ride as CBOR byte sub-blobs. CBOR encoders legitimately emit a single self-delimiting top-level item, so a strict whole-buffer rule is mostly fine — BUT WIRE-3 never reconciles with the possibility of CBOR tag/indefinite-length encodings or an encoder that pads, and more importantly it does not state that the item must be a single top-level CBOR data item (a sequence of 2 valid items would currently be 'trailing bytes'). The bigger gap: 'trailing_bytes' and 'truncated' are invented detail strings not in the closed error-code register (SEC-5/CAPS-5 pins the enum at cap_exceeded/parse_error/msg_too_large/truncated/bad_ref/dup_id/unknown_op/unsupported/vram). => FIX: State that the buffer MUST decode to exactly one top-level CBOR data item with no trailing bytes; keep field/op-skipping forward-compat INSIDE that item (per §7.2). Map outcomes onto the SEC-5 closed code enum: use code=parse_error with detail as advisory only (detail is explicitly non-load-bearing per SEC-5), and do NOT assert on detail strings in tests as if they were normative.
- [medium] WIRE-5: WIRE-5 keys reassembly by (token, asset_id) citing F1, but the namespace token is owned by LIFE-6 (and SCEN-8 for id hardening), and the token's existence/shape/negotiation is resolved THERE, not in WIRE. WIRE-5 silently assumes a per-token addressing model exists at the chunk-buffer layer. If LIFE-6's resolution makes the token OPT-IN (tokenless writers share one default namespace, per F1's 'tokenless or untrusted writers cannot address... a different token'), then two tokenless writers BOTH using asset id=1 land in the SAME (default-token, 1) bucket and WILL collide/abort each other — exactly the corruption vector WIRE-5 claims to prevent. WIRE-5 does not define the tokenless/default-namespace key. => FIX: Make the key (namespace_token_or_default, asset_id) and explicitly state the tokenless-writer behavior: tokenless frames share one default namespace, so concurrent tokenless uploads on the same asset id legitimately abort-on-reopen per the same rule (this is acceptable and safe). Cross-reference LIFE-6 as the token owner and note the dependency; do not assert F1 isolation guarantees that only hold for tokened writers.
- [medium] WIRE-4: Two problems. (1) The capability advertisement edit adds a NEW feat token 'bintrailer' and reorders enc= (b64 first) — but CAPS-3 (feat token set freeze) and SEC/CAPS-9 (caps reply is a closed set) own the §7.1 vocabulary. WIRE-4 unilaterally extends feat= without coordinating with the cluster that froze it; the design doc's current enc=bin,b64 lists bin FIRST (line 267), and WIRE-4 flips ordering to b64-first as normative, which is a cross-cluster caps change. (2) test_note (e) 'trl=1 not negotiated but sent -> reject as parse_error unknown-trailer' is underspecified/hand-wavy: if bintrailer was not negotiated the terminal does NOT read a trailer (WIRE-1 base framing), so after consuming len bytes the 8 trailer bytes become the START OF THE NEXT FRAME (TGPB magic + len-echo parsed as text/escape) — the test cannot assert 'unknown-trailer parse_error' because there is no trailer-read state to trip; it would instead desync or mis-parse. The decision body contradicts itself here (base framing reads no trailer, yet the test expects a trailer-specific error). => FIX: Coordinate the feat/enc-order change with CAPS-3/CAPS-9 (note it as a cross-cluster dependency, do not assert it unilaterally). Fix test (e): with bintrailer un-negotiated and trl=1 sent, define behavior precisely — either trl=1 in the header when bintrailer wasn't negotiated is itself a header-validation error (x;parse_error;detail=bad field, emitted BEFORE reading the body, like WIRE-7 field_order), OR trl is ignored and the trailer bytes are consumed-as-next-input. Pick one and make the test assert the resulting internal state (queued reply OR next-frame parse), not a vague 'reject'.
- [medium] WIRE-1: The optional-ST tolerance interacts badly with WIRE-7's enc=b64 default and with multi-byte 8-bit ST. (1) 0x9C is a valid C1 control that also terminates a kitty/other APC; tolerating a single trailing 0x9C as a no-op after a bin frame is fine, but the decision says 'a second consecutive ST is treated as ordinary input' — for 0x9C 'ordinary input' in Ground means a C1 control execute, and for 0x1B it starts AfterEsc. test (c) asserts 'second ST routed to vte' but the current parser (parser.rs) has no path where a lone 0x9C in Ground is forwarded to vte as anything but an execute; the test note is imprecise about WHICH internal state proves the assertion. (2) The decision never says whether the optional ST tolerance applies in DISCARD mode (WIRE-8 over-cap drain) — after draining N bytes, is a trailing ST also tolerated? Unspecified. => FIX: Specify the trailing-ST tolerance as: after the Nth raw byte, peek exactly one byte; if it is 0x1B-followed-by-0x5C, or 0x07, or 0x9C, consume it and return to Ground; otherwise return to Ground WITHOUT consuming and let normal Ground processing handle it. Make test (c) assert the concrete accessor (e.g. the byte became an execute(0x9c) record or started AfterEsc), not 'routed to vte'. State explicitly that the same single-ST tolerance applies after a WIRE-8 discard drain so the two paths are uniform.
- [medium] WIRE-8: BIN_HARD_CEIL behavior is internally inconsistent with WIRE-1/WIRE-9 resync guarantees and is undertested. When len > BIN_HARD_CEIL the decision says 'return to Ground at the header boundary WITHOUT draining'. But the header APC has ALREADY been closed by its ST (WIRE-1) and the parser was about to enter binary-read state; 'return to Ground without draining' means the N announced raw bytes (which ARE arriving on the wire) are now interpreted as text/escapes — i.e. the exact stream-desync / binary-leaks-into-grid corruption that WIRE-3 and principle 3 exist to prevent. Declaring 'unrecoverable desync' is honest but the decision simultaneously claims to keep the stream synced everywhere else; this is the one place it knowingly desyncs, and it is not flagged as such in the doc_changes for §15.2. Also 'detail=unrecoverable' is not in the SEC-5 closed code enum. => FIX: Acknowledge in the decision and doc that the BIN_HARD_CEIL branch INTENTIONALLY accepts desync as the lesser evil vs an attacker-forced multi-GB drain, and that recovery requires a host-side reset (RIS, per LIFE-2). Use code=cap_exceeded (in the enum) and treat detail=unrecoverable as advisory only. Add a test asserting the parser is in Ground AND that subsequent bytes are (correctly, by design) treated as text — i.e. assert the desync is the defined behavior, not silently hoping for resync.
- [low] WIRE-9: test (a) asserts 'intermediate &self accessor shows remaining decreasing (20->12->4->0)' — this is a good PTY-seam internal-state assertion, but the decision puts the binary-read state in the Parser (toastty-parser crate) while remaining/buf are private fields; there is currently NO &self accessor on Parser exposing remaining (parser.rs Parser struct exposes nothing, and its Debug is finish_non_exhaustive). The test as written cannot compile without a new test-only accessor that the decision does not mandate. Same gap for WIRE-8 test (d) 'buffer never allocates beyond cap'. => FIX: Add to the decision an explicit requirement to expose a test-only accessor (e.g. #[cfg(test)] or pub(crate) fn binary_remaining(&self)->Option<u64> and buffer len/capacity) on Parser, since the TESTABILITY IMPERATIVE requires asserting internal state via &self accessors with no GPU. Without mandating the accessor, the cross-read tests are unimplementable as specified.
- [low] WIRE-2: ApcEnd enum naming/return-type change is correct and matches grounding, but the decision says 'The Perform impl (Term layer) parses the tgp header during apc_chunk/apc_end and returns BinaryFollows from apc_end' — this requires changing the Perform trait signature for apc_end across ALL implementors (perform.rs has a default no-op apc_end and VteAdapter/AdapterBuffer forward it; the test Recorder in parser.rs also impls it returning ()). The decision understates the blast radius: every apc_end impl in the workspace (default trait method, the buffering adapter at perform.rs:117, and the kitty/RGP demux) must change return type. Not wrong, but the doc_changes don't note the trait-wide migration. => FIX: Note that changing apc_end's return type touches the Perform trait default, the AdapterBuffer/VteAdapter forwarders (perform.rs ~117), and existing kitty/RGP demux impls; the default should return ApcEnd::Done so non-tgp impls are unaffected. Add this migration note to the doc_changes/grounding callout.
- [low] WIRE-6: Sound and well-aligned with §8.6 atomicity, but it overlaps CAPS-3 (chunk reassembly cap teardown: check-per-chunk vs at-assembly, immediate free) without cross-referencing it. WIRE-6 says 'any failure discards the whole buffer' but does not say WHEN the cap is checked (per incoming chunk vs at final assembly) — CAPS-3 owns that and recommends per-chunk check with immediate free. If WIRE-6 implies at-assembly-only checking it contradicts CAPS-3's per-chunk model and reopens the parse-time-bomb (buffer grows to max_reasm before any check). => FIX: Add a sentence deferring cap-check TIMING to CAPS-3/WIRE-8 (per-incoming-chunk cumulative check, immediate free on breach) so the two resolutions agree, and cross-reference CAPS-3 as the owner of teardown timing.

## Cross-cluster
- ERROR OPT-IN (WIRE-3/4/5/6/8/9/10/11 ALL depend on it): The owner is CAPS-6/CAPS-7 (in SEC.md) + register line 27 — 'a completed tgp;q/tgp;r handshake IS the error-reporting opt-in', NOT a feat flag. WIRE-10 contradicts this. Every WIRE test that drains a tgp;x reply assumes the gate; if the gate resolution differs, all those tests change. Reconcile WIRE-10 to the CAPS resolution.
- ERROR-CODE ENUM: SEC-5/CAPS-5 pins a CLOSED versioned code enum (cap_exceeded, parse_error, msg_too_large, truncated, bad_ref, dup_id, unknown_op, unsupported, vram) with detail strings explicitly NON-load-bearing/advisory. WIRE invents detail strings (trailing_bytes, truncated, chunk_interleave, chunk_fmt_mismatch, field_order, trailer_corrupt, base64, max_msg, max_reasm, unrecoverable) and several of its test_notes ASSERT on detail= as if normative. Either get these details added to the enum spec or rewrite tests to assert only on code= (the load-bearing part). Note WIRE uses 'parse_error' where CAPS-1/SEC-1 uses 'msg_too_large' for the cap case — WIRE-8 uses cap_exceeded which is consistent, but verify msg_too_large vs cap_exceeded naming is unified across clusters.
- NAMESPACE TOKEN (F1): Owned by LIFE-6 (multi-process scene, opt-in token) + SCEN-8 (id hardening, reserved prefix). WIRE-5 and WIRE-10 consume per-token keying/routing but the token's negotiation, shape, and tokenless-default behavior are resolved in LIFE-6. WIRE must defer the token model to LIFE-6 and only specify the chunk-buffer key tuple and reply-routing consumption. Critical edge: tokenless writers share a default namespace (per F1) so WIRE-5's collision-isolation guarantee does NOT hold between two tokenless writers — must be stated.
- TXN-IN-TEXT-HEADER: WIRE-10 correctly hoists txn into the text header, which is the SAME resolution as CAPS-1/SEC-1 (register line 23: 'hoist txn into the text header so cap-rejections cite it & still drain N bytes') and WIRE-8's drain behavior. These are consistent — good — but WIRE should cross-reference CAPS-1 as co-owner so the header field order (txn/enc/len ordering from WIRE-7) is jointly specified. WIRE-7 mandates enc-before-len but is SILENT on where txn sits; CAPS-1 needs txn present pre-body. Specify txn ordering too.
- CAPS-8 (malformed near-miss tgp; prefix): Resolves that a malformed tgp; frame in a native session emits x rather than silent-drop, and unknown-prefix APCs stay silent. WIRE never addresses what happens to an APC whose prefix is almost-but-not tgp; or a tgp; control frame with an unknown type — these route through apc_end returning Done (WIRE-2) and then... unspecified in WIRE. Align with CAPS-8 so detection failures are diagnosable.
- FEAT/CAPS REPLY VOCABULARY: WIRE-4 adds 'bintrailer' to feat= and WIRE-8 adds max_reasm_mb to §7.1, and WIRE-4 reorders enc= to b64-first. CAPS-3 (feat token freeze + implication rules) and CAPS-9/SEC-9 (closed caps set with explicit scope) own §7.1. These WIRE additions must be merged into the CAPS-owned reply schema, not asserted independently, or the two clusters will emit divergent capability replies. Note current doc (line 267) lists enc=bin,b64 (bin first) and feat without bintrailer.
- CAPS-5-in-CAPS.md vs CAPS-7-in-SEC.md NAMING COLLISION: The findings file SEC.md actually contains findings labeled CAPS-1..CAPS-10 (caps enforcement/errors), while CAPS.md contains the handshake-negotiation CAPS-1..CAPS-8. There are TWO different 'CAPS-5', 'CAPS-6', 'CAPS-7' etc. across the two files. When WIRE cites a cross-cluster id, it must disambiguate (e.g. the error-enum is SEC.md/CAPS-5; the error opt-in is SEC.md/CAPS-6 AND CAPS.md/CAPS-7 — both say handshake-is-opt-in). The resolver should normalize cluster ids to avoid mis-wiring dependencies.

## Missed
- MALFORMED HEADER / unknown header fields: WIRE-7 handles enc-before-len order, but no WIRE decision covers a header with an UNKNOWN field, a missing/garbage len= on enc=bin, or a non-numeric len. Per §7.2 unknown FIELDS are skip-tolerant, but a missing/garbage len on enc=bin is unrecoverable (parser can't know how many bytes to consume) — must be a parse_error that does NOT enter binary state. This is the most dangerous unhandled header case (it decides whether the raw bytes leak into the grid) and is unspecified.
- CONTROL FRAME vs BINARY FRAME demux for type: WIRE-2 says non-bin/control frames return Done, but §8.5 lists vp as 'control/binary' — a vp frame CAN be enc=bin. WIRE-2/7 implicitly assume only type=p uses enc=bin. No decision states which message TYPES may carry enc=bin (p, vp?) vs are always control (q/r/e/x/a/sub/anim). An enc=bin on a type that should be control-only is unhandled.
- DETERMINISTIC CLOCK / animation: The TESTABILITY IMPERATIVE and grounding both flag RGP animation uses real-Instant ticks (non-deterministic) and require an injectable deterministic clock. No WIRE decision is about animation, which is correct (that's ANIM cluster), BUT WIRE-9's EOF-handling and any timeout-based partial-frame abort (CAPS-2 proposes an inactivity timeout for stalled partial frames) would need the deterministic clock. WIRE-9 handles EOF but NOT the stalled-partial-frame DoS (slow-drip huge len) that CAPS-2 raises — WIRE-9 only discards on actual EOF, leaving the hung-curl-drips-bytes-forever vector to CAPS-2. WIRE should cross-reference CAPS-2 or note the stall case is out of WIRE scope.
- b64 WHITESPACE / line-folding: WIRE-11 covers base64 decode errors (detail=base64) but does not address whether embedded whitespace/newlines in the b64 payload (common when frames are line-folded for transport) are tolerated or rejected. Real base64-over-APC often contains soft line breaks. Unspecified — affects whether the 'app pre-trims to ceil(cap*4/3)' bound is in raw chars or non-whitespace chars.
- RIS/reset interaction with in-flight binary-read and chunk buffers: LIFE-2 resolves RIS = full scene teardown INCLUDING pending chunk buffers. But what if RIS (ESC c) arrives while the parser is MID binary-read (remaining>0)? The ESC of RIS would be consumed as raw payload bytes (binary-read disables escape scanning per WIRE-1), so RIS cannot interrupt an in-flight binary frame. This is a real safety gap: an attacker who sends a huge len then never finishes wedges the parser AND RIS can't recover it until the byte count completes or EOF. WIRE-9 + LIFE-2 together leave this uncovered; WIRE-8's BIN_HARD_CEIL only helps if len itself is over-ceiling.
- ack (tgp;a) timing for chunked/binary frames: §8.5 defines tgp;a ack for a committed txn. WIRE-6 says the completing chunk frame carries the txn cited in ack/x, but no WIRE decision specifies whether/when an ACK is emitted for a successfully applied binary patch (vs only errors). LIFE/CAPS may own acks, but WIRE-3/6/10 mention ack routing without defining ack emission — note the gap or defer explicitly.
- Parser back-channel for enc=b64 size enforcement: WIRE-11 says b64 flows through the existing APC chunk path bounded by min(encoded-cap, 256MiB APC cap). But the existing apc_chunk path (term.rs apc_buffer, APC_BUFFER_CAP=256MiB at term.rs:3380) has NO per-message encoded-cap today — WIRE-11 requires NEW logic to bound the APC accumulation at ceil(max_msg_mb*4/3) specifically for tgp b64 frames while leaving kitty/other APCs at 256MiB. The decision doesn't specify HOW the apc layer distinguishes a tgp b64 frame (needs header peeking) from a generic APC to apply the tighter cap — this is a real implementation gap mirroring the WIRE-2 back-channel problem but for the b64 path.
