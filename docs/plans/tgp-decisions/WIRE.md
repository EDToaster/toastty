# WIRE resolutions (WIRE)

### WIRE-1 [P0] What consumes the ST terminator after raw binary bytes
- Decision: NORMATIVE: For an enc=bin frame, the header APC is closed by its own ST (ESC \\ or BEL or 0x9C); the parser then enters a binary-read state and consumes EXACTLY `len` raw bytes WITHOUT any escape/terminator scanning. After the Nth byte the parser returns directly to Ground. NO trailing terminator is required or expected after the raw bytes. If the byte immediately following the N raw bytes is an ST (ESC \\, BEL, or 0x9C), the parser MUST tolerate it as a no-op sync marker and consume it (one optional ST only); any other byte begins the next frame/text normally. The optional-ST tolerance is bounded to a single ST token so a flood of 0x9C cannot be absorbed.
- Rationale: Length-prefix is self-delimiting, so a mandatory trailer is redundant; tolerating one optional ST gives senders a harmless sync hedge and aids human-pasted frames without creating ambiguity. Conforms to principle 5 (compact wire: no forced 33% or trailer tax) and principle 3 (bounded tolerance, no unbounded ST absorption). Note: per F4/F2 the WIRE-4 magic trailer (below) is a SEPARATE opt-in integrity feature, not the base-frame terminator — the base frame has no required trailer.
- Doc change: Section 8.2(b): replace the example annotation with explicit framing prose. After the example add: 'The header APC is terminated by ST as normal. The parser then reads exactly `len` raw bytes with escape-scanning DISABLED, and returns to Ground after the Nth byte. No terminator follows the raw payload. A single ST token (ESC \\, BEL, or 0x9C) immediately after the raw bytes is tolerated and consumed as a no-op sync marker; a second consecutive ST is treated as ordinary input.'
- Test: (a) advance(term, b"ESC_ tgp;p;txn=1;enc=bin;len=3 ESC\\ \x00\x01\x02") then advance text 'X' -> assert one patch decoded AND grid shows 'X' at expected cell (proves Ground re-entry, no ST swallowed text). (b) Same frame with a trailing ESC \\ before 'X' -> assert identical patch + 'X' printed (optional ST consumed). (c) Same frame with TWO trailing ESC \\ then 'X' -> assert second ST routed to vte (no spurious print/state from first being mis-handled) and 'X' printed. (d) Raw payload containing 0x1B 0x5C bytes mid-data -> assert full N bytes captured verbatim (no early terminate).

### WIRE-2 [P0] Parser back-channel: apc_end must trigger binary-read mode
- Decision: NORMATIVE: Change the parser hook so apc_end returns a signal: `fn apc_end(&mut self) -> ApcEnd` where `enum ApcEnd { Done, BinaryFollows { len: u64, enc: BinEnc } }` (BinEnc = Bin only; b64 stays inside the APC and never sets BinaryFollows — see WIRE-7). The Perform impl (Term layer) parses the `tgp;...;enc=bin;len=N` text header during apc_chunk/apc_end and returns BinaryFollows{len,enc} from apc_end; the Parser, on receiving BinaryFollows, transitions from Ground into the binary-read state for exactly N bytes. The Parser itself does NOT parse tgp header semantics — it only acts on the returned enum. Non-tgp / non-bin APCs return Done and behave exactly as today.
- Rationale: Keeps the Parser a dumb pre-scanner and keeps all tgp;/CBOR/len knowledge in the Term layer, matching the existing layering and principle 1 (terminal simple, app-authoritative parsing localized). A typed return enum is the minimal cross-crate API change and is fully deterministic/testable. The Parser-peeks-the-header alternative is rejected because it pushes protocol knowledge into the generic escape parser. F2: no RGP demux constraint applies — TGP owns this path independently.
- Doc change: Section 8.2(b): add 'Parser back-channel (normative): the APC end hook returns `ApcEnd { Done | BinaryFollows{len,enc} }`. The tgp header is parsed in the terminal/Perform layer, which returns BinaryFollows for an enc=bin frame; the pre-scanner then consumes exactly `len` bytes outside escape-scanning. The pre-scanner has no knowledge of tgp semantics.' Add to the grounding callout that today apc_end returns unit and this is the required signature change.
- Test: (a) Drive Parser::advance with a tgp;enc=bin;len=4 header and assert (via a test Perform recording apc_end's return) that BinaryFollows{len=4,enc=Bin} was returned. (b) A kitty/other APC (no tgp prefix) -> apc_end returns Done, subsequent bytes flow to vte as text. (c) A tgp control frame (enc absent / q / e) -> apc_end returns Done, no binary state entered. (d) After BinaryFollows, feed 4 bytes and assert parser back in Ground (next ESC starts AfterEsc).

### WIRE-3 [P0] len mismatch with actual CBOR payload size
- Decision: NORMATIVE: `len` is authoritative for FRAMING ONLY. The parser always consumes exactly `len` bytes (subject to the cap/ceiling rules of WIRE-8) and hands that buffer to the CBOR decoder. Decode outcomes: (1) buffer decodes to a complete CBOR item that consumes the WHOLE buffer -> apply patch. (2) CBOR self-terminates BEFORE the end of the buffer (trailing bytes) -> reject: emit `x;code=parse_error;detail=trailing_bytes` (txn from header per WIRE-10), scene unchanged, return to Ground. (3) CBOR is truncated / needs more than `len` bytes -> reject: emit `x;code=parse_error;detail=truncated`, return to Ground. In all three cases the parser has already consumed exactly N bytes, so the stream stays synced regardless of internal mismatch. Under-len never leaks into the text grid because framing consumes N, not 'until CBOR ends'.
- Rationale: Separating framing-truth (len) from content-validity (CBOR) is the only way to stay resynced against a hostile/buggy sender (principle 3): a lie about content cannot desync the stream because framing is byte-counted. Structured errors instead of silent drop or crash. The 'trust len only, ignore mismatch' option is rejected because trailing garbage in the buffer would silently corrupt the decoded op set.
- Doc change: Section 8.3: add subsection 'len vs payload (normative): `len` governs framing exclusively; the parser consumes exactly `len` bytes then CBOR-decodes the buffer. The decoded item MUST consume the entire buffer. Trailing bytes after a complete item, or a truncated/incomplete item, are rejected as `x;code=parse_error` (detail=trailing_bytes | truncated); the txn is unchanged and the stream resyncs at the next frame.'
- Test: (a) len=N where N exceeds the encoded CBOR by 2 trailing 0x00 -> assert queued reply contains tgp;x;code=parse_error;detail=trailing_bytes AND scene node count unchanged. (b) len=N two bytes short of a valid CBOR map -> assert x;detail=truncated, scene unchanged. (c) Immediately send a valid frame after each failure -> assert it applies (proves resync). (d) Exact-length valid CBOR -> assert patch applied, scene_revision bumped once.

### WIRE-4 [P1] tmux/screen passthrough stripping/splitting raw binary bytes
- Decision: NORMATIVE (per USER DECISION): The terminal advertises BOTH enc=bin and enc=b64 in the capability reply, listing b64 first as the recommended default; the app SELECTS the encoding and is responsible for choosing b64 when it cannot confirm a clean PTY (the terminal never auto-detects multiplexers — principle 4, app owns fallback). For enc=bin only, the terminal supports an OPT-IN integrity trailer negotiated via a capability flag `bintrailer` and requested per-frame with header field `trl=1`: when `trl=1`, after the `len` raw bytes the terminal reads a fixed 8-byte trailer = 4-byte magic `0x54 0x47 0x50 0x42` ('TGPB') + 4-byte little-endian echo of `len`. Mismatch or absent trailer -> `x;code=parse_error;detail=trailer_corrupt`, scene unchanged, return to Ground. Without `trl=1` no trailer is read (WIRE-1 base framing). The trailer bytes are NOT counted in `len`.
- Rationale: Safe-by-default for untrusted/lossy transports (principle 3) while keeping conveniences opt-in (principle 2) and app-authoritative fallback (principle 4): the app, not the terminal, decides bin-vs-b64 and whether to pay for the trailer. A fixed magic+length-echo detects the two realistic passthrough corruptions (ST-strip shifting bytes, mid-frame truncation) and surfaces them as structured errors instead of silent desync. F2: no RGP transport behavior constrains this.
- Doc change: Section 7.1: add `bintrailer` to the feat list and note 'enc list is ordered by terminal recommendation (b64 first when a clean transport is unconfirmed).' Section 8.2(b): add 'Integrity trailer (opt-in): when the app negotiated `bintrailer` and sends `trl=1`, an 8-byte trailer (magic "TGPB" + u32-LE len echo) follows the raw payload and is verified; mismatch -> x;parse_error;detail=trailer_corrupt. The trailer is excluded from `len`. The app SHOULD prefer enc=b64 behind multiplexers; the terminal does not detect multiplexers.' Update §16 tmux row to reference this opt-in trailer.
- Test: (a) trl=1 frame with correct trailer -> patch applied. (b) trl=1 frame with corrupted magic byte -> x;detail=trailer_corrupt, scene unchanged, and a following valid frame applies (resync). (c) trl=1 frame whose len-echo disagrees with header len -> x;detail=trailer_corrupt. (d) capability reply assertion: drain_pty_replies after tgp;q contains enc=b64,bin (b64 first) and feat includes bintrailer. (e) trl=1 not negotiated but sent -> treated per policy (reject as parse_error unknown-trailer) — assert structured error.

### WIRE-5 [P1] Chunk reassembly keying across concurrent uploads / interleaving
- Decision: NORMATIVE: Chunk reassembly is keyed by `asset id` (the numeric u32 handle of the asset.add being uploaded), SCOPED to the owning app's namespace token (F1) — keys are (token, asset_id) so two tokens cannot collide or corrupt each other's buffers. Within one token: (1) independent asset ids MAY interleave their chunk streams freely. (2) A single asset id MUST NOT interleave: a second open `more=1` stream for an id that already has an in-progress buffer, OR a format/fmt mismatch against the opener, ABORTS the prior buffer for that id and emits `x;code=parse_error;detail=chunk_interleave` (or `chunk_fmt_mismatch`); the new stream then starts fresh. Caps from WIRE-8 apply to the accumulating buffer. A tokenless/untrusted writer cannot address or abort another token's in-progress upload (F1).
- Rationale: Per-id keying is the minimal granularity that supports concurrent independent uploads while forbidding the corruption vector of two streams writing one id. F1 token-scoping is mandatory so cross-app addressing/abort is impossible. F2: the RGP-matching rationale in the finding is dropped — TGP defines this independently; we keep abort-on-mismatch because it is the safe behavior (principle 3), not because RGP does it. Structured error replaces RGP's silent drop.
- Doc change: Section 8.7: replace with 'Reassembly is keyed by (namespace token, asset id). Independent asset ids may interleave; a single id may not — a second open stream for an in-progress id, or an fmt mismatch with the opener, aborts the prior buffer and emits x;code=parse_error (detail=chunk_interleave | chunk_fmt_mismatch). Keys are token-scoped: an app cannot abort or address another app token's pending upload (§F1 namespace).'
- Test: (a) Interleave chunks of asset id=1 and id=2 (more=1 each, then more=0 each) under one token -> assert both assets present, asset_revision bumped. (b) Open id=1 more=1, then open id=1 more=1 again before close -> assert prior aborted, x;detail=chunk_interleave queued, only the new stream's bytes retained. (c) id=1 chunk fmt=glb then fmt=obj mid-stream -> x;detail=chunk_fmt_mismatch. (d) Two tokens both using asset id=1 -> assert separate buffers, no cross-corruption (each completes independently).

### WIRE-6 [P1] Chunked asset.add vs patch atomicity
- Decision: NORMATIVE: Chunk frames are PURE pre-parse buffering and carry NO transaction semantics: a `more=1` chunk frame bumps nothing, applies nothing, and has no txn effect. Only the FINAL frame (more=0) completes reassembly; the fully assembled buffer is then CBOR-decoded as one patch and applied ATOMICALLY (all ops or none), bumping asset_revision once (and scene_revision once if the patch also mutates nodes/transforms) on success. A failure on any chunk (cap overflow, interleave, fmt mismatch, or final-frame decode error) discards the whole buffer and leaves the scene unchanged — no partial asset is ever installed. txn correlation lives on the FINAL frame's header (intermediate chunk frames need no txn); the x/ack reply cites that txn. Chunk frames are NOT required to be alone in a patch, but a chunked asset.add's op set is only evaluated once, at completion.
- Rationale: Preserves the §8.6 atomic-patch guarantee for the most expensive op without inventing multi-frame txn correlation: buffering is invisible to the scene until complete (principle 3, no partial state from untrusted input). Generalizes the dirty-split (principle 6): a completed asset upload bumps asset_revision exactly once. F2: independent of RGP chunk semantics.
- Doc change: Section 8.7: append 'Atomicity (normative): chunk frames are pure buffering and carry no txn/scene semantics — they bump nothing. The assembled buffer is decoded and applied as a single atomic patch only on the final (more=0) frame, bumping asset_revision once (and scene_revision once if nodes change). Any failure discards the whole buffer; no partial asset is installed. The completing frame carries the txn echoed in ack/x.' Cross-reference §8.6.
- Test: (a) Send asset.add in 3 chunks (more=1,1,0); after chunk 1 and 2 assert asset_revision UNCHANGED and asset absent; after chunk 3 assert asset present and asset_revision bumped exactly once. (b) Final-chunk CBOR invalid -> assert no asset installed, asset_revision unchanged, x;parse_error with the final frame's txn. (c) Multi-op final patch (asset.add + node.upsert) completing via chunks -> assert BOTH applied atomically and scene_revision bumped once.

### WIRE-7 [P0] Two len semantics under enc=bin vs enc=b64 conflated
- Decision: NORMATIVE: Header field ordering and defaults are fixed. `enc=` MUST appear before `len=` in the header; a `len=` seen before any `enc=` in the same header is a `x;code=parse_error;detail=field_order` and the frame is rejected (control-frame style, no binary state entered). Default when `enc=` is absent = `b64`. ONLY `enc=bin` engages the raw-byte-count binary-read state (apc_end returns BinaryFollows). For `enc=b64`, `len` denotes the base64 CHARACTER count INSIDE the APC; the payload is scanned/terminated by ST as a normal APC (no binary-read state), then base64-decoded. So the parser always knows its read mode from `enc=` before it acts on `len`. `len` is OPTIONAL for enc=b64 (ST delimits); when present it is validated against the actual b64 char count (mismatch -> parse_error).
- Rationale: Mandating enc-before-len removes the only path to entering the wrong read mode (principle 3, hardened parsing). Defaulting to b64 keeps the safe, transport-robust path as the no-enc fallback. One field name, two clearly-mode-gated meanings, decided deterministically by enc. F2: independent of RGP.
- Doc change: Section 8.2(b): add 'Header field order (normative): `enc=` precedes `len=`; `len` before any `enc` -> x;parse_error;detail=field_order. enc absent defaults to b64. enc=bin: `len` = raw byte count read outside escape-scanning. enc=b64: `len` = base64 char count inside the ST-terminated APC (optional; validated if present); the payload is base64-decoded after the APC closes.'
- Test: (a) Header 'tgp;p;len=10;enc=bin' (len before enc) -> assert x;detail=field_order, no binary state entered, no scene change. (b) Header with enc absent + b64 payload in-APC -> assert decoded as b64 patch. (c) enc=bin;len=N -> assert binary-read state entered (BinaryFollows). (d) enc=b64;len mismatching actual char count -> assert x;parse_error. (e) enc=b64 no len, ST-terminated -> assert decoded.

### WIRE-8 [P0] max_msg_mb cap vs chunk reassembly cap and overflow drain
- Decision: NORMATIVE: Define two caps, both advertised in §7.1: `max_msg_mb` = max DECODED size of a single message/frame; `max_reasm_mb` = max accumulated size of a single chunk-reassembly buffer (>= max_msg_mb). Overflow handling for enc=bin: if header `len` > the applicable cap, the terminal MUST STILL consume-and-DISCARD exactly `len` bytes (without buffering them, to bound memory) to keep the stream synced, then emit `x;code=cap_exceeded;detail=max_msg|max_reasm`. A second ABSOLUTE hard ceiling `BIN_HARD_CEIL` (a compile-time constant, e.g. 1 GiB, >= max_reasm_mb) caps even the discard loop: if `len` > BIN_HARD_CEIL the terminal declares unrecoverable desync, emits `x;code=cap_exceeded;detail=unrecoverable`, and stops consuming the binary stream (returns to Ground at the header boundary) rather than draining a potentially-fabricated multi-GB count. Chunk total is bounded by max_reasm_mb; per-frame by max_msg_mb. Never leave announced-but-undrained bytes when len <= BIN_HARD_CEIL.
- Rationale: An over-cap len that is also a lie is a denial-of-sync vector; draining exactly N (when bounded by the hard ceiling) is the only way to stay synced, but the ceiling prevents an attacker from forcing a multi-GB drain loop (principle 3, bounded resources). Structured cap_exceeded instead of silent drop. Two named caps make the b64-vs-bin and per-frame-vs-stream relationships explicit.
- Doc change: Section 7.1: advertise max_msg_mb and max_reasm_mb (and document BIN_HARD_CEIL as an internal absolute). Section 15.2: add 'Overflow (normative): len>cap -> consume-and-discard exactly len bytes (no buffering) then x;cap_exceeded; len>BIN_HARD_CEIL -> declare unrecoverable desync, x;cap_exceeded;detail=unrecoverable, return to Ground without draining. Chunk buffer bounded by max_reasm_mb, per-frame by max_msg_mb.'
- Test: (a) enc=bin;len just over max_msg_mb -> assert x;cap_exceeded;detail=max_msg, then send a small valid frame and assert it applies (proves the oversize was drained and stream resynced). (b) len > BIN_HARD_CEIL -> assert x;detail=unrecoverable and that parser is back in Ground (next ESC parsed as escape) WITHOUT having attempted to buffer/drain. (c) chunk stream whose accumulated bytes cross max_reasm_mb -> assert x;cap_exceeded;detail=max_reasm and buffer discarded. (d) assert caps appear in capability reply.

### WIRE-9 [P0] Partial binary frame spanning multiple PTY reads
- Decision: NORMATIVE: The binary-read state lives in the Parser and PERSISTS across advance() calls. It holds `remaining: u64` and a capped accumulation `Vec<u8>` (capped at the WIRE-8 cap, with the discard-mode variant for over-cap frames that accumulates nothing and only counts down). Each advance() appends min(remaining, bytes.len()) bytes (or counts them down in discard mode), decrements remaining, and consumes them from the input slice; when remaining reaches 0 the frame is complete -> hand buffer to decoder (WIRE-3) and return to Ground; if the input slice empties first, the state is retained for the next advance(). On terminal EOF/stream close with remaining>0, the partial buffer is DISCARDED; if error reporting is negotiated, emit `x;code=parse_error;detail=truncated` (txn from the header captured at frame start). The accumulation buffer must never exceed the cap regardless of how reads are split.
- Rationale: advance() is non-blocking and per-read, so a byte-counted frame WILL straddle reads; an explicit persisted remaining-count + capped buffer is the only correct, deterministic state machine (principle 3, bounded accumulation under cap across reads). Buffering in the Parser (not Term) keeps the byte-count authority co-located with the read state from WIRE-2.
- Doc change: Section 8.2(b): add 'Cross-read lifecycle (normative): the binary-read state persists across advance() calls with a remaining counter and a cap-bounded accumulation buffer; bytes append until remaining==0, then the buffer is decoded and the parser returns to Ground. On EOF with remaining>0 the partial is discarded and (if error reporting negotiated) x;parse_error;detail=truncated is emitted with the header txn.'
- Test: (a) Split a len=20 frame across three advance() calls (8, 8, 4 bytes) -> assert no decode until the 20th byte, then exactly one patch decoded; assert intermediate &self accessor shows remaining decreasing (20->12->4->0). (b) Header in one advance, raw bytes split across two more -> assert correct reassembly. (c) Feed header + 10 of 20 bytes, then signal EOF -> assert partial discarded, scene unchanged, x;truncated with the header txn. (d) Split an over-cap frame across reads in discard mode -> assert buffer never allocates beyond cap and x;cap_exceeded emitted once.

### WIRE-10 [P0] CBOR decode-error surfacing through the reply channel
- Decision: NORMATIVE: Identity/correlation fields (`txn`, and `enc`/`len`) live in the TEXT header and are parsed BEFORE the CBOR body, so they are always known even when the body fails to decode. The decode site returns a Result; the Term layer routes a decode error to queue_reply -> pty_replies, emitting `x;code=parse_error` with the header `txn` (and op index when the failure is op-localized, omitted when the failure is whole-frame). Emission is GATED on the app having negotiated error reporting (capability flag, e.g. `feat=event`/a dedicated `errors` flag); if NOT negotiated, the error is silently dropped (dumb-reader behavior preserved). Replies route only to the owning namespace token (F1). The Result MUST NOT be discarded at the decode site.
- Rationale: Putting txn in the text header is what makes the structured-error promise real rather than vapor: a body that fails CBOR decode still has a correlatable txn. Gating on negotiation preserves dumb-reader safety (principle 3) while delivering structured errors to apps that asked (principle 4). F1 token routing prevents cross-app error leakage. F2: independent of RGP's discarded-Result behavior — TGP wires the Result through deliberately.
- Doc change: Section 8.2/8.6: state 'txn, enc, len are header (text) fields parsed before the CBOR body.' Section 15.3: add 'Surfacing (normative): the decoder returns a Result routed to the reply channel; on error, emit x;code=parse_error with the header txn (op index when localized), only if the app negotiated error reporting, else drop silently. Errors route only to the owning namespace token.'
- Test: (a) With error reporting negotiated: send enc=bin frame with txn=99 and a malformed CBOR body -> assert drain_pty_replies contains tgp;x;txn=99;code=parse_error. (b) Same frame WITHOUT error reporting negotiated -> assert drain_pty_replies is empty (silent drop) and scene unchanged. (c) Decode error where the failing op index is known -> assert x includes op=K. (d) Two tokens; malformed frame from token A -> assert error queued only for token A's reply routing, not token B.

### WIRE-11 [P1] base64 fallback cap and parse-path reconciliation
- Decision: NORMATIVE: `max_msg_mb` is defined as the cap on the DECODED payload for BOTH encodings. For enc=b64 the encoded (in-APC) length is bounded at ceil(max_msg_mb * 4 / 3) rounded up to the next multiple of 4 (plus padding); exceeding the encoded bound -> consume-to-ST then `x;code=cap_exceeded;detail=max_msg`. The b64 path flows through the existing APC chunk/ST-scan machinery (so the APC accumulation is independently bounded by the encoded-length cap, NOT only the legacy 256 MiB APC cap — the smaller of the two applies). After the APC closes, base64-decode: a base64 decode error -> `x;code=parse_error;detail=base64`. The decoded bytes then go through the SAME CBOR decode + error path as enc=bin (WIRE-3/WIRE-10), so both encodings share one decoded-size cap and one CBOR error contract. An app that pre-trimmed to max_msg_mb for bin is therefore valid for b64 too (same decoded budget).
- Rationale: One logical message must not have two effective size limits or two error stories; anchoring the cap to decoded size and routing both encodings through the same post-decode CBOR path unifies them (principle 5 compact wire with a robust fallback, principle 3 hardened parsing). base64 decode failure becomes a first-class structured error rather than an uncovered mode.
- Doc change: Section 7.1/15.2: 'max_msg_mb is the DECODED-payload cap for both enc=bin and enc=b64; for b64 the encoded length is bounded at ceil(cap*4/3) and the in-APC accumulation is bounded by min(that, APC cap).' Section 8.3: 'b64 frames are base64-decoded after the APC closes (decode error -> x;parse_error;detail=base64) then fed to the same CBOR decode/error path as bin, sharing one cap and one error contract.'
- Test: (a) enc=b64 frame whose base64 is valid and decodes to a valid patch within max_msg_mb -> assert patch applied. (b) enc=b64 with malformed base64 (bad char/length) -> assert x;parse_error;detail=base64, scene unchanged. (c) enc=b64 whose encoded length exceeds ceil(cap*4/3) -> assert x;cap_exceeded;detail=max_msg and stream resyncs (next frame applies). (d) Same logical CBOR payload sent once as enc=bin and once as enc=b64 (both within cap) -> assert identical resulting scene state (parity across encodings).
