# MISC resolutions (VIEW)

### VIEW-1 [P1] Inline viewport binding survives ScrollbackLine eviction undefined
- Decision: When the last placeholder cell of an inline viewport is evicted from the bounded scrollback ring, the terminal AUTO-DESTROYS that viewport: it frees the viewport's offscreen color+depth targets and pick target, drops the viewport entry from Scene.viewports, and clears the viewport dirty flag. The referenced Camera node and any scene nodes are NOT touched (a viewport owns only its compositing resources, never scene content). Destruction is keyed on placeholder-cell liveness, not on the stored {line,col} hint (consistent with F3/VIEW-12: cells are authoritative). If the owning token's app has an active sub on that viewport, the terminal emits exactly one lifecycle event `tgp;e;vp=<id>;ev=destroyed;reason=evicted` routed ONLY to the owning token (F1); a tokenless/other-token writer that created or addressed it gets nothing. A viewport with zero live placeholder cells is treated as not-rendered for the frame in which the last cell leaves the visible+scrollback set, then destroyed. No `tgp;x` error is emitted for eviction (eviction is normal teardown, not an error).
- Rationale: Principle 3 (bounded resources) and the §15.2 VRAM caps require reclaiming offscreen+depth targets when the anchor leaves the ring; keeping orphaned targets leaks the very VRAM the caps promise. Auto-destroy is the only option that reclaims VRAM deterministically. F3 makes placeholder cells authoritative, so eviction must key on cell liveness, not the {line,col} hint. F1 routes the lifecycle event to the owning token only. Emitting a lifecycle event (not an error) lets the app re-create the viewport if it scrolls content back, without spamming dumb readers (§15.3).
- Doc change: §10.2 (Inline vs pinned): after the sentence on inline scrolling off-screen (state retained), add: 'An inline viewport is bound to its placeholder cells (§10.2/§12). When ALL of a viewport's placeholder cells are evicted from the bounded scrollback ring, the terminal auto-destroys the viewport: it frees that viewport's offscreen color+depth and pick targets and removes it from the scene. Scene nodes and the referenced Camera node are not affected. If the owning app (F1 token) has an active sub on the viewport, the terminal emits exactly one `tgp;e;vp=<id>;ev=destroyed;reason=evicted` to that app only; no `tgp;x` is emitted (eviction is normal teardown).' Add `destroyed` to the `ev` enum in §12.5. §6.5: note that viewport auto-destroy clears the per-viewport dirty flag.
- Test: Construct Term with a small scrollback cap (e.g. 4 rows). Feed: tgp handshake + a patch upserting a Camera node + a `tgp;vp` inline viewport anchored to a line, plus the placeholder cells written into the grid. Assert via &self accessor that scene.viewports contains the id and its pixel rect is non-empty. Then feed enough newlines to push the anchor line + all placeholder cells past the scrollback cap. Assert: (1) scene.viewports no longer contains the id; (2) the Camera node still exists in scene.nodes; (3) drain_pty_replies after subscribing yields exactly one `tgp;e;vp=...;ev=destroyed;reason=evicted` frame; (4) with no sub, drain_pty_replies yields no destroyed frame. Cross-token test (F1): an inline viewport owned by token A, subscribed by A; evict; assert the destroyed event routes to A's reply queue and NOT to a token-B reply context.

### VIEW-2 [P0] Inline placeholder row/col cap silently truncates large viewports
- Decision: The capability reply (§7.1) advertises two explicit inline-cell caps, `max_inline_cols` and `max_inline_rows` (each a u16, default value 256 in v1 — well under any placeholder-encoding ceiling and an easy round number; final number pinned at implementation). On a `tgp;vp;anchor=inline` whose CellRect.cols > max_inline_cols OR rows > max_inline_rows, the terminal REJECTS the viewport: it does not create or partially create it, and emits a structured `tgp;x;txn=<n>;code=cap_exceeded;detail=max_inline_cols` (or `max_inline_rows`) routed to the owning token (F1). It NEVER silently clamps, truncates, or partially binds. CellRect remains u16 in the wire/model (§10.1); the cap is a separately-advertised limit, not a type change. Pinned viewports are bounded by VIEW-10's pixel cap, not by these inline cell caps (placeholder encoding does not apply to pinned).
- Rationale: Direct USER DECISION F3: advertise an inline cell cap and REJECT over-cap inline viewports with a structured `tgp;x`; never silently clamp/truncate. Principle 3 (structured errors not silent drops) and principle 4 (reliable caps so the app owns fallback) both require the cap be advertised and the rejection be structured. Silent clamp (the third option) is explicitly forbidden by F3. F1 routes the error to the owning token.
- Doc change: §7.1: add `max_inline_cols=256;max_inline_rows=256` to the example reply and to the §15.2 caps list. §10.2: add 'Inline viewports are realized via placeholder cells; the terminal advertises `max_inline_cols`/`max_inline_rows` in the capability reply. A `tgp;vp;anchor=inline` whose CellRect exceeds either cap is rejected with `tgp;x;code=cap_exceeded;detail=max_inline_cols|max_inline_rows` and is NOT created (never silently clamped or partially bound).' §15.2: list max_inline_cols/max_inline_rows among enforced caps. §15.3: add cap_exceeded;detail=max_inline_cols as an example.
- Test: Feed handshake; assert drain_pty_replies `tgp;r` contains max_inline_cols and max_inline_rows. Feed `tgp;vp;id=2;anchor=inline;cells=0,0,400,16` (cols=400 > 256): assert scene.viewports does NOT contain id 2, and drain_pty_replies yields `tgp;x;...;code=cap_exceeded;detail=max_inline_cols`. Feed an at-cap viewport cells=0,0,256,256: assert it IS created. Feed an over-cap `anchor=pinned` viewport: assert it is NOT rejected by the inline cap path (handled by VIEW-10 instead). Cross-token (F1): assert the cap_exceeded error routes only to the writing token's reply queue.

### VIEW-3 [P1] Inline region occupancy vs text written into the same cells is undefined
- Decision: Occupancy is tied to `clear`, and ordinary text written into placeholder cells detaches the binding. (a) `clear=Some(rgba)`: the viewport fully occludes its placeholder cells — the offscreen layer is composited opaquely over those cells and any underlying cell glyphs are not shown while the viewport is live. (b) `clear=None` (transparent): the viewport composites OVER whatever cell content occupies those cells using premultiplied-alpha straight-over compositing (see VIEW-9); un-drawn pixels reveal the underlying text/cell exactly. (c) DETACH-ON-OVERWRITE: when the app (or a TUI like vim/less) writes a NEW non-placeholder glyph into a cell that currently holds a viewport placeholder, that cell reverts to normal text and is removed from the viewport's live placeholder set. If overwriting reduces the live set below the viewport's required cell count, the binding is broken and the viewport is auto-destroyed exactly as in VIEW-1 (free targets; emit `tgp;e;...;ev=destroyed;reason=detached` to the owning token if subscribed). Re-emitting the SAME placeholder glyph into a cell is not an overwrite and does not detach.
- Rationale: Direct USER DECISION F3 (placeholder cells authoritative, follow text like text) plus the finding recommendation, which the user decisions endorse. Tying occupancy to `clear` reuses the existing field rather than adding state. Detach-on-overwrite keeps reflow correct for the line-based apps the doc targets (vim/less/tmux): text the app writes wins, so the grid never desyncs from what the app believes it drew. Principle 1 (app-authoritative): the app's text writes are authoritative over a stale placeholder. Auto-destroy on under-count reuses VIEW-1's teardown (principle 3, bounded resources).
- Doc change: §10.4: replace the bare 'clear: background; None = transparent' note with: 'clear=Some(rgba) makes the viewport OCCLUDE its placeholder cells (underlying glyphs not shown while live); clear=None composites over the underlying cell content via premultiplied alpha (§VIEW-9).' §10.2: add 'Placeholder cells follow text. Writing a new non-placeholder glyph into a placeholder cell detaches that cell from the viewport (it reverts to text); if this drops the viewport below its required cell count the viewport is auto-destroyed (reason=detached, see eviction teardown). Re-emitting the identical placeholder glyph is not an overwrite.' Add `reason=detached` alongside `reason=evicted` for the `destroyed` event in §12.5.
- Test: Feed handshake + Camera + inline viewport with clear=Some over a region that already had text 'abc': assert via accessor that the viewport's composited cells are flagged occluding (cell-background/glyph-suppressed flag set) for those cells. Repeat with clear=None: assert the cells are flagged composite-over (glyph still present in cell buffer, viewport alpha-over). Detach test: create a 3x1 inline viewport; write a normal glyph ('X') into one of its placeholder cells via Parser::advance; assert that cell is no longer in the viewport's live placeholder set and (since count dropped) scene.viewports no longer contains the viewport and a `ev=destroyed;reason=detached` reply is queued for a subscribed owner. Re-emit-identical test: write the same placeholder glyph into a placeholder cell; assert the live set is unchanged and viewport still present.

### VIEW-4 [P1] Reflow recompute on edit/reflow of the anchor line is undefined
- Decision: Post-reflow viewport position is DERIVED FROM WHERE THE PLACEHOLDER CELLS LAND, not from the stored {line,col} hint. On any reflow event (SIGWINCH, font-size change, resize-driven rewrap that splits/merges lines, or scrollback-line edit that moves cells), the terminal: (1) lets the placeholder cells reflow exactly like text through the existing grid reflow machinery; (2) recomputes the viewport's pixel rect from the bounding region of its live placeholder cells in the current grid; (3) sets the per-viewport dirty flag so the next frame re-composites (re-render only if camera/content/size also changed, per §6.5). If rewrap splits the viewport's placeholder cells across non-contiguous display regions (e.g. a wrapped line breaks mid-viewport), the terminal renders the offscreen layer once at the viewport's logical (cols x rows) size and composites it into the SMALLEST axis-aligned grid rect that contains all live placeholder cells, clipping (not re-rendering) per VIEW-10's on-screen-intersection rule. The {line,col} field is never re-read after initial placement (F3/VIEW-12).
- Rationale: Direct USER DECISION F3 (placeholder cells authoritative; scroll/reflow/selection follow the placeholder cells like text) and the finding recommendation, which the design doc already commits to ('flows naturally', kitty model). Deriving from landed cells is the only rule consistent with making cells the source of truth (VIEW-12). Recompute-pixel-rect-on-reflow generalizes the existing §10.3 SIGWINCH path to all reflow causes. Using the per-viewport dirty flag (principle 6, §6.5 generalization) keeps a pure reflow as a re-composite, not a re-render.
- Doc change: §10.3: extend 'Terminal-driven reflow' to read: 'On SIGWINCH, font-size change, OR resize-driven rewrap that moves/splits the anchor line, the terminal recomputes each inline viewport's pixel rect from the CURRENT landed positions of its placeholder cells (the cells are authoritative, §10.2/§VIEW-12 — the stored {line,col} is only the initial placement hint and is not re-read). If rewrap splits the placeholder cells across a wrap boundary, the offscreen layer is rendered once at logical size and composited into the smallest grid rect bounding the live cells, clipped to the on-screen intersection (§VIEW-10). Reflow sets the per-viewport dirty flag (re-composite, not re-render, unless content/camera/size changed — §6.5).'
- Test: Feed handshake + Camera + an inline viewport bound to placeholders on a wide line. Record the viewport pixel rect via accessor. Then drive a resize (narrower columns) through Parser/Term so the line rewraps; assert the viewport's recomputed pixel rect matches the bounding box of the landed placeholder cells (not the original {line,col}). Split test: place placeholders such that a narrower width wraps them across two display rows; assert the composited grid rect is the smallest rect bounding all live cells and that only the viewport dirty flag (not scene_revision) was bumped. Assert {line,col} stored value is unchanged after reflow (proving it is not re-read as authority).

### VIEW-5 [P0] Viewport referencing a missing/deleted camera node has no defined behavior
- Decision: A viewport whose `camera` NodeId resolves to no Camera node (never created, or removed via node.remove) renders with an IMPLICIT DEFAULT CAMERA: an auto-framing camera computed each frame from the bounding sphere of the viewport's `root` subtree (or the whole scene if root=None), with a fixed default FOV and a look-at framing that fits the bounds. This makes vp-before-camera ordering (§18.1 step 3) and post-remove dangling refs degrade gracefully instead of crashing on the per-frame camera lookup. The lookup is non-fatal: a missing camera is NOT a txn error (creating a vp that names a not-yet-created camera is legal). If the owning app (F1 token) subscribed to a viewport diagnostic channel, the terminal emits an opt-in `tgp;x;vp=<id>;code=camera_missing;detail=<name>` ONCE per transition into the missing state (edge-triggered, not per frame), but KEEPS RENDERING with the default camera. When the named Camera node later appears (upsert), the viewport silently switches to it (clears the diagnostic state). The default camera is terminal-owned scratch state, never a real scene node, so it is never addressable/retargetable by another token (F1).
- Rationale: USER DECISION: finding recommendation chosen (implicit default camera fallback; opt-in diagnostic; keep rendering). Principle 3 (structured errors not crashes; no dangling-reference crash path on a hot per-frame lookup). Principle 1 zero-config promise — symmetric with default material (MaterialId 0) and default lighting. Edge-triggered diagnostic avoids spamming dumb readers (§15.3). NOTE: the finding text mentions 'the RGP adapter, which has no camera node concept' — that adapter rationale is MOOT under F2 (no RGP-to-TGP adapter), but the implicit-default-camera decision stands on its own zero-config/safety merits and is therefore NOT mooted.
- Doc change: §10.1: change `camera: NodeId` to `camera: Option<NodeId>` is handled in VIEW-6; here add to §10.5: 'If a viewport's camera reference is absent OR resolves to no Camera node (not yet created, or removed), the terminal renders the viewport with an implicit auto-framing default camera (fits the root subtree bounding sphere; default FOV). A missing camera is not a txn error. If the owning app subscribed to viewport diagnostics, the terminal emits `tgp;x;vp=<id>;code=camera_missing;detail=<name>` once on entering the missing state and keeps rendering; it silently adopts the real camera when that node later appears.' Remove §4 RGP-adapter framing for this case (F2: mooted sub-rationale).
- Test: Feed handshake + a mesh node + a `tgp;vp;camera="cam"` BEFORE any 'cam' node exists (mirrors §18.1 ordering). Assert: scene.viewports contains the vp; computing the viewport's effective camera/world-view matrix via accessor returns the auto-framing default (matches expected fit of the mesh bounds) and does NOT panic. Then upsert node 'cam' as a Camera; assert the viewport's effective camera now resolves to 'cam'. Removal test: with 'cam' present and viewport rendering it, send node.remove id='cam'; assert no crash, effective camera reverts to default, and (with diagnostic sub) exactly ONE `tgp;x;code=camera_missing` is queued, not one per render. F1: assert the default camera does not appear in scene.nodes and is not addressable by id from another token.

### VIEW-6 [P1] No default camera concept despite default-material/default-light precedent
- Decision: Make `Viewport.camera` OPTIONAL (`camera: Option<NodeId>`). When omitted (or unresolved, per VIEW-5), the viewport uses the same implicit auto-framing default camera defined in VIEW-5. This makes the simplest scene (one mesh + one viewport, no Camera node) render zero-config, symmetric with default material (MaterialId 0) and default lighting. An explicit Camera node is opt-in: the app names a camera only when it wants explicit control (and it must name one for explore, since explore mutates a real Camera node — see note). EXPLORE INTERACTION: explore (§12.3) requires a concrete, persistent Camera node to mutate; if `explore` is set on a viewport with no resolvable camera, the terminal auto-promotes the implicit default into a concrete terminal-owned Camera node bound to that viewport (terminal-owned, addressable only by the owning token for sync-back, F1) so orbit/zoom have stable state to write. Without explore, the default camera stays as per-frame scratch (VIEW-5).
- Rationale: USER DECISION: finding recommendation (camera Optional with implicit auto-framing default). Principle 1 zero-config symmetry; principle 2 (explicit camera is the opt-in). Defining the default once (shared with VIEW-5) avoids divergence. The explore nuance is required because §12.3 explore mutates a Camera NODE transform — a per-frame scratch camera has nowhere to persist orbit state, so explore must materialize a concrete camera. NOTE: the finding's RGP-adapter justification ('the RGP adapter must synthesize anyway') is MOOT under F2; the zero-config justification is independent and stands.
- Doc change: §10.1: change struct field to `camera: Option<NodeId>, // None ⇒ implicit auto-framing default camera (§VIEW-5/6)`. §10.5: add 'Viewport.camera is optional; omitting it (or naming an unresolved node) uses the implicit auto-framing default camera, mirroring the default material (id 0) and default lighting. Explore (§12.3) requires a concrete Camera node; if explore is enabled on a viewport with no resolvable camera, the terminal materializes a terminal-owned Camera node (addressable only by the owning app, F1) to hold orbit/zoom state.' §11.2/§11.3: add a cross-reference noting camera now joins material and light as zero-config defaults. Strike §4/§6 RGP-adapter camera-synthesis wording (F2).
- Test: Feed handshake + one mesh node + a `tgp;vp` with NO camera field. ### VIEW-7 [P2] Cached-layer re-composite is wrong when only the text plane moved under the viewport
- Decision: The cached color+depth layer of a viewport is VALID for re-composite ONLY for moves that are pure screen translations of the viewport while the text plane stays at its fixed NDC depth (z=0.5, grounding). Formally: the cached layer may be re-composited (not re-rendered) iff (a) the viewport's content/camera/size dirty flags are clear AND (b) the move is a translation in screen space only (scroll/reflow reposition), because text occupies a constant NDC depth plane so the depth comparison between cached viewport depth and the text plane is invariant under screen translation. Any change that alters the relative depth ordering of viewport geometry vs the text plane — i.e. anything that would change the camera, projection, or per-viewport depth values — forces a re-render (sets content/camera dirty). The cached depth is stored and blitted in the viewport's own projected depth space at the new screen offset; this is correct precisely because the only other depth participant (text) is a constant-z plane. This invariant is documented as the load-bearing reason cache-recomposite is sound.
- Rationale: Finding recommendation chosen (option 1): grounding confirms text sits at a CONSTANT NDC z=0.5 with a LessEqual test (text.wgsl, lib.rs:1483/1545), so a pure screen translation of the cached layer preserves the depth comparison and cache-recomposite is exact. Principle 6 (the dirty-split): this defines exactly which dirty class (viewport-moved-only) qualifies for re-composite vs re-render, generalizing §6.5. Stating the invariant explicitly closes the §10.4 contradiction (it is not 'free' in general, but it IS free under the constant-z text invariant the renderer actually has).
- Doc change: §10.4 'Smooth scroll/resize': replace 'scrolling/moving a viewport that hasn't changed content is a re-composite of the cached layer' with: 'Because the text plane sits at a CONSTANT NDC depth (z=0.5, grounding lib.rs/text.wgsl), a pure SCREEN-TRANSLATION of a viewport (scroll/reflow reposition) preserves the depth comparison between the cached viewport depth and the text plane, so the cached color+depth layer is re-composited at the new offset rather than re-rendered. Re-render is forced by any content/camera/size change (which alters viewport-local depth relative to the text plane). This translation-only invariant is what makes cache-recomposite exact; it holds only while text remains at a constant z.' §6.5 viewport row: clarify 'just re-blit cached layer if only moved (screen-translation only)'.
- Test: Feed handshake + scene + inline viewport; render once (CPU-side: populate the cached-layer-valid flag and record scene_revision / viewport dirty). Scroll the terminal by N rows (translation only): assert the viewport's cached-layer-valid flag remains true, no re-render was triggered (a render-count or 'recompute world matrices' accessor unchanged), and the composited screen rect translated by the expected pixel delta. Then send a camera-changing patch (or resize the viewport cells): assert the cached-layer-valid flag is cleared and a re-render is scheduled. This is fully CPU-side: assert the dirty-class transitions, not pixels.

### VIEW-8 [P1] Z-order ties between overlapping viewports (and pinned vs inline) are unresolved
- Decision: Overlapping viewports composite in a TOTAL, DETERMINISTIC order: primary key `z: i32` ascending (higher z composites on top), tie-broken by ViewportId ascending (stable, deterministic). Inline and pinned anchors share ONE z-space with NO implicit layer separation: a pinned viewport does NOT automatically sit above an inline one — apps control all stacking via `z`. With F1, ViewportId is allocated within the owning token's namespace; the global composite order uses the tuple (z, owning-token-order, ViewportId) so the tiebreak is total across tokens and stable (token order = handshake order). The compositor iterates viewports in this sorted order every frame; ordering never depends on HashMap iteration or creation-time insertion into an unordered map.
- Rationale: Finding recommendation chosen (break z ties by ViewportId; inline/pinned share one z-space). Principle 3/reliability: a total deterministic order eliminates flicker from non-deterministic compositing on ties. Principle 1 (app-authoritative): apps decide pinned-vs-inline stacking via z rather than the terminal imposing a layer policy. F1 adds the owning-token component so cross-token ties are still total and deterministic (and a token cannot reorder another token's viewports, only its own z-values).
- Doc change: §10.4 'Z-order': replace with 'Overlapping viewports composite in a total deterministic order: by `z` ascending (higher z on top), ties broken by ViewportId ascending. Inline and pinned anchors share ONE z-space — pinned does NOT implicitly sit above inline; apps control all stacking via `z`. Across apps (F1 tokens), the tiebreak tuple is (z, owning-token-order, ViewportId), keeping the order total and stable. The compositor sorts every frame; order never depends on map iteration.'
- Test: Feed handshake + Camera + two overlapping viewports id=2 and id=3 with the SAME z (e.g. z=5); assert via the compositor-order accessor that the deterministic order is [2,3] (ViewportId ascending) regardless of creation order — create them in both orders in two test cases and assert identical composite order. Pinned/inline test: an inline z=10 and a pinned z=5 overlapping; assert inline composites above pinned (z wins, no implicit pinned-on-top). Cross-token (F1): token A vp id=2 z=5, token B vp id=2 z=5 (same numeric id in separate namespaces); assert the composite order is total and stable using token order as the secondary key.

### VIEW-9 [P2] Transparent (clear=None) depth-composite exactness for text behind vs in-front is underspecified
- Decision: Each viewport's offscreen color target uses PREMULTIPLIED ALPHA. Pixels where no fragment was drawn have alpha=0 (fully transparent); drawn opaque fragments have alpha=1. For clear=None the composite into the main framebuffer is a straight 'over' blend of the premultiplied viewport color onto whatever cell/text content lies beneath, with the depth test gating ONLY drawn fragments: a drawn opaque fragment depth-tests against the text plane (LessEqual vs z=0.5) so geometry in front of text covers it and geometry behind text is hidden; an un-drawn (alpha=0) pixel contributes nothing and the underlying text/cell shows through exactly. For clear=Some(rgba) the offscreen is cleared to that opaque color (alpha=1) so the viewport occludes its cells (VIEW-3a). Translucent fragments pick a single depth for the test (the existing §10.4 honest approximation) and blend over; only fully opaque geometry is exact. The offscreen depth buffer is cleared to FAR so un-drawn pixels never spuriously occlude text.
- Rationale: Finding recommendation chosen (premultiplied-alpha offscreen; un-drawn alpha=0 reveals text; depth gates drawn fragments only). This is the only option that prevents the inline viewport from 'punching a hole' over text it was meant to overlay. Grounding: text is at constant z=0.5 with LessEqual, so a drawn fragment's depth test against text is well-defined. Premultiplied alpha is the standard correct compositing for over-blend and integrates cleanly with VIEW-3's clear-tied occupancy and VIEW-7's cached-layer (alpha+depth both cached). Principle: honest about translucency being approximate (already in §10.4).
- Doc change: §10.4: add a 'Transparent fill' paragraph: 'Offscreen color targets use premultiplied alpha. Un-drawn pixels have alpha=0; for clear=None the composite is a straight over-blend onto the underlying cell/text content, and the depth test gates only drawn fragments (a drawn opaque fragment occludes text per the LessEqual test vs the z=0.5 text plane; an alpha=0 pixel reveals text exactly). The offscreen depth buffer clears to FAR so empty pixels never occlude. clear=Some clears the color target to an opaque color (the viewport occludes its cells, §VIEW-3). Translucent fragments remain the documented single-depth approximation; only opaque geometry is exact.'
- Test: CPU-side: assert the offscreen-target descriptor for a clear=None viewport specifies premultiplied-alpha blend and a depth-clear value of FAR (queryable via the render-config/target-spec accessor without a GPU). Assert clear=Some yields an opaque clear color (alpha=1). Assert the composite blend-state for clear=None is 'over' (src=One, dst=OneMinusSrcAlpha) vs clear=Some being opaque-replace. Combined with VIEW-3: create a clear=None viewport over text 'abc' and assert the cell glyphs are retained in the buffer (composite-over, not occluded), whereas clear=Some flags them occluded.

### VIEW-10 [P0] Cell rect off-screen, larger than screen, or zero-size has no defined handling
- Decision: The terminal NEVER allocates offscreen/depth targets for area outside the visible screen. Behavior is: (1) ZERO-SIZE (cols=0 or rows=0): the viewport is created (legal) but is treated as NOT-RENDERED — no offscreen target is allocated, no composite occurs — until it later gains non-zero size via vp update or reflow. (2) PARTIALLY OR FULLY OFF-SCREEN: the rendered/allocated region is CLAMPED to the on-screen intersection of the pixel rect with the terminal viewport; only the on-screen portion gets an offscreen target. A fully off-screen rect allocates nothing and is not composited (state retained). (3) OVERSIZED: the terminal advertises `max_viewport_px_w`/`max_viewport_px_h` (and the existing max_vram_mb). A requested pixel rect whose ON-SCREEN clamped size still exceeds the per-viewport pixel cap is REJECTED with `tgp;x;code=cap_exceeded;detail=max_viewport_px` (routed to owning token, F1) — the viewport is not created/updated. Because allocation is always clamped to on-screen, a 10000x10000 cell rect can never demand a 10000x10000 allocation (it allocates at most the screen-sized intersection, then is further bounded by the pixel cap). Inline viewports are additionally bounded by VIEW-2's cell caps before pixel mapping.
- Rationale: USER DECISION: finding recommendation chosen (clamp to on-screen intersection; zero-size = not-rendered; advertise max viewport pixel size; never allocate off-screen). Principle 3 directly: this closes the unbounded-allocation/VRAM-DoS vector §15.1 cites — clamping to the screen makes allocation independent of the requested rect magnitude. Principle 4 (advertised caps so the app owns fallback). Structured rejection over silent behavior (§15.3). Zero-size-as-not-rendered avoids a degenerate target.
- Doc change: §7.1/§15.2: add `max_viewport_px_w`/`max_viewport_px_h` to advertised caps. §10.3: add 'Allocation is always clamped to the on-screen intersection of the viewport pixel rect with the terminal viewport — off-screen area is never allocated. A zero-size cell rect (cols=0 or rows=0) creates a not-rendered viewport (no target) until it gains size. A pixel rect whose on-screen size still exceeds the advertised max_viewport_px cap is rejected with `tgp;x;code=cap_exceeded;detail=max_viewport_px` and not created. This makes an oversized cell rect a bounded (screen-sized at most) allocation, neutralizing the VRAM-DoS vector (§15.1).' §15.2: list the pixel caps.
- Test: Feed handshake; assert `tgp;r` advertises max_viewport_px_w/h. Zero-size: `tgp;vp;cells=0,0,0,16`; assert viewport exists but its offscreen-target accessor reports None/not-allocated and it is absent from the composite list. Off-screen: a viewport whose pixel rect lies entirely below the screen; assert allocated target = None, no composite, viewport retained. Partial: a viewport half off the right edge; assert the allocated target size equals the on-screen intersection (clamped), not the requested size. ### VIEW-11 [P1] clip_to_scroll_region under tmux: terminal cannot see tmux pane geometry
