# MATE resolutions (Materials, lighting, MSAA, tone-map, theme-tint (MATE))

### MATE-1 [P0] Mixed default-material + PBR nodes in one viewport: tone-map applied to whom?
- Decision: Every TGP viewport renders ALL nodes (default-material and PBR) into ONE linear-light offscreen color target, and a single per-viewport tone-map operator (render.tone_map: none/Reinhard/ACES, default none) is applied to the whole resolved linear target uniformly before sRGB-encode and composite. The default material is therefore defined as a LINEAR-light shader (its base/tint/brightness inputs are linearized from sRGB on input, lit in linear, written linear). There is no per-pixel material-class branch and no two-subtarget split: tone-map is unconditionally a whole-viewport stage. With the default operator 'none' (passthrough clamp to [0,1]), a default-only viewport is visually identical to a plain linear render; choosing Reinhard/ACES tone-maps default and PBR pixels identically. The RGP-byte-stability concern in this finding is MOOT under F2 (no adapter, no rgp.wgsl reproduction requirement).
- Rationale: F2 removes the only reason to special-case default material (matching legacy rgp.wgsl post-tone-map). With a clean break, the simplest correct rule is one linear pipeline + one whole-viewport tone-map, which is unambiguous regardless of node mix and satisfies principle 6 (generalize, don't special-case) and MATE-9's linear-internal mandate. Defaulting the operator to 'none' means mixing PBR into a viewport never silently alters default-material color unless the app explicitly opts into a tone-map operator.
- Doc change: Section 11.1 flow + 11.2 Materials: change 'apply per-viewport tone-map (if PBR/linear)' to 'apply the per-viewport tone-map operator (render.tone_map, default none) uniformly to the whole linear offscreen color target, then sRGB-encode'. In 11.2 redefine the default material as linear-light (inputs linearized from sRGB, lit and written in linear). Delete the implication that tone-map is PBR-only. Note that the default operator 'none' is a clamp-only passthrough so default-only viewports are unchanged.
- Test: (1) Send a patch building one default-material Mesh + one PBR Mesh in a viewport with render.tone_map omitted; assert the viewport's resolved RenderOpts.tone_map == None and that both nodes route to the single linear color target (assert pipeline-class tags on both draw records, one shared target id). (2) Same scene with render.tone_map=aces; assert the tone-map stage flag is set once at viewport scope (not per-node) in the CPU-side render plan. (3) Default-only viewport with tone_map omitted: assert no tone-map op is emitted (operator None short-circuits) and color target format is the linear target. All via Parser::advance + &self render-plan accessors, no GPU.

### MATE-2 [P1] Default material 'exact look' underspecified: hemispherical term, ambient, brightness range
- Decision: Pin exact constants for the TGP default material as a clean-break definition (NOT reproducing rgp.wgsl; the adapter/byte-stability half of this finding is MOOT under F2). Default material = Lambertian diffuse + constant ambient + a soft hemispherical term, all in linear space: key light dir = normalize((-0.3, -1.0, -0.4)) in view space, key color = linear(1.0,1.0,1.0), key intensity = 1.0; ambient (used only when zero registered lights, see MATE-3) = linear(0.12,0.12,0.12); hemisphere sky = linear(0.30,0.34,0.40), ground = linear(0.16,0.14,0.12), hemisphere weight = 0.25 along view-up. final_linear = clamp(base_linear x tint_linear x brightness, 0, large) x (ambient + hemi + key x N.L). brightness is a scalar clamped to [0.0, 8.0]; values outside are clamped (not an error, brightness is a continuous gain not a resource). The hemisphere term is ALWAYS on (it is part of the one default material; there is no legacy/no-hemisphere mode because there is no legacy).
- Rationale: F2 deletes the 'must match hardcoded sun bit-for-bit' constraint and the adapter entirely, so we are free to specify the look as we like and there is no golden-image-against-RGP requirement. Pinning exact constants satisfies principle 4 (apps can predict the look) and removes implementer divergence. Always-on hemisphere is simpler than a gated flag and the legacy-gating rationale is moot.
- Doc change: Section 11.2: replace the prose '(+ a soft hemispherical term)' and 'generalizes rgp.wgsl' with a normative constants block (key dir/color/intensity, ambient, hemisphere sky/ground/weight, brightness clamp [0,8]) and a one-line formula. Remove the 'generalizes rgp.wgsl' phrasing entirely (clean break per F2). State the hemisphere term is unconditional.
- Test: (1) Send node.upsert with a Mesh + tint and a brightness=2.5; assert the CPU-side resolved material params (key dir, ambient, hemi sky/ground/weight, effective brightness) equal the pinned constants and brightness==2.5. (2) Send brightness=20.0; assert resolved brightness clamped to 8.0 and NO x error is queued. (3) Send brightness=-1.0; assert clamped to 0.0. Assertions read &self material-param accessors; no GPU.

### MATE-3 [P0] Implicit default lighting vs registered Light nodes: replace or augment?
- Decision: The built-in key+ambient+hemisphere is an IMPLICIT default that is fully disabled for a viewport the moment that viewport's visible subtree contains >= 1 Light node; from then on the default material is lit ONLY by registered lights (default-material nodes DO respond to registered lights, sharing the same forward lighting loop as PBR). The switch is per-viewport and evaluated per frame from the visible-subtree light set (consistent with MATE-4's per-viewport count). An opt-in viewport render flag render.keep_default_light=true keeps the built-in key+ambient+hemisphere on additively alongside registered lights for apps that want a guaranteed fill. Default of that flag is false (replace).
- Rationale: Matches the finding recommendation and principle 1/2: once an app registers lights it has taken authorship of lighting, so the terminal stops injecting its own (no uncontrollable additive fill). The opt-in keep-flag preserves the 'single weak light looks broken' escape hatch without making augment the surprising default. Per-viewport evaluation is required because lights are nodes scoped per F1 token but visibility is per-viewport subtree.
- Doc change: Section 11.3: after 'lit by a built-in key + ambient' add: 'The built-in key+ambient+hemisphere is an implicit default disabled per-viewport whenever that viewport's visible subtree contains at least one Light node; thereafter only registered lights illuminate, and default-material nodes are lit by registered lights via the same forward loop as PBR. An opt-in render.keep_default_light flag (default false) retains the built-in lighting additively.' Add render.keep_default_light to RenderOpts in 10.1/11.4.
- Test: (1) Build a viewport with a Mesh and no Light nodes; assert CPU-side effective-light-set for that viewport == [built-in key] and ambient applied. (2) Add a Light node into the viewport's root subtree via patch; assert effective-light-set == [that registered light] and built-in key flag == off. (3) Same with render.keep_default_light=true; assert effective-light-set includes BOTH the registered light and the built-in key. (4) Two viewports sharing the scene, one with root subtree excluding the Light: assert the excluding viewport still has built-in key on. All via &self per-viewport lighting-state accessors.

### MATE-4 [P1] Per-viewport light-count cap exceeded: no defined behavior
- Decision: Advertise max_lights in the 7.1 capability reply. The effective light set per viewport per frame is computed from the visible subtree; if it contains more than max_lights Light nodes, the renderer DETERMINISTICALLY selects the max_lights highest-intensity lights (intensity = light.intensity scalar; ties broken by ascending node id lexicographic order) and ignores the rest for that frame. This selection never crashes and never produces nondeterministic shading. Going over cap also queues a one-time-per-viewport structured event/error tgp;x;code=cap_exceeded;detail=max_lights (routed only to the owning F1 token, and only if that app opted into error reporting); the patch that pushed it over cap is NOT rejected (lights are dynamic/animated; rejecting a transform patch because an animated light drifted into view would violate principle 1). The over-cap state clears (and may re-fire once) when the count drops back under cap.
- Rationale: Matches the finding recommendation and reconciles principle 3 (structured feedback, deterministic) with principle 1 (don't reject app transforms for a soft rendering limit). Deterministic highest-intensity selection avoids the nondeterministic mid-animation shading the finding warns about. F1 scoping is honored: the error routes only to the owning token. Hard-rejecting at node.upsert (an option) is wrong because visibility/animation make the visible count dynamic and per-viewport, not knowable at upsert.
- Doc change: Section 7.1 reply example: add max_lights=8 to the caps list. Section 11.3: replace 'a per-viewport light-count cap (advertised in caps)' with the deterministic selection rule (highest-intensity, tie-break by node id), the one-time cap_exceeded event per viewport gated on opt-in error reporting and F1 ownership, and an explicit statement that the patch is NOT rejected. Section 15.3: note cap_exceeded;detail=max_lights is a non-fatal (non-txn-rejecting) report.
- Test: (1) Set max_lights=2 (test config), build a viewport whose subtree has 3 Light nodes with intensities 5,3,1 and ids in mixed order; assert CPU-side selected-light-set == the two with intensity 5 and 3, and assert a single queued tgp;x cap_exceeded;detail=max_lights in pty_replies for the owning token. (2) Add a 4th light, still over cap; assert NO second error queued (one-time latch). (3) Hide one light so count drops to 2 then back to 3; assert error may fire again (latch reset). (4) Tie intensities; assert selection by ascending node-id. (5) App that did NOT opt into error reporting: assert selection still deterministic but NO x queued. (6) Assert the over-cap patch still committed (scene_revision bumped, nodes present).

### MATE-5 [P1] Theme-tint exact semantics + palette source undefined
- Decision: Define theme-tint (render.theme_tint, default false) as a bounded MULTIPLY of the terminal's default-foreground color (the palette 'foreground' / SGR default fg, NOT one of the 16 ANSI indices and NOT background) into the default material's DIFFUSE base only, applied as a material-input stage (pre-lighting; see MATE-11). It applies ONLY to: (a) nodes using the default material (MaterialId 0), and (b) only nodes whose per-node tint is the neutral default (white, 1,1,1,1) -- a node with an explicit non-white tint is left untouched so a deliberate red sphere is never recolored by a blue theme. It NEVER applies to PBR-material nodes and never to baseColor of registered materials. The multiply is bounded: effective_diffuse_linear = base_linear x lerp(white, fg_linear, theme_tint_strength) with theme_tint_strength fixed at 1.0 in v1 (the flag is boolean; fg is read once per frame from the active palette).
- Rationale: Matches the finding recommendation and resolves the collision with per-node tint (skip explicitly-tinted nodes) and with PBR (default-material only). Using default fg (a single well-defined source) makes it predictable across themes. Multiplying into diffuse pre-lighting (not a post grade) avoids the hue-shift hazard flagged in MATE-11. Bounded/boolean keeps the wire compact (principle 5).
- Doc change: Section 11.2 Theme-tint bullet: replace the prose with: 'render.theme_tint (default false) multiplies the terminal default-foreground color into the default material diffuse, as a pre-lighting material-input stage. It applies only to default-material (MaterialId 0) nodes whose per-node tint is neutral white; nodes with an explicit non-white tint and all PBR nodes are unaffected. Palette source = the active default foreground color (linearized). Boolean in v1.' Cross-reference MATE-11 ordering.
- Test: (1) Default-material Mesh with neutral white tint in a viewport with theme_tint=true; assert CPU-side resolved diffuse-input == base x linear(fg). (2) Same node but explicit tint=red; assert resolved diffuse-input == base x red (NOT fg-multiplied; theme-tint skipped). (3) PBR-material node with theme_tint=true; assert its baseColor is unchanged (theme-tint flag not applied). (4) theme_tint=false; assert no fg multiply. Use an injectable palette so fg is a known constant; assert via &self resolved-material-input accessors, no GPU.

### MATE-6 [P1] Default MSAA sample count unspecified; cost vs VRAM cap unmodeled
- Decision: Default render.msaa = 4x. Advertise the GPU-supported sample counts in the 7.1 reply as msaa=1,4 (extend to 2,8 only if the adapter reports support). A requested sample count not in the supported set is silently clamped DOWN to the nearest supported count <= requested (never up; never an error -- MSAA is a quality knob, not a resource the app must size). The effective clamped count is reported back to the app via the viewport ack (a;vp=<id>;msaa=<n>) when the app subscribed to acks. MSAA offscreen color+depth memory counts against max_vram_mb: a viewport's VRAM charge = pixels x samples x (color_bytes + depth_bytes) + the 1x resolve target + the 1x pick target. The pick target is ALWAYS 1x (see MATE-7).
- Rationale: Matches the finding recommendation. 4x is the standard quality/cost default; advertising supported counts lets the app reason about VRAM (principle 4). Clamping (not erroring) keeps a viewport from failing on a GPU that lacks 8x while still being predictable via the ack report. Counting MSAA memory against max_vram_mb makes the advertised cap honest.
- Doc change: Section 11.4: 'render.msaa is per-viewport; default 4x. Supported sample counts are advertised (msaa= in 7.1). A requested unsupported count is clamped down to the nearest supported value and the effective count is reported in the viewport ack. MSAA color+depth memory counts toward max_vram_mb; the pick target is always 1x.' Section 7.1 reply: add msaa=1,4 to the caps. Section 15.2: list MSAA-multiplied offscreen memory as a contributor to the VRAM cap.
- Test: (1) Create a viewport with render.msaa omitted; assert resolved RenderOpts.msaa == 4. (2) Create with msaa=8 on an injected GPU-caps stub advertising {1,4}; assert resolved msaa clamped to 4 and an a;vp=...;msaa=4 ack queued (when ack subscribed). (3) Create with msaa=3; assert clamped to 1 (nearest supported <= 3) -- wait, with {1,4} nearest <=3 is 1; assert ==1. (4) Assert CPU-side VRAM accounting for the viewport includes samples-multiplied color+depth plus a 1x resolve and 1x pick target. All via &self viewport RenderOpts + vram-accounting accessors; GPU-caps injected as a stub.

### MATE-7 [P0] MSAA on the pick target would corrupt color-ID picking
- Decision: The pick target is ALWAYS single-sample (1x), is NEVER MSAA-resolved, and is NEVER tone-mapped, regardless of the viewport's render.msaa or render.tone_map. Pick rendering uses a dedicated 1x non-MSAA pass with nearest/point semantics; node-id+instance-index colors are written and read back unmodified. The whole-viewport tone-map (MATE-1) and MSAA resolve (MATE-6) apply ONLY to the color target, never the pick target.
- Rationale: Matches the finding recommendation; this is a correctness invariant (averaging id colors yields nonexistent ids and mis-routes events, the exact bug the finding identifies). Writing it down is required because 11.1 lists tone-map+resolve as viewport-wide steps that would otherwise read as applying to the pick pass too.
- Doc change: Section 11.1 flow: annotate the pick line as '(pick pass: always 1x, never tone-mapped, never resolved)'. Section 12.4: add 'The pick target is always single-sample; MSAA and tone-map never touch it, so id colors read back exactly.' Section 11.4: reiterate pick target is always 1x.
- Test: (1) Viewport with render.msaa=4 and a pick subscription; assert the CPU-side render plan has the color target sample_count==4 but the pick target sample_count==1, and the tone-map/resolve stage list does NOT reference the pick target. (2) Viewport with tone_map=aces; assert pick target has no tone-map stage attached. (3) Encode node-id 0x010203 into a pick pixel (CPU-side pick buffer model) and assert exact readback resolves to that node id with no averaging. Via &self render-plan + pick-buffer accessors, no GPU.

### MATE-8 [P1] Accepted texture formats undefined; caps reply lacks texture-format/dimension advertisement
- Decision: v1 accepts exactly two texture sources: (a) PNG byte assets via asset.add fmt=png, decoded by ONE hardened PNG decoder, and (b) textures embedded in GLB (decoded by the same GLB-embedded image path, which itself is restricted to PNG; embedded JPEG is rejected in v1 to keep a single decoder). No standalone JPEG, no raw RGBA, no KTX2/Basis in v1. Advertise tex_fmt=png and max_tex_dim=<N> (e.g. 4096) in the 7.1 reply. A texture exceeding max_tex_dim on either axis, or any non-PNG byte asset, is rejected with a structured x;code=parse_error;detail=tex_format or detail=tex_dim, rejecting the whole txn atomically (per 8.6). Decode is bounded by the max decode/parse-time cap (15.2) against decompression bombs.
- Rationale: Matches the finding recommendation, narrowed to a single decoder (PNG) for the smallest attack surface (principle 3) while remaining useful. GLB-embedded restricted to PNG avoids pulling in a second (JPEG) decoder. Advertising tex_fmt+max_tex_dim lets the app pre-trim (principle 4). Rejecting over-cap/unknown formats with structured errors (not silent) satisfies principle 3.
- Doc change: Section 11.2: replace 'optional texture maps (texture = an asset of an image type; KTX2/Basis support is a later add)' with 'v1 textures: PNG byte assets (asset.add fmt=png) or PNG images embedded in GLB; one hardened PNG decoder. JPEG/KTX2/Basis deferred.' Section 7.1 reply: add tex_fmt=png;max_tex_dim=4096. Section 15.2: note texture decode bounded by decode-time cap; over-dimension/unknown-format rejected with parse_error. Section 8.6: fmt enum for asset.add includes glb,png.
- Test: (1) asset.add fmt=png with a valid small PNG within max_tex_dim; assert asset stored as a texture and asset_revision bumped. (2) asset.add fmt=jpeg; assert whole txn rejected with x;code=parse_error;detail=tex_format and scene unchanged. (3) asset.add fmt=png whose header declares dimensions > max_tex_dim; assert x;code=parse_error;detail=tex_dim and txn rejected (dimension checked from header before full decode). (4) GLB with embedded JPEG texture; assert parse_error;detail=tex_format. All via Parser::advance + &self asset-map + pty_replies accessors; decoder fed bytes, no GPU.

### MATE-9 [P0] color=srgb cap vs PBR linear-light: where does sRGB/linear conversion happen?
- Decision: All wire colors (per-node tint, per-instance tint, default-material base, PBR baseColor, theme-tint fg source, clear color) are sRGB-encoded 8-bit-or-float RGBA on the wire. PBR scalar params (metallic, roughness, occlusion strength, emissive intensity) and TRS/geometry are linear/numeric (NOT color-managed). On input the terminal linearizes all color fields once into linear space. The ENTIRE viewport renders in linear internally (default material is linear per MATE-1, PBR is linear). After lighting, the per-viewport tone-map runs in linear, THEN the result is sRGB-encoded into the offscreen color target, so the composite against the sRGB text plane (NDC z=0.5) matches automatically. The offscreen color target is a linear-data UNORM that the shader sRGB-encodes into explicitly (NOT an *_SRGB auto-encoding format), so tone-map output is well-defined and the depth-tested composite sees sRGB-encoded color exactly like text. color=srgb in 7.1 stays a single value (no linear negotiation in v1).
- Rationale: Matches the finding recommendation and is the standard-correct pipeline. Explicit sRGB-encode-in-shader (rather than an _SRGB target format) keeps tone-map math in linear and the composite unambiguous. Defining tints as sRGB and PBR scalars as linear resolves the per-field ambiguity. Keeps color=srgb single-valued (principle 5, compact).
- Doc change: Section 11.2: add a 'Color space' paragraph stating wire colors are sRGB, scalars are linear, the pipeline linearizes on input, renders linear, tone-maps in linear, then sRGB-encodes into the offscreen target; composite against the sRGB text plane is therefore exact. Section 7.1: clarify color=srgb means wire colors are sRGB-encoded. Section 10.4: note offscreen color targets carry sRGB-encoded color for the depth-tested composite.
- Test: (1) Send a node tint of sRGB (188,188,188) and assert CPU-side linearized stored value ~= 0.5 linear (within epsilon), confirming linearization-on-input. (2) Assert PBR roughness=0.5 stored as 0.5 verbatim (NOT linearized). (3) Assert the viewport color target descriptor in the render plan is the linear-UNORM target with an explicit sRGB-encode stage flag, not an _SRGB format flag. (4) Assert clear color sent as sRGB is linearized for the linear clear but the composite path treats final pixels as sRGB. Via &self color-store + render-plan accessors, no GPU.

### MATE-10 [P1] Per-instance material override vs per-viewport PBR/default pipeline selection
- Decision: v1 constrains per-instance material: an Instanced node has ONE shared material (the node's material id) that fixes the SHADING MODEL and pipeline for the whole instance buffer. Per-instance records may vary only TINT (and the per-instance transform). The per-instance material field is DROPPED in v1 (tint-only), matching the §16 open-questions lean; a per-instance MaterialId that differs in shading model is rejected at validation with x;code=parse_error;detail=instance_material_mixing, rejecting the txn. This guarantees one pipeline per Instanced draw, preserving the single draw_indexed(0..N) instancing claim. Full per-instance material handles (bindless/material arrays) stay deferred (§16).
- Rationale: Matches the finding recommendation. A single draw can bind only one pipeline, so mixed-model instances are physically incompatible with the one-draw claim. Dropping per-instance material to tint-only (the existing §16 lean and §6.4 'limited in v1 to a tint + a single shared material') is the cleanest v1 rule and keeps the instancing win intact. Validation rejection (not silent split) satisfies principle 3.
- Doc change: Section 6.4: change the InstanceBuffer record from '{ transform, tint, material: Option<MaterialId> }' to '{ transform, tint }' for v1 and state per-instance material is deferred; reaffirm 'one shared material fixes the pipeline'. Section 11.1: note the instanced draw uses the node's single material/pipeline. Section 15.3: add instance_material_mixing to error detail enum (for any client that still sends a per-instance material field). Section 16: keep per-instance material handles deferred.
- Test: (1) node.instances with a uniform shared material and per-instance tints; assert one CPU-side draw record with instance_count==N and a single pipeline/material binding. (2) A patch carrying a per-instance material field (legacy/forward field) that differs in shading model; assert x;code=parse_error;detail=instance_material_mixing and txn rejected (scene unchanged). (3) Per-instance material field equal to the node's material (same model); assert accepted and still one draw. Via &self draw-plan + pty_replies accessors, no GPU.

### MATE-11 [P1] theme-tint and tone-map ordering vs the per-viewport composite
- Decision: Fixed pipeline order per viewport: theme-tint (default-material diffuse input, MATE-5) -> lighting (linear) -> [whole-viewport, all nodes, in linear] tone-map (MATE-1, default none) -> sRGB-encode -> MSAA resolve -> depth-tested composite vs text plane. Theme-tint is a material-INPUT stage applied before lighting and ONLY to default-material nodes (never PBR); it is therefore inside the linear render and naturally precedes tone-map, with no post-resolve color grade. Because theme-tint runs pre-lighting per-node and tone-map runs whole-viewport post-lighting, their interaction in a mixed default+PBR viewport is fully defined: theme-tint touches only the default-material nodes' diffuse input; tone-map then applies to the combined linear result uniformly.
- Rationale: Matches the finding recommendation and composes cleanly with MATE-1 (whole-viewport tone-map), MATE-5 (theme-tint = default-material diffuse multiply, pre-lighting), and MATE-9 (linear render then sRGB-encode). Defining theme-tint as a shader-input stage avoids the post-tone-map hue-shift hazard the finding warns about and makes the ordering total and unambiguous.
- Doc change: Section 11.1 flow: insert the explicit ordered stage list 'theme-tint (default-material diffuse input) -> lighting -> tone-map (whole viewport, linear) -> sRGB-encode -> MSAA resolve -> composite' and state theme-tint is pre-lighting and default-material-only. Section 11.2: cross-link theme-tint (MATE-5) and tone-map (MATE-1) to this canonical order.
- Test: (1) Mixed viewport (default node with neutral tint + PBR node), theme_tint=true, tone_map=aces; assert the CPU-side render-plan stage order is exactly theme-tint(default node)->light->tonemap(viewport)->srgb-encode->resolve->composite, that theme-tint is attached only to the default node, and tone-map is a single viewport-scoped stage. (2) PBR-only viewport with theme_tint=true; assert NO theme-tint stage attached to any node (default-material-only). (3) Default-only viewport with tone_map=none; assert stage list omits the tone-map op. Via &self ordered-render-plan accessor, no GPU.
