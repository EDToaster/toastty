# SCEN resolutions (SCEN — Scene model, nodes, transforms, dirty, instancing, ids, patch semantics)

### SCEN-1 [P0] Clearing optional node fields under sparse-merge: CBOR null = clear, key-absent = preserve
- Decision: node.upsert is a sparse merge with a three-way distinction per optional field, decided by the CBOR map: (a) key absent => field preserved unchanged; (b) key present with CBOR null (major type 7, value 22) => field cleared to its type default; (c) key present with a value => field set to that value. Defaults on clear: parent -> None (node becomes a root, added to roots set; its existing children and animation phase are retained); alt -> None; tint -> opaque white [255,255,255,255] (the identity multiply in the SCEN-11 chain); trs sub-fields are NOT individually nullable (trs is replaced wholesale when present, see note). Required structural fields (id) may never be null. A null on a non-nullable field (id, or the kind-selector key when present) is a parse_error (op rejected, txn atomic-rejected per 8.6) with code=null_not_allowed, detail naming the field. Clearing parent re-roots the node in the same txn's final-state validation (interacts with SCEN-3 cycle check and SCEN-4 ref resolution).
- Rationale: CBOR natively distinguishes absent-key from explicit-null at zero wire cost, so we get a clear/preserve/set trichotomy without a side-channel clear:[...] list or a forced-required parent. Re-rooting via parent:null is the only non-destructive detach (remove+re-add would lose children and animation phase, per the finding's own concern). Matches the recommendation; conforms to principle 5 (compact wire) and principle 3 (explicit, hardened: a stray null on a structural field is a structured error, not a silent reinterpretation).
- Doc change: §8.6 'Idempotent addressing' bullet: replace 'Omitted fields are preserved.' with: 'node.upsert is a sparse merge over the CBOR op map. For each optional field: key absent = preserve; key present and CBOR null = clear to default (parent->root, alt->none, tint->opaque white); key present with a value = set. parent:null re-roots the node, retaining its children and animation phase. A CBOR null on a non-nullable field (id, kind selector) is rejected: x code=null_not_allowed. trs, when present, is replaced wholesale.' Add a one-line table of per-field clear defaults under §6.1 Node.
- Test: Send patch upsert{id:car,trs:T,alt:'x',parent:p,tint:[1,2,3,4]}; assert node fields populated and car in p's children. (1) Send upsert{id:car,trs:T2} (parent key ABSENT) -> assert parent still p, alt still 'x', tint unchanged, trs==T2. (2) Send upsert{id:car,parent:null} -> assert parent None, car in scene.roots, children of car unchanged, animation phase unchanged. (3) upsert{id:car,alt:null} -> alt None. (4) upsert{id:car,tint:null} -> tint==[255,255,255,255]. (5) upsert{id:null,...} -> assert queued reply is tgp;x;code=null_not_allowed;detail=id and scene unchanged. All via Parser::advance bytes -> &self node accessors / roots accessor / drain_pty_replies.

### SCEN-2 [P0] Kind transitions on an existing node id are forbidden; kind selectors are mutually exclusive per op
- Decision: A node's kind (Group | Mesh | Instanced | Light | Camera) is immutable for the lifetime of its id. An upsert that carries a kind-selector field (mesh / instances / camera / light, or implicitly Group when none is given on first creation) whose implied kind differs from the existing node's kind is rejected: x code=kind_conflict, citing the op index and detail=<existing_kind>-><attempted_kind>. Within a single op the kind-selector fields are mutually exclusive: at most one of {mesh, instances, camera, light} may appear; two or more => x code=kind_conflict;detail=multiple_selectors. On FIRST creation of an id: zero selectors => Group; exactly one selector => that kind. On a subsequent upsert of an existing id: selectors that match the existing kind mutate its kind-specific data in place (e.g. mesh:7 on an existing Mesh swaps its asset/material; instances:<...> on an existing Instanced re-uploads, see SCEN-7); a selector for a different kind => kind_conflict. Changing kind requires explicit node.remove + node.upsert (which, per SCEN-5, cascades children — the app must rebuild them). Whole txn rejected atomically on any kind_conflict.
- Rationale: Immutable-per-id keeps NodeKind a stable discriminant: pick targets, instance buffers, and the asset_revision-vs-scene_revision accounting never have to migrate a node's storage mid-life. Mutually-exclusive selectors remove the 'both mesh and camera' ambiguity at parse time. Matches the recommendation and principle 3 (structured error, no silent reinterpretation). Note: F2 means we do NOT preserve any RGP replace-place kind-morph quirk.
- Doc change: New §8.6 sub-bullet 'Kind is immutable': 'A node's kind is fixed at creation. On first upsert, zero kind selectors => Group; exactly one of {mesh, instances, camera, light} => that kind; two or more => x code=kind_conflict. A later upsert whose selector implies a different kind than the existing node => x code=kind_conflict (change kind via remove+re-add). A matching selector mutates kind-specific data in place.' Update the §6.1 NodeKind comment accordingly.
- Test: (1) upsert{id:n} then upsert{id:n,mesh:7} -> x code=kind_conflict (Group->Mesh), scene unchanged. (2) upsert{id:n,mesh:7} then upsert{id:n,mesh:9,material:3} -> assert kind still Mesh, asset==9, material==3, no error. (3) Single op upsert{id:n,mesh:7,camera:{...}} -> x code=kind_conflict;detail=multiple_selectors. (4) upsert{id:n,instances:<...>} on existing Mesh n -> kind_conflict. Assert via &self node kind accessor + drain_pty_replies.

### SCEN-3 [P0] Cycle and self-parent detection at txn commit; hard parent-chain depth cap as defense-in-depth
- Decision: At txn commit, after applying all ops to a staged copy and resolving refs (SCEN-4), the terminal validates the parent graph: every node's parent chain must terminate at a root within MAX_PARENT_DEPTH steps (cap = 256, advertised in caps as max_node_depth). A self-parent (A.parent=A) or any cycle (A->B->...->A) => reject the WHOLE txn atomically with x code=cycle, detail=<id-in-cycle>, citing the offending op index (the op that introduced or last touched a node on the cycle). A chain that would exceed MAX_PARENT_DEPTH (even acyclic) => x code=depth_exceeded;detail=<id>. The lazy render-time world-matrix walk additionally carries the same depth cap as a belt-and-suspenders guard, but commit-time validation guarantees it is never hit by committed state. Detection is an iterative visited-set walk (no recursion) so the validator itself cannot stack-overflow.
- Rationale: A cycle is a guaranteed render-time hang/stack-overflow reachable from untrusted PTY bytes (principle 3). Commit-time atomic rejection keeps the committed scene always-acyclic so the hot lazy walk needs no per-frame cycle bookkeeping; the depth cap bounds even pathological-but-acyclic chains and is advertised so apps can pre-trim. Matches the recommendation. Not mooted by F2.
- Doc change: New §6.2 bullet: 'The committed scene is always acyclic. At txn commit the terminal walks every node's parent chain (iterative, visited-set); a cycle or self-parent => x code=cycle; a chain exceeding max_node_depth (256, advertised) => x code=depth_exceeded. The whole txn is rejected, scene unchanged. The render-time walk also caps depth as defense-in-depth.' Add max_node_depth to the §7.1 caps list and §15.2 resource caps.
- Test: (1) Single txn: upsert{id:a,parent:b}, upsert{id:b,parent:a} -> x code=cycle, scene has neither a nor b (atomic). (2) upsert{id:a,parent:a} -> x code=cycle;detail=a. (3) Pre-existing chain root->...; then upsert{id:leaf,parent:self-or-ancestor} forming a cycle -> x code=cycle and scene unchanged (leaf's parent still old value). (4) Build a 257-deep chain in one txn -> x code=depth_exceeded. Assert via &self parent/roots accessors + drain_pty_replies; no GPU.

### SCEN-4 [P0] All refs (parent/asset/material) resolve against the txn's final committed state; order-independent; dangling => atomic reject
- Decision: A txn is validated as a whole against its FINAL post-apply staged state, making intra-txn references order-independent: a child op may precede its parent op, and a node.upsert{mesh:7} may precede the asset.add{id:7} in the same txn. Resolution rules: (a) parent must name a node that exists in the staged final state (created in this txn or pre-existing AND not removed by a later op in this txn); unresolved => x code=bad_ref;detail=parent:<id>. (b) mesh/asset/material/tex refs must name an asset/material that is COMMITTED in the staged final state — i.e. present pre-txn or fully added (more=0, per SCEN-9) within this txn; an in-flight (more=1) reassembly buffer does NOT satisfy a ref. Unresolved => x code=bad_ref;detail=mesh:<id> (or material:/tex:). (c) A node removed and re-upserted in the same txn resolves to its final state. Any unresolved ref rejects the whole txn atomically (scene unchanged), citing the first offending op index. Within-txn duplicate ids: last-writer-wins for node.upsert merges (each upsert merges onto the running staged node, in op order); asset.add duplicate-of-committed => error (SCEN-9).
- Rationale: F2 USER DECISION removes the RGP-adapter ordering concern entirely (this finding's 'RGP adapter' interaction is MOOT). Final-state resolution matches the atomic-frame promise (8.6: 'all ops apply together or not at all') and frees apps from topologically sorting ops — a major usability contract. Forward refs within a txn are exactly the §18.1/§18.3 examples (node.instances{parent:'mol'} before/with the group, segments referencing assets). Matches the recommendation; conforms to principle 3 (structured bad_ref, never a dangling pointer in committed state).
- Doc change: §8.6 add bullet 'Reference resolution': 'All references (parent, mesh/asset, material, texture) resolve against the txn's final staged state, so ops are order-independent within a txn (a child may precede its parent). Asset/material refs require a fully-committed (more=0) target; in-flight chunks do not satisfy a ref (§8.7, SCEN-9). Any unresolved reference rejects the whole txn: x code=bad_ref, detail=<kind>:<id>, citing the first offending op index.' Note in §4/§8.6 that RGP-adapter ordering is N/A (RGP is independent legacy, see clean-break).
- Test: (1) One txn, child-before-parent: upsert{id:wheel,parent:car,mesh:7}, upsert{id:car}, asset.add{id:7,...} (all out of order) -> assert all committed, wheel.parent==car, car a root, wheel kind Mesh asset 7. (2) upsert{id:wheel,parent:ghost} with no ghost anywhere -> x code=bad_ref;detail=parent:ghost, scene unchanged. (3) upsert{id:m,mesh:7} with no asset 7 -> bad_ref;detail=mesh:7. (4) asset.add{id:7,more=1} + upsert{id:m,mesh:7} in same txn -> bad_ref (in-flight not committed). Assert via &self node/asset accessors + drain_pty_replies.

### SCEN-5 [P0] node.remove cascade-deletes the subtree by default; opt-in reparent:root flag
- Decision: node.remove{id} deletes the node AND its entire descendant subtree (recursive) by default. The removed nodes are erased from nodes, roots, the dirty set, any viewport that names a removed node as camera or root (see below), and any pending pick/event subscription targeting them. An optional field reparent:'root' (string enum; only 'root' supported in v1) changes the behavior to: detach the node's direct children to the scene root (their world transform is NOT preserved/baked in v1 — they keep their local TRS, now relative to world; documented), then delete only the named node. Removing a node that is a viewport's camera or root: the viewport is NOT auto-deleted; instead the dangling viewport ref is an error at commit (x code=bad_ref;detail=viewport:<vp>;camera|root) UNLESS the same txn also updates/removes that viewport — i.e. viewport refs obey the SCEN-4 final-state rule. Removing a non-existent id is a no-op (no error, no revision bump), matching RGP's delete-one-missing-no-bump behavior. A remove bumps scene_revision once (part of the atomic txn) and marks the removed subtree's former parent dirty.
- Rationale: Cascade matches the 'remove the car removes its wheels' intuition in the finding and bounds memory (orphan-leak of 10k nodes is the failure mode of reparent-to-root-by-default). The opt-in reparent flag preserves a subtree when wanted (principle 2: convenience is opt-in). Refusing to silently orphan a viewport's camera/root keeps viewports consistent and reuses the SCEN-4 bad_ref machinery. Matches the recommendation. Not mooted by F2 (scene.clear adapter mapping in the finding is MOOT under F2; RGP stays independent).
- Doc change: New §8.6 bullet 'node.remove cascade': 'node.remove deletes the node and its whole descendant subtree by default. reparent:"root" instead detaches direct children to the scene root (local TRS retained, world transform not baked in v1) and removes only the named node. Removing a node referenced by a viewport (camera/root) is x code=bad_ref unless the same txn also fixes the viewport (final-state rule). Removing a missing id is a no-op.' Remove the §8.6 example's reliance on RGP scene.clear semantics; mark RGP mapping N/A.
- Test: (1) Build car->wheel1,wheel2; remove{id:car} -> assert car, wheel1, wheel2 all gone, roots empty, scene_revision bumped once. (2) remove{id:car,reparent:'root'} -> assert car gone, wheel1/wheel2 now in roots with unchanged local trs. (3) Viewport vp1 camera='cam'; remove{id:'cam'} alone -> x code=bad_ref;detail=viewport:vp1;camera, scene unchanged. (4) Same txn: remove{id:'cam'} + vp destroy vp1 -> both succeed. (5) remove{id:'nope'} -> no error, no revision bump. Assert via &self node/roots/viewport accessors, revision accessor, drain_pty_replies.

### SCEN-6 [P0] Single canonical packed instance layout: mat4 f32 LE + RGBA8 tint, explicit count, hard bounds check
- Decision: node.instances pins ONE canonical layout for v1 (the Trs|mat4 ambiguity in §6.4 collapses to mat4): the op carries count:u32 and two CBOR byte-strings. xforms = count * 64 bytes, each record = 16 little-endian IEEE-754 f32 in column-major order (a mat4 model matrix). tints = count * 4 bytes, each record = R,G,B,A as u8 in sRGB (matches color=srgb cap); tints is OPTIONAL — if absent, all instances default to opaque white. tints, when present, MUST have exactly count records. Validation (hardened, §15.5): xforms.len() must == count*64 and (if present) tints.len() == count*4, else x code=bad_layout;detail=xforms_len|tints_len|count_mismatch. count must be <= max_instances cap, else x code=cap_exceeded;detail=max_instances. NaN/inf in any matrix element => x code=parse_error;detail=instance_nan (reject, do not clamp). Per-instance material handles are NOT in v1 (deferred, §16) — instances share the node's single material. instance_index for picking (§12.4) is the record index 0..count.
- Rationale: This is the hot binary path; an unpinned stride/count is a direct OOB-read risk (principle 3) and makes an interoperable codec impossible (principle 5). Fixing mat4 f32 LE column-major matches the renderer's @location instance vertex attributes with zero CPU re-pack and avoids per-record Trs->mat4 math on the hot path. Explicit count + hard count==len/stride check is the bounds gate. Matches the recommendation, with tints made optional for the common single-color case. Not mooted by F2.
- Doc change: Rewrite §6.4 instance-buffer bullet: 'An Instanced node's buffer is pinned: op fields count:u32, xforms (count*64 bytes = column-major mat4 f32 LE), optional tints (count*4 bytes = RGBA8 sRGB; absent => opaque white). Counts must match exactly or x code=bad_layout; count<=max_instances or x code=cap_exceeded; NaN/inf => x code=parse_error. Per-instance material deferred (§16).' Drop 'Trs|mat4' from the §6.1 InstanceBuffer comment; state mat4-only v1.
- Test: (1) instances{id:pts,mesh:1,count:3,xforms:<192 bytes>,tints:<12 bytes>} -> assert instance buffer has 3 records, matrices == decoded f32, tints == bytes. (2) count:3 but xforms 128 bytes -> x code=bad_layout;detail=xforms_len, node unchanged. (3) count:3, tints 8 bytes -> bad_layout;detail=tints_len. (4) count > max_instances -> cap_exceeded. (5) xforms with a NaN -> parse_error;detail=instance_nan. (6) tints absent -> assert all 3 tints == [255,255,255,255]. Assert via &self instance-buffer accessor + drain_pty_replies; all CPU-side.

### SCEN-7 [P1] node.instances always bumps scene_revision + a dedicated per-node instance-dirty flag; never asset_revision
- Decision: Resolves the 6.4/6.5 contradiction in favor of 6.5's intent: any node.instances op (new buffer, same-size content re-upload, or count change) bumps scene_revision once (within the atomic txn) and sets a dedicated per-node instance_dirty flag on that node. It NEVER bumps asset_revision. The renderer consumes instance_dirty to do a TARGETED instance vertex-buffer re-upload for that node only, independent of mesh re-upload (which remains gated solely by asset_revision per the 96da70a split). If a count change exceeds the node's current GPU instance-buffer capacity, the renderer grows that node's instance buffer as part of consuming instance_dirty — this is still NOT an asset_revision bump (it is per-node GPU-side reallocation, not a shared asset/mesh re-upload). instance_dirty is cleared by the renderer after upload; it is a per-node flag in DirtySet (generalizing the SCEN-10 dirty-flag approach), orthogonal to the node's transform/visibility dirty flag.
- Rationale: If a per-frame point cloud bumped asset_revision it would force needless re-upload of all meshes every frame — the exact regression 96da70a fixed (cited in the finding). A dedicated instance-dirty flag keeps mesh uploads gated by asset_revision while still guaranteeing new instance bytes reach the GPU. Directly generalizes the scene_revision/asset_revision split (principle 6). Matches the recommendation. Not mooted by F2.
- Doc change: §6.5 table: change the 'Node transform/visibility/tint/instance buffer' row to split out instances: add a row 'Instance buffer (node.instances) | scene_revision + per-node instance_dirty | targeted instance-buffer re-upload for that node; never asset_revision (grow buffer in place if count exceeds capacity)'. Update §6.4 'Static instances' bullet to delete 'bumps asset_revision when the buffer identity/size changes' and replace with the instance_dirty rule.
- Test: (1) asset.add + instances{count:N} -> assert asset_revision==1 (from asset.add), scene_revision bumped, node.instance_dirty set. (2) Second instances{count:N} same size -> assert asset_revision UNCHANGED, scene_revision bumped again, instance_dirty re-set. (3) instances{count:N+1000} (grow) -> asset_revision UNCHANGED, instance_dirty set. (4) A pure transform upsert on a different node -> assert that node's transform-dirty set but instance_dirty of the instanced node NOT set. Assert via &self asset_revision()/scene_revision()/dirty-flag accessors; no GPU.

### SCEN-8 [P0] Node ids: hard 64-byte cap, printable non-control non-ESC charset; per-app-token namespacing replaces the one-global-namespace collision concern
- Decision: Node ids are UTF-8 strings, hard-capped at 64 bytes (the §8.4 'e.g.' is removed; 64 is normative, advertised as max_id_bytes). Charset: the byte sequence MUST be valid UTF-8 AND contain no C0 control bytes (0x00-0x1F), no DEL (0x7F), no C1 range (0x80-0x9F), and no ESC (0x1B) — i.e. nothing that could re-enter the app's stdin as a control sequence when echoed in a §12.5 event report. Violation => x code=bad_id;detail=charset|too_long, op rejected, txn atomic-rejected. Per F1, ids are NOT one global namespace: each id is scoped to the owning app's session/namespace token negotiated at handshake; two apps may both use 'cam' without collision, and a tokenless/untrusted writer cannot address or retarget another token's nodes (cross-token addressing => x code=denied;detail=token). The RGP-adapter-synthesized-id collision concern is MOOT under F2 (RGP is independent legacy with its own code path and its own namespace; TGP does not share a namespace with it). Event reports (§12.5) emit ids verbatim only because the charset guarantees they are control-safe; no escaping needed, but a defense-in-depth assertion rejects any id containing a forbidden byte before it can be queued.
- Rationale: Uncontrolled id strings enable memory amplification and — since §12.5 echoes the id back into the app's stdin inside an APC — control/ESC injection (principle 3). A hard cap + control-safe charset closes the injection hole at ingress so the egress path is safe by construction. F1 makes ids token-scoped, which structurally eliminates the app/adapter and app/app collision problem the finding raised (no shared namespace). F2 makes the adapter-prefix half of the recommendation unnecessary — note and drop it.
- Doc change: §8.4 'Node ids' bullet: replace 'bounded length, e.g. <=64 bytes' with 'UTF-8, hard cap 64 bytes (max_id_bytes, advertised); forbidden bytes: C0 (0x00-0x1F), DEL (0x7F), C1 (0x80-0x9F), ESC (0x1B). Violation => x code=bad_id.' Replace the §8.4 'Namespace: one global namespace per session' bullet with the F1 per-app-token scoping rule (ids scoped to the handshake token; cross-token addressing => x code=denied). Strike the §4 adapter-id-synthesis text (RGP independent, see clean-break). Add max_id_bytes to §7.1/§15.2 caps.
- Test: (1) upsert{id:'a'*64} -> ok; upsert{id:'a'*65} -> x code=bad_id;detail=too_long. (2) upsert{id:'ev\x1bil'} (embedded ESC) -> x code=bad_id;detail=charset, scene unchanged. (3) upsert{id:'tab\x09'} -> bad_id;detail=charset. (4) Two distinct tokens each upsert{id:'cam'} -> assert two independent nodes in their respective scopes; token A's remove{id:'cam'} does not affect token B's 'cam'. (5) Tokenless writer upsert{id:'cam'} targeting token A's scope -> x code=denied;detail=token. (6) Valid id flows to a §12.5 event report verbatim (assert queued reply bytes contain the id and no forbidden bytes). Assert via &self node accessor (scoped) + drain_pty_replies.

### SCEN-9 [P1] Chunked asset.add reassembles into an in-flight buffer; immutability and ref-resolution check only committed (more=0) assets
- Decision: A chunked asset.add (§8.7, more=1...more=0) reassembles into a per-id in-flight reassembly buffer that is NOT a registered asset. Rules: (a) The duplicate-id immutability check ('add on an existing asset id is an error', §8.4) fires ONLY against fully-committed assets, and ONLY when the final more=0 chunk would commit. The first chunk (more=1) of id 7 does not error even though later chunks reuse id 7. (b) A second chunk for an id with no open in-flight buffer and no committed asset starts a new buffer; a chunk for an id that is ALREADY committed (exists in assets) => x code=dup_asset;detail=<id> immediately (cannot re-open a committed asset; replace via remove+add). (c) Starting a second concurrent more=1 buffer for an id that already has an open in-flight buffer => x code=chunk_conflict (one in-flight buffer per id). (d) node.upsert{mesh:id} and SCEN-4 ref resolution see an in-flight buffer as NOT present (bad_ref) until more=0 commits. (e) asset_revision bumps exactly once, at more=0 commit (not per chunk). (f) Each chunk is bounded by max_chunk_mb and the running reassembly total by max_asset_mb / max_reassembly_mb (§15.2); overflow => x code=cap_exceeded and the in-flight buffer is dropped. (g) An in-flight buffer left open (no more=0) is reclaimable under a reassembly cap/timeout; it never partially registers.
- Rationale: Without this, every multi-frame asset would self-error on its second chunk (the contradiction the finding identifies). Treating in-flight bytes as a reassembly buffer distinct from a registered asset resolves it cleanly and makes the immutability rule and mesh-ref resolution both check exactly one thing: committed assets. Matches the recommendation and reuses RGP's existing more=1|0 reassembly model and 64/256 MiB caps (generalized, principle 6). Not mooted by F2 (this is native TGP chunking, not RGP-bridging).
- Doc change: §8.7 expand: 'Chunked asset.add reassembles into a per-id in-flight buffer that is not a registered asset. The §8.4 duplicate-id error fires only at more=0 commit and only against committed assets; a chunk targeting an already-committed id => x code=dup_asset; a second open buffer for the same id => x code=chunk_conflict. asset_revision bumps once at more=0. Refs (mesh/asset) do not resolve to an in-flight buffer (bad_ref) until commit. Per-chunk and reassembly-total caps apply; overflow => x code=cap_exceeded and the buffer is dropped.' Cross-link §8.4 immutability to 'committed assets only'.
- Test: (1) asset.add{id:7,more=1,data:A} then asset.add{id:7,more=0,data:B} -> assert single committed asset 7 == A++B, asset_revision==1 (bumped once). (2) Between the two chunks, upsert{id:m,mesh:7} -> x code=bad_ref (in-flight not committed). (3) After commit, upsert{id:m,mesh:7} -> ok. (4) asset.add{id:7,...} after 7 committed -> x code=dup_asset. (5) Two more=1 chunks for id 7 without an intervening commit, from a fresh second begin -> x code=chunk_conflict. (6) Chunk total exceeding max_reassembly_mb -> x code=cap_exceeded and assert no in-flight buffer remains. Assert via &self asset accessor + asset_revision() + drain_pty_replies.

### SCEN-10 [P2] Revisions are u64 everywhere; renderer gate consumes per-node/per-viewport dirty flags, not numeric equality
- Decision: asset_revision and scene_revision are u64 (as §6.1 already declares); the §6.5 narrative no longer cites RGP's u32-wrapping as the gate template — the GATE generalizes, not the width. The renderer no longer repaints by numeric equality of a single counter; it consumes explicit dirty flags: a per-node transform/visibility dirty flag, the per-node instance_dirty flag (SCEN-7), and per-viewport dirty flags (§6.5). The u64 counters remain as coarse monotonic change tokens for accessors/tests and for the asset-vs-scene split decision, but the per-frame 'what to recompute/re-upload' decision reads the dirty sets, which are cleared after consumption. u64 + monotonic increment (saturating at u64::MAX, which is unreachable in practice) eliminates the wrap-equality hole entirely; the counters are documented as 'wrap unreachable in practice'. Increments use saturating_add (not wrapping_add) so the theoretical wrap-to-a-seen-value skip cannot occur even in principle. RGP's existing u32 wrapping counters are untouched legacy (F2).
- Rationale: u64 makes wrap unreachable; switching the gate to dirty flags (which TGP needs anyway for per-node/per-viewport granularity, §6.5) removes any dependence on numeric equality and thus the rare correctness hole the finding identifies. This is a strict generalization of the 96da70a split (principle 6), not a re-spec. Matches the recommendation. RGP's u32 wrapping stays as independent legacy under F2.
- Doc change: §6.1: keep u64; add comment 'monotonic, saturating; wrap unreachable in practice'. §6.5: add a closing paragraph: 'The renderer's recompute/re-upload decision consumes per-node (transform/visibility, instance_dirty) and per-viewport dirty flags, cleared after consumption — not numeric revision equality. The u64 revisions are coarse monotonic change tokens (and the asset-vs-scene split signal), not the per-frame gate.' Update principle 6's wording in §2 to cite the split as the template while noting TGP uses dirty flags for the gate (u32-wrapping is an RGP implementation detail, not inherited).
- Test: (1) Transform upsert on node A -> assert scene_revision increased (u64) AND A's transform-dirty flag set; a sibling B's flag NOT set. (2) Simulate renderer consume() -> assert dirty flags cleared but u64 revision retains its value. ### SCEN-11 [P1] Fixed color chain baseColor x tint x brightness with sRGB->linear tint decode; Instanced forbids node-level tint; single-instance re-tint via partial update
- Decision: One fixed multiply chain for all lit nodes: final_linear = baseColor_linear (texture-sampled or material.base, already linear) * tint_linear * brightness, where tint is sRGB-encoded on the wire (RGBA8 / color=srgb cap) and decoded sRGB->linear before the multiply; alpha multiplies straight through (no sRGB curve on alpha). For the default material (id 0, no PBR), baseColor_linear = 1.0 (white) so the look is tint * brightness * lighting, generalizing rgp.wgsl. Tint location by kind: a Mesh node carries one node-level tint (default opaque white); an Instanced node carries per-instance tints (SCEN-6) and MUST NOT set a node-level tint — an upsert/instances that sets a node-level tint on an Instanced node => x code=kind_conflict;detail=instanced_node_tint. Per-instance tint multiplies exactly like the Mesh node tint (NOT an emissive add, NOT a baseColor replace). Single-instance re-tint (the §12.6 highlight-on-click flow) is supported via a partial instance update op node.instance_set{id, index:u32, tint:[r,g,b,a]} that writes one tints record and sets instance_dirty (SCEN-7) WITHOUT re-sending xforms or the whole buffer — avoiding a full re-upload. index >= count => x code=bad_index. This is distinct from node.instances (which replaces the whole buffer).
- Rationale: An unpinned chain leaves the shader color math and the srgb/linear question undefined; PBR is linear-light so tint must be sRGB-decoded before multiply or colors shift. Multiply (not replace/add) composes predictably with both default and PBR materials and makes the default material a special case (baseColor=white) rather than a separate path. Forbidding a node-level tint on Instanced removes the 'which tint wins' ambiguity. A dedicated single-instance partial update keeps the §12.6 click-highlight cheap (one record, not a full re-upload), reusing the SCEN-7 instance_dirty path. Matches the recommendation. Not mooted by F2.
