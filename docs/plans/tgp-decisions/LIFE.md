# LIFE resolutions (Terminal-lifecycle interactions (LIFE))

### LIFE-1 [P0] Alt-screen enter/leave for inline and pinned viewports
- Decision: Every viewport carries a screen affinity. Inline viewports bind to the screen buffer (primary or alt) active at create time and render ONLY while that buffer is active: on DECSET 1049/1047/47 enter from primary, all primary-bound inline viewports are hidden (state retained, not rendered, no GPU teardown); on exit they are restored exactly. Pinned viewports default to the buffer active at create time but expose an explicit screen_affinity field (primary | alt | both, default = current buffer); a HUD opts into both to persist a pinned overlay across an alt-screen TUI. Affinity is per-token-owned viewport; an alt-screen switch never destroys scene nodes or assets (those are buffer-independent), only gates viewport visibility. Mirror exactly the existing image-grid stash/restore model (enter_alt_screen stashes image_grid, exit restores it) so inline TGP viewports follow the same primary/alt isolation images already get.
- Rationale: Matches the kitty image model already implemented in this codebase (term.rs enter_alt_screen/exit_alt_screen stash and restore image_grid; primary/alt maintain independent image lists). Principle 1 (app-authoritative): the app chose inline vs pinned and now chooses affinity; the terminal does not guess. Principle 2 (opt-in): persisting a pinned HUD over a TUI requires an explicit both flag. F1: affinity is a property of a token-owned viewport, so an alt switch only gates the owning app's viewports. Scene nodes/assets are buffer-independent (shared VRAM cap), so a switch is pure visibility gating, never teardown. F2: prior finding text mentioning 'RGP placements have no alt-screen model' is dropped — RGP stays legacy and untouched.
- Doc change: Add new subsection 10.6 'Screen-buffer affinity'. Add field `screen_affinity: ScreenAffinity` to the Viewport struct in 10.1 with `enum ScreenAffinity { Primary, Alt, Both }` and document default = buffer active at create time. New 10.6 prose: 'On alt-screen enter (DECSET 1049/1047/47) the terminal hides every viewport whose affinity excludes the now-active buffer and renders those whose affinity includes it; on exit the prior set is restored. Hiding retains all viewport and scene state (no GPU teardown); only render gating changes. Inline viewports are implicitly Primary-or-Alt = their create-time buffer. Pinned viewports may set Both to persist across a full-screen TUI. This generalizes the terminal's existing per-buffer image isolation.'
- Test: Parser::advance bytes-in tests (no GPU): (1) Create an inline viewport on primary (tgp;vp ... anchor=inline), assert viewport present and visible-on-primary via accessor; send ESC[?1049h, assert the inline viewport's effective-render flag is false and its CellRect/scene nodes still resident; send ESC[?1049l, assert render flag true again and rect unchanged. (2) Create a pinned viewport with screen_affinity=both on primary; send ESC[?1049h; assert it is still effective-rendered on the alt buffer. (3) Create a pinned viewport with default affinity; ESC[?1049h; assert hidden. (4) Assert that across an enter/exit cycle scene.nodes count and asset_revision are unchanged (no teardown). Add accessor `viewport_visible_on_active_buffer(vp_id) -> bool`.

### LIFE-2 [P0] RIS / DECSTR / CSI 3J effect on the retained scene
- Decision: RIS (ESC c) performs a COMPLETE TGP scene teardown across ALL tokens: destroy every viewport, node, asset, material, clip, pending chunk-reassembly buffer, in-progress binary frame, all subscriptions, the explore controllers, the animation clocks, and free all GPU buffers; reset both scene_revision and asset_revision tracking. This is the guaranteed VRAM-recovery path. RIS emits NO TGP error/event/ack to any app (the reset is a user/host recovery action, not an app-addressed event), but it does invalidate all session/namespace tokens so a surviving writer cannot address freed nodes. DECSTR (soft reset) leaves the TGP scene entirely UNTOUCHED (it is a pen/mode soft reset only). CSI 3J (clear scrollback) does NOT touch pinned viewports or scene assets; it follows the inline-anchor rule (see LIFE-3 / LIFE-9): inline viewports whose anchor lines are in the cleared scrollback are evicted like their cells.
- Rationale: Directly mirrors the existing ris() in term.rs which already does a full teardown of grids + image placements (the kitty hard requirement) and resets private modes, while soft reset does not. Principle 3 (safe-by-default): RIS must always reclaim up to max_vram_mb so a hostile process cannot pin GPU memory permanently — this is the only guaranteed recovery. The cross-token wipe is intentional: RIS is the user's terminal-wide 'reset everything' and is not per-app. Token invalidation prevents a confused-deputy write to freed ids (F1). F2: no RGP-adapter consideration — RGP scene teardown on RIS is its own untouched legacy path.
- Doc change: Edit 15 (Security & robustness) add subsection 15.6 'Reset semantics': 'RIS (ESC c) is the guaranteed VRAM/scene recovery path: it tears down the entire TGP scene (assets, materials, nodes, viewports, clips), cancels all subscriptions/explore/animation, frees all GPU buffers and all pending chunk-reassembly and in-progress binary-frame buffers, and invalidates all session tokens. RIS emits no TGP reply. DECSTR (soft reset) does not affect the TGP scene. CSI 3J clears scrollback only and follows the inline-anchor eviction rule (10.2/§LIFE-3); it never removes pinned viewports or assets.' Also add a row to the 15.2 cap-recovery discussion noting RIS as the bounded-resource escape hatch.
- Test: Bytes-in tests: (1) Build a scene (asset.add + node.upsert + vp create) via tgp;p frames; assert scene.nodes/assets/viewports non-empty and asset_revision>0; send ESC c (RIS); assert scene.nodes/assets/viewports all empty, subscriptions empty, pending_chunk_bytes()==0, in-progress binary frame state cleared, and a `gpu_buffers_freed` / effective-revision-reset accessor reflects teardown. (2) Build a scene; send ESC[!p (DECSTR); assert scene unchanged (node count, asset_revision identical). (3) After RIS, send a tgp;p node.upsert referencing an old token; assert it is rejected (token invalid) rather than mutating. (4) Inline viewport in scrollback + CSI 3J: assert pinned viewport survives, inline-in-scrollback viewport evicted.

### LIFE-3 [P1] Scrollback eviction of an inline anchor line
- Decision: When the last placeholder cell of an inline viewport falls off the bottom of the bounded primary scrollback ring (i.e. all anchor cells are evicted), the terminal DESTROYS that viewport: free its offscreen layer/GPU buffers and remove it from the viewport map. The backing scene nodes/assets are NOT freed (they are shared and may be referenced by other viewports). If the owning app subscribed to lifecycle events, emit one tgp;e;ev=destroyed;vp=<id> to the owning token only; otherwise destroy silently. Inline-viewport lifetime is documented as bounded by scrollback depth. Eviction is per-placeholder-cell: a viewport is destroyed only once NONE of its placeholder cells remain in the live grid or retained scrollback. F3 makes placeholder cells authoritative, so this is a direct consequence — the viewport dies with its cells.
- Rationale: F3 binding: placeholder cells are authoritative for position; therefore the viewport's existence tracks its cells, and when the cells are gone the viewport is gone. Principle 3 (bounded resources): without reclaim, a long-running app placing many inline viewports silently leaks VRAM as anchors fall off scrollback — the destroy path caps this. Mirrors the existing O(1) VecDeque pop_front eviction (prompt_marks) and image eviction-on-scrollback already in the codebase. The opt-in destroyed event (principle 2) lets a subscribed app re-place; routing only to the owning token satisfies F1. F2: no RGP placement model involved.
- Doc change: Edit 10.2 Inline bullet to add: 'Inline lifetime is bounded by scrollback depth. The placeholder cells are authoritative (F3): when every placeholder cell of an inline viewport has been evicted from the scrollback ring, the terminal destroys the viewport and frees its offscreen layer. Shared scene nodes/assets are not freed. An app subscribed to lifecycle events receives a single tgp;e;ev=destroyed;vp=<id> (owning token only); otherwise eviction is silent.' Add `destroyed` to the ev enum list in 12.5 and add a `lifecycle` event class to the sub granularity note.
- Test: Bytes-in tests, constructing Term::new(rows, cols, small_scrollback): (1) Place an inline viewport near the bottom; write enough newlines to push the anchor line beyond rows+scrollback; assert the viewport is removed from the viewport map and an offscreen-layer-freed accessor reflects reclaim, while the backing node still exists in scene.nodes. (2) Same but with a lifecycle subscription active for the owning token: assert one queued PTY reply matching tgp;e;ev=destroyed;vp=<id>. (3) Same without subscription: assert NO queued reply. (4) Partial eviction: push only some placeholder cells past the boundary; assert the viewport is NOT yet destroyed. Accessor: `viewport_ids() -> Vec<ViewportId>`.

### LIFE-4 [P1] DECSTBM scroll-region scrolling vs inline viewports
- Decision: Inline viewport placeholder cells are ORDINARY cells: a DECSTBM-bounded scroll moves them exactly as it moves text. The viewport's CellRect is recomputed from the new placeholder-cell positions (F3: cells are authoritative) and the cached layer is re-composited at the new pixel rect (no re-render unless content/camera/size changed). For a viewport whose placeholder cells straddle a scroll-region margin, only the cells inside the region scroll; the cells outside do not — this can split the placeholder run. The viewport's clip_to_scroll_region flag governs the visible portion: when true (default), the portion of the cached layer outside the active scroll region is clipped (not drawn); when false, the layer composites in full at its recomputed rect. Text never scrolls 'through' a viewport because the viewport tracks its own cells. Inline viewports are NOT disallowed inside a DECSTBM region and are never silently downgraded to pinned.
- Rationale: F3 binding: placeholder cells authoritative means region scrolls move them like text and the rect follows the cells — this is the only consistent rule. Principle 1 (terminal stays simple): treat placeholder cells as cells, reusing the existing scroll_up/scroll_down grid machinery rather than special-casing viewports. Re-composite-not-re-render reuses the §10.4 cached-layer model and the scene_revision/viewport-dirty split (principle 6). clip_to_scroll_region already exists in the Viewport struct; this gives it precise meaning for the straddle case. Region scrolling is the core pager/editor mechanic (the showcase apps), so correctness here is load-bearing. F2: no RGP relevance.
- Doc change: Edit 10.3 (reflow) add a paragraph: 'DECSTBM scroll-region scrolling moves an inline viewport's placeholder cells exactly like text (F3). The viewport CellRect is recomputed from the new cell positions and only the viewport dirty flag is set, so the cached layer is re-composited at the new rect without a re-render. When placeholder cells straddle a scroll-region margin, only cells inside the region scroll; clip_to_scroll_region (default true) clips the cached layer to the active region so nothing bleeds across the margin. Inline viewports are permitted inside DECSTBM regions and are never downgraded.'
- Test: Bytes-in tests: (1) Set DECSTBM (CSI t;b r) covering rows where an inline viewport sits; emit a scroll (newline at region bottom / CSI S); assert the viewport CellRect.row decreased by 1 and viewport-dirty is set while scene_revision is unchanged (re-composite not re-render). (2) Place a viewport straddling the bottom margin; scroll; assert only the in-region placeholder cells moved and a `viewport_clip_rect(vp)` accessor reflects clipping to the region. (3) Scroll text past an inline viewport entirely inside the region; assert no text cell overlaps the viewport's current placeholder cells (no corruption). Accessors: `viewport_cell_rect(vp)`, `viewport_dirty(vp) -> bool`, `scene_revision()`.

### LIFE-5 [P2] GPU device loss / context reset recovery
- Decision: The full scene (assets, nodes, world matrices, viewport rects, instance buffers) is mandated CPU-resident (already required for tests). On wgpu device loss the terminal: recreates the device/queue, then forces a complete re-upload of ALL assets/materials/instances and re-creates ALL per-viewport offscreen color+depth+(MSAA) and pick targets by treating the effective asset_revision and every viewport dirty flag as bumped — explicitly IGNORING revision equality for that one recovery pass. CPU-side scene state is NEVER lost. Device loss is NOT a session teardown and emits no TGP error to apps (it is invisible recovery; the app's scene survives). An in-flight explore drag MAY be cancelled by device loss (and only by device loss) with a tgp;e;ev=leave (or drag-cancel) to the owning subscriber; animation clocks resume from saved phase (see LIFE-10). This generalizes the scene_revision/asset_revision dirty split (principle 6) with a 'force-all-dirty' invalidation primitive.
- Rationale: Principle 6: the dirty split is the template; device loss needs a force-all-dirty path because equality gating (revision unchanged -> skip upload) otherwise prevents recovery forever. Principle 3 (no permanent broken state): rebuilding from CPU state is the robust recovery. Keeping CPU state authoritative is exactly the testability mandate (all geometry CPU-side). Cancelling a drag only on device loss (not on resize/theme) is the minimal interaction disruption, consistent with LIFE-10. F2: RGP has its own path; not bridged.
- Doc change: Add subsection 11.5 'Device loss recovery': 'All scene state is CPU-resident. On wgpu device loss the terminal recreates the device and forces a full re-upload of all GPU resources by treating asset_revision and every viewport dirty flag as bumped for one recovery pass (revision equality is ignored), re-creating offscreen and pick targets. CPU state is never lost; no TGP error is emitted. Only device loss may cancel an in-flight explore drag (emitting a drag-cancel/leave to the owning subscriber); animation resumes from saved phase (14, §LIFE-10).' Add to 6.5 a note: 'a force-all-dirty invalidation (device loss) bypasses revision-equality gating.'
- Test: Device loss is a GPU event, so the testable surface is the CPU invalidation primitive: (1) Build a scene; record asset_revision and per-viewport dirty flags; call an injectable `Term::on_device_lost()` hook; assert an `effective_force_reupload` flag/accessor is set and all viewport dirty flags are true while CPU scene.nodes/assets are byte-identical (unchanged counts and ids). (2) Assert no PTY reply is queued by device loss (no error frame). (3) With an active explore drag state (set via prior tgp;e drag bytes), call on_device_lost(); assert the drag state is cleared and a drag-cancel reply is queued to the owning token; assert animation phase value is preserved. Accessor: `force_reupload_pending() -> bool`.

### LIFE-6 [P0] Single global scene shared across multiple TGP-writing processes
- Decision: Resolved by F1 (per-app namespace token), which supersedes the finding's 'keep one shared scene for v1' recommendation. There is ONE shared scene + renderer and a shared resource cap (max_vram_mb etc.), but addressing and event routing are token-isolated: at handshake an app opts into a session/namespace token (tgp;q ... returns/accepts a token in tgp;r); all node/asset/viewport ids it creates are scoped to that token. node.upsert / node.remove / vp retarget / sub on an id owned by a DIFFERENT token is REJECTED with tgp;x;code=token_denied (never silently honored). Tokenless or untrusted writers (a log line, curl|cat) get no token and therefore cannot address or retarget any token-owned node/viewport — they can only create within an anonymous/ephemeral default scope that cannot collide with a real app's ids. Event reports, error replies, and acks route ONLY to the owning token's PTY. The shared VRAM cap is still global but enforced per-op so one token's overuse yields cap_exceeded to that token, not silent eviction of another's assets. Add this confused-deputy + DoS surface to the §15.1 threat model.
- Rationale: F1 is binding and directly addresses this finding: it isolates addressing and event routing while sharing the renderer and caps. This closes the confused-deputy hole (untrusted output overwriting 'cam'/'car' via upsert) and the wrong-process-gets-the-click hole the threat model omitted. Principle 3 (safe-by-default for untrusted bytes): tokenless writers are powerless to retarget. Principle 1: still one app-authoritative scene model. F2: the finding's RGP-shared-namespace concern is moot (RGP is a separate untouched code path with its own namespace) — note and drop the RGP wording.
- Doc change: Edit 8.4 Namespace bullet: replace 'one global namespace per session for the scene' with 'one shared scene with per-app namespace tokens (F1): an app negotiates a session/namespace token at handshake; node/asset/viewport ids are scoped to that token. Cross-token addressing (upsert/remove/retarget/sub on another token's id) is rejected with tgp;x;code=token_denied. Tokenless writers create only in an ephemeral default scope and cannot address token-owned objects.' Edit 7.1 to show the token in the q/r exchange. Add to 15.1 threat model: 'Multiple processes share one PTY and one scene; without token scoping, untrusted output could overwrite or retarget another app's nodes (confused deputy) or steal its event reports. Tokens isolate addressing and routing; the VRAM cap is shared but enforced per-op so one writer cannot silently evict another's assets.' Add code `token_denied` to the 15.3 error table.
- Test: Bytes-in tests: (1) Handshake token A (tgp;q -> capture token in tgp;r), upsert node 'car' under A; handshake token B; from B send node.upsert id='car' trs=...; assert scene's 'car' node unchanged AND a tgp;x;code=token_denied queued to B's reply channel only. (2) Tokenless writer (bytes with no token) sends node.upsert id='car'; assert 'car' (A's) unchanged and the tokenless op either rejected or lands in an ephemeral scope distinct from A. (3) sub from B on a viewport owned by A: assert rejected. (4) Event routing: a pick/click on A's viewport queues tgp;e to A's channel only (assert B's channel empty). Requires a multi-channel reply accessor keyed by token, e.g. `pty_replies_for(token) -> &[u8]`.

### LIFE-7 [P1] Event/error replies emitted while no foreground app is reading stdin
- Decision: Subscriptions, explore controllers, and terminal-side animation/auto-spin clocks are tied to the lifetime of the owning session token (F1). The terminal cancels all of a token's subscriptions + explore + animation when: (a) the foreground process / PTY input owner changes away from the token owner, or (b) the PTY input side closes (EOF) / the app exits, or (c) the token is invalidated (RIS, LIFE-2). While cancelled, NO tgp;e events are emitted for that token. Additionally, the terminal NEVER emits tgp;e input events (click/hover/enter/leave/drag/wheel/camera) while the terminal window is unfocused; resize/lifecycle reports may still queue. This prevents 'ESC _ tgp;e;... leaking into bash' — events only flow to a live, foreground, focused subscriber on the owning token. Auto-spin and the explore controller stop advancing once their subscriber is gone (no orphan camera motion driving events into a shell prompt).
- Rationale: Binding F1 (route only to owning app) + F4 (subscriptions capture within viewport) imply lifetime must track the owner; emitting to a non-owner or a dead reader is the classic mouse-escape-leak bug. Principle 3 (safe-by-default): unconsumed frames must not back up the reply buffer or corrupt another app's command line. Principle 2 (terminal only takes control when asked): when the asker is gone, the terminal relinquishes (stops explore/anim). Gating input events on focus matches the existing report_focus model in term.rs. F2: no RGP relevance.
- Doc change: Add subsection 12.7 'Subscription & controller lifetime': 'A token's subscriptions, explore controllers, and animation/auto-spin clocks are cancelled when the foreground PTY input owner changes away from the token owner, when the PTY input side closes (EOF/app exit), or on RIS. No tgp;e events are emitted for a cancelled token. Input events (click/hover/enter/leave/drag/wheel/camera) are never emitted while the terminal is unfocused; lifecycle/resize reports may still queue. Auto-spin and explore stop advancing once their subscriber is gone.'
- Test: Bytes-in / state tests with an injectable focus + foreground-owner signal: (1) Token A subscribes vp=2 ev=click; simulate a click (input injection) while focused+foreground; assert tgp;e;ev=click queued to A. (2) Set terminal unfocused via accessor; inject same click; assert NO event queued. (3) Signal foreground-owner change away from A (or PTY EOF); assert A's subscriptions/explore/anim are cleared (subscription_count(A)==0) and a subsequent click queues nothing. (4) Enable auto_spin via vp explore opts + camera subscription; advance the injectable clock; assert camera node mutates and tgp;e;ev=camera queues; then signal owner-gone; advance clock again; assert camera node no longer mutates and no event queues.

### LIFE-8 [P1] Copy/paste and text selection over a viewport's cells
- Decision: Copying a selection that covers an inline viewport's placeholder cells yields the node/scene alt-text (13) for that viewport's region (one alt string per viewport occurrence, in reading order among the surrounding text); if no alt text is set, the placeholder cells copy as nothing (zero characters, not the raw placeholder code points). For input disambiguation: an explore-enabled viewport consumes drag/wheel within its cell rect (F4), so to make a TEXT selection across an explore viewport the user holds a reserved modifier (SHIFT); SHIFT-drag forces terminal selection and is never consumed by explore. Without the modifier, a drag inside an explore viewport's rect drives the camera (F4: explore consumes drag); a press/release that did not move is a click event (F4), not a selection. This makes drag intent unambiguous and never silently eats an intended selection.
- Rationale: Binding F4: an active sub/explore captures pointer events within the viewport cell rect; the SHIFT escape hatch is the standard terminal convention (matches how apps let users select over mouse-reporting TUIs) and resolves the input-routing collision the finding flags. Alt-text-on-copy is principle 1 plus the §13 accessibility lead (alt already travels in the scene); copying nothing when alt is absent avoids leaking placeholder code points into the clipboard. The whole resolution is testable on the CPU selection model. F2: no RGP relevance.
- Doc change: Add subsection 13.1 'Selection & clipboard over viewports': 'A terminal selection covering an inline viewport's placeholder cells copies the viewport's alt-text (one alt string per viewport, in reading order); if no alt is set, those cells copy as empty (placeholder code points are never emitted to the clipboard). SHIFT-drag forces a terminal text selection across an explore-enabled viewport; an ordinary drag inside an explore viewport drives the camera (F4) and a no-move press/release is a click event, not a selection.' Cross-reference from 10.2 (inline) and 12.3 (explore).
- Test: CPU selection-model tests (no GPU): (1) Place an inline viewport with alt='caffeine, C8H10N4O2'; programmatically select a cell range covering its placeholder cells plus surrounding text; call the copy/extract-selection accessor; assert the returned string contains 'caffeine, C8H10N4O2' positioned where the viewport sits. (2) Same viewport with no alt; assert the extracted string contains the surrounding text but ZERO characters for the viewport cells (no placeholder code points). (3) Drag-routing: with an explore viewport, inject a plain drag inside its rect; assert it is routed to the explore controller (camera node mutated / drag state set) and selection is empty; inject a SHIFT-drag over the same rect; assert a terminal selection range is created and the camera did not move.

### LIFE-9 [P1] CSI 2J / ED / EL erase vs viewports and the cached layer
- Decision: ED/EL erase the underlying cells exactly like normal text. Erasing an inline viewport's placeholder cells erases those cells, and (F3: placeholder cells authoritative) once ALL of a viewport's placeholder cells are erased the viewport is destroyed and its offscreen layer freed (same destroy path and opt-in tgp;e;ev=destroyed as scrollback eviction, LIFE-3); a partial erase that leaves some placeholder cells leaves the viewport alive with a recomputed CellRect over the surviving cells. Pinned viewports are NOT cell-bound and therefore PERSIST across any ED/EL (2J/3J/2K) — a HUD composites over freshly-cleared cells, which is correct. CSI 2J/3J additionally clears images (matching existing kitty behavior already in erase_display) but does NOT free TGP scene nodes/assets and does NOT remove pinned viewports. Apps must clear deliberately: 2J does not nuke pinned overlays nor the scene graph; it only erases cells (and thus cell-bound inline viewports).
- Rationale: F3 binding makes the inline rule a direct corollary of LIFE-3 (cells authoritative -> erasing cells erases/destroys the inline viewport). Mirrors the existing erase_display in term.rs precisely: 2J/3J clear images and the visible grid; partial erases (0J/1J) do not touch graphics. Pinned-persists is the HUD-correct behavior and is consistent with pinned being not cell-bound (10.2). Principle 1 (deterministic, app-reasonable): apps already reason about 2J clearing cells; aligning viewports to that is least-surprise. F2: no RGP relevance.
- Doc change: Add to 10.4 (or a new 10.7 'Erase semantics'): 'ED (CSI J) and EL (CSI K) erase underlying cells like text. Erasing all of an inline viewport's placeholder cells destroys it (and frees its layer; opt-in destroyed event per §LIFE-3); a partial erase recomputes its CellRect over surviving cells. Pinned viewports are not cell-bound and persist across all ED/EL. CSI 2J/3J also clear images (existing behavior) but never free TGP scene nodes/assets and never remove pinned viewports.' Cross-reference 10.2 and LIFE-3.
- Test: Bytes-in tests: (1) Place an inline viewport; position cursor at home; send CSI 2J; assert the inline viewport is destroyed (removed from viewport map, layer freed) but its backing scene node persists, and pinned viewports (if any) persist. (2) Place an inline viewport spanning several cells on one row; send CSI K (EL 2) on a different row; assert the viewport survives unchanged. (3) Partial erase: 0J from a cursor mid-viewport so only some placeholder cells are erased; assert the viewport survives with a shrunk CellRect. (4) Pinned viewport + CSI 2J; assert pinned survives and is still effective-rendered. (5) Assert 2J still clears image_grid (regression) while leaving scene assets resident. Accessors: viewport_ids(), viewport_cell_rect(vp).

### LIFE-10 [P2] Resize / device loss / theme change while explore-dragging or animating
- Decision: Explore drag origin and animation phase are stored in resolution-independent terms: the drag origin and accumulated delta are kept in viewport-normalized coordinates (0..1 within the viewport rect) plus the live camera pose, and the animation/auto-spin clock is stored as a phase (a t value via the injectable deterministic clock), never as pixels or wall-clock pixels. On SIGWINCH reflow or font-size change, the terminal recomputes each viewport's pixel rect from its cell rect WITHOUT resetting drag deltas (re-derive current pixel cursor from the normalized origin) or animation phase. On a runtime theme/palette change, theme-tinted viewports (11.2) re-tint and re-composite WITHOUT resetting animation phase (bump viewport dirty / palette_revision only, not the clock). ONLY device loss (LIFE-5) may cancel an in-flight explore drag. Reflow and theme changes never cancel a drag and never reset a phase.
- Rationale: Resolution-independent state is the only way reflow mid-drag doesn't make camera deltas discontinuous (cell->pixel rect changes under the cursor). Keeping phase separate from pixels reuses the injectable deterministic clock the testability mandate requires and the established 'preserve phase across re-apply' precedent. Principle 6: theme re-tint is a viewport-dirty re-composite, not a re-render/reset. Restricting drag-cancel to device loss alone (consistent with LIFE-5) keeps interaction stable across the common events (resize/theme) and only disrupts on the unavoidable one. F2: precedent is generalized, not borrowed from RGP's code path.
- Doc change: Add subsection 12.8 'Stability across resize / theme / device loss': 'Explore drag state is stored in viewport-normalized coordinates plus camera pose; animation/auto-spin state is stored as a phase against the injectable clock. SIGWINCH/font reflow recomputes each viewport pixel rect from its cell rect without resetting drag deltas or animation phase. A theme/palette change re-tints and re-composites theme-tinted viewports (viewport dirty / palette_revision bump) without resetting phase. Only device loss may cancel an in-flight drag.' Cross-reference 10.3 (reflow), 11.2 (theme-tint), 14 (animation), and §LIFE-5.
- Test: Deterministic-clock tests: (1) Begin an explore drag (inject drag-start + a move) and record camera pose and normalized drag origin; send a resize (CSI 8;rows;cols t or resize API); assert the camera pose is unchanged immediately after resize (no jump) and the viewport pixel rect was recomputed from the new cell rect; inject a further drag move and assert the delta is continuous (computed from normalized origin, no discontinuity). (2) Start auto-spin; advance the injectable clock to phase P (assert camera reflects P); apply a theme/palette change (e.g. OSC palette set); assert palette_revision/viewport-dirty bumped, the camera still reflects phase P (unchanged), and the animation clock value is unchanged. (3) Mid-drag device loss: call on_device_lost(); assert the drag is cancelled (per LIFE-5) while phase is preserved.

### LIFE-11 [P0] PTY EOF / terminal close mid-binary-frame and mid-chunked-asset
- Decision: On PTY EOF / terminal close the parser ABORTS any in-progress binary-length frame (discard the partially-consumed bytes and the awaiting-N-bytes state) and DROPS all pending per-id chunk-reassembly buffers, freeing their memory immediately; no error is emitted (the app is gone). Independently, to harden against a stalled-but-not-EOF stream that could wedge the parser by promising N bytes and never delivering, a max-message duration/quiescence guard (driven by the injectable clock) aborts an in-progress binary read or stalled chunk reassembly after the guard elapses, emitting tgp;x;code=timeout;detail=binary_incomplete to the owning token (if it opted into errors) and freeing the buffers. A complete-but-shorter-than-len read that terminates early (transport framing breaks) emits tgp;x;code=truncated and discards the frame. The binary back-channel apc_end returns Option<BinaryFollow{len,enc}> (per grounding) so the parser knows exactly how many bytes to consume and can detect short reads.
- Rationale: Grounding: the APC pre-scanner terminates on ESC/BEL/0x9C and apc_end returns unit, so a binary len=N frame needs a back-channel — apc_end -> Option<BinaryFollow{len,enc}> is the minimal change, and it is what lets EOF/short-read detection work at all. Principle 3 (safe-by-default, bounded, structured errors not crashes/silent drops): EOF must reclaim up-to-64MiB per-id reassembly buffers (the §15.2 cap) and the timeout guards a hostile/stalled stream from pinning the parser. Matches the existing RGP handler's drop-pending-chunked-upload behavior. The structured timeout/truncated errors replace RGP's silent drop. F2: RGP's own chunk path is untouched.
