## WIRE

### WIRE-1 [P0] What consumes the ST terminator after raw binary bytes
- **Decision:** NORMATIVE: For an enc=bin frame, the header APC is closed by its own ST (ESC \\ or BEL or 0x9C); the parser then enters a binary-read state and consumes EXACTLY `len` raw bytes WITHOUT any escape/terminator scanning. After the Nth byte the parser returns directly to Ground. NO trailing terminator is required or expected after the raw bytes. If the byte immediately following the N raw bytes is an ST (ESC \\, BEL, or 0x9C), the parser MUST tolerate it as a no-op sync marker and consume it (one optional ST only); any other byte begins the next frame/text normally. The optional-ST tolerance is bounded to a single ST token so a flood of 0x9C cannot be absorbed.
- **Rationale:** Length-prefix is self-delimiting, so a mandatory trailer is redundant; tolerating one optional ST gives senders a harmless sync hedge and aids human-pasted frames without creating ambiguity. Conforms to principle 5 (compact wire: no forced 33% or trailer tax) and principle 3 (bounded tolerance, no unbounded ST absorption). Note: per F4/F2 the WIRE-4 magic trailer (below) is a SEPARATE opt-in integrity feature, not the base-frame terminator — the base frame has no required trailer.
- **Doc change:** Section 8.2(b): replace the example annotation with explicit framing prose. After the example add: 'The header APC is terminated by ST as normal. The parser then reads exactly `len` raw bytes with escape-scanning DISABLED, and returns to Ground after the Nth byte. No terminator follows the raw payload. A single ST token (ESC \\, BEL, or 0x9C) immediately after the raw bytes is tolerated and consumed as a no-op sync marker; a second consecutive ST is treated as ordinary input.'
- **Test:** (a) advance(term, b"ESC_ tgp;p;txn=1;enc=bin;len=3 ESC\\ \x00\x01\x02") then advance text 'X' -> assert one patch decoded AND grid shows 'X' at expected cell (proves Ground re-entry, no ST swallowed text). (b) Same frame with a trailing ESC \\ before 'X' -> assert identical patch + 'X' printed (optional ST consumed). (c) Same frame with TWO trailing ESC \\ then 'X' -> assert second ST routed to vte (no spurious print/state from first being mis-handled) and 'X' printed. (d) Raw payload containing 0x1B 0x5C bytes mid-data -> assert full N bytes captured verbatim (no early terminate).

### WIRE-2 [P0] Parser back-channel: apc_end must trigger binary-read mode
- **Decision:** NORMATIVE: Change the parser hook so apc_end returns a signal: `fn apc_end(&mut self) -> ApcEnd` where `enum ApcEnd { Done, BinaryFollows { len: u64, enc: BinEnc } }` (BinEnc = Bin only; b64 stays inside the APC and never sets BinaryFollows — see WIRE-7). The Perform impl (Term layer) parses the `tgp;...;enc=bin;len=N` text header during apc_chunk/apc_end and returns BinaryFollows{len,enc} from apc_end; the Parser, on receiving BinaryFollows, transitions from Ground into the binary-read state for exactly N bytes. The Parser itself does NOT parse tgp header semantics — it only acts on the returned enum. Non-tgp / non-bin APCs return Done and behave exactly as today.
- **Rationale:** Keeps the Parser a dumb pre-scanner and keeps all tgp;/CBOR/len knowledge in the Term layer, matching the existing layering and principle 1 (terminal simple, app-authoritative parsing localized). A typed return enum is the minimal cross-crate API change and is fully deterministic/testable. The Parser-peeks-the-header alternative is rejected because it pushes protocol knowledge into the generic escape parser. F2: no RGP demux constraint applies — TGP owns this path independently.

The tgp header is parsed in the terminal/Perform layer, which returns BinaryFollows for an enc=bin frame; the pre-scanner then consumes exactly `len` bytes outside escape-scanning. The pre-scanner has no knowledge of tgp semantics.' Add to the grounding callout that today apc_end returns unit and this is the required signature change.

### WIRE-3 [P0] len mismatch with actual CBOR payload size
- **Decision:** NORMATIVE: `len` is authoritative for FRAMING ONLY. The parser always consumes exactly `len` bytes (subject to the cap/ceiling rules of WIRE-8) and hands that buffer to the CBOR decoder. Decode outcomes: (1) buffer decodes to a complete CBOR item that consumes the WHOLE buffer -> apply patch. (2) CBOR self-terminates BEFORE the end of the buffer (trailing bytes) -> reject: emit `x;code=parse_error;detail=trailing_bytes` (txn from header per WIRE-10), scene unchanged, return to Ground. (3) CBOR is truncated / needs more than `len` bytes -> reject: emit `x;code=parse_error;detail=truncated`, return to Ground. In all three cases the parser has already consumed exactly N bytes, so the stream stays synced regardless of internal mismatch. Under-len never leaks into the text grid because framing consumes N, not 'until CBOR ends'.
- **Rationale:** Separating framing-truth (len) from content-validity (CBOR) is the only way to stay resynced against a hostile/buggy sender (principle 3): a lie about content cannot desync the stream because framing is byte-counted. Structured errors instead of silent drop or crash. The 'trust len only, ignore mismatch' option is rejected because trailing garbage in the buffer would silently corrupt the decoded op set.
- **Doc change:** Section 8.3: add subsection 'len vs payload (normative): `len` governs framing exclusively; the parser consumes exactly `len` bytes then CBOR-decodes the buffer. The decoded item MUST consume the entire buffer. Trailing bytes after a complete item, or a truncated/incomplete item, are rejected as `x;code=parse_error` (detail=trailing_bytes | truncated); the txn is unchanged and the stream resyncs at the next frame.'
- **Test:** (a) len=N where N exceeds the encoded CBOR by 2 trailing 0x00 -> assert queued reply contains tgp;x;code=parse_error;detail=trailing_bytes AND scene node count unchanged. (b) len=N two bytes short of a valid CBOR map -> assert x;detail=truncated, scene unchanged. (c) Immediately send a valid frame after each failure -> assert it applies (proves resync). (d) Exact-length valid CBOR -> assert patch applied, scene_revision bumped once.

### WIRE-4 [P1] tmux/screen passthrough stripping/splitting raw binary bytes
- **Decision:** NORMATIVE (per USER DECISION): The terminal advertises BOTH enc=bin and enc=b64 in the capability reply, listing b64 first as the recommended default; the app SELECTS the encoding and is responsible for choosing b64 when it cannot confirm a clean PTY (the terminal never auto-detects multiplexers — principle 4, app owns fallback). For enc=bin only, the terminal supports an OPT-IN integrity trailer negotiated via a capability flag `bintrailer` and requested per-frame with header field `trl=1`: when `trl=1`, after the `len` raw bytes the terminal reads a fixed 8-byte trailer = 4-byte magic `0x54 0x47 0x50 0x42` ('TGPB') + 4-byte little-endian echo of `len`. Mismatch or absent trailer -> `x;code=parse_error;detail=trailer_corrupt`, scene unchanged, return to Ground. Without `trl=1` no trailer is read (WIRE-1 base framing). The trailer bytes are NOT counted in `len`.
- **Rationale:** Safe-by-default for untrusted/lossy transports (principle 3) while keeping conveniences opt-in (principle 2) and app-authoritative fallback (principle 4): the app, not the terminal, decides bin-vs-b64 and whether to pay for the trailer. A fixed magic+length-echo detects the two realistic passthrough corruptions (ST-strip shifting bytes, mid-frame truncation) and surfaces them as structured errors instead of silent desync. F2: no RGP transport behavior constrains this.
- **Doc change:** Section 7.1: add `bintrailer` to the feat list and note 'enc list is ordered by terminal recommendation (b64 first when a clean transport is unconfirmed).' Section 8.2(b): add 'Integrity trailer (opt-in): when the app negotiated `bintrailer` and sends `trl=1`, an 8-byte trailer (magic "TGPB" + u32-LE len echo) follows the raw payload and is verified; mismatch -> x;parse_error;detail=trailer_corrupt. The trailer is excluded from `len`. The app SHOULD prefer enc=b64 behind multiplexers; the terminal does not detect multiplexers.' Update §16 tmux row to reference this opt-in trailer.
- **Test:** (a) trl=1 frame with correct trailer -> patch applied. (b) trl=1 frame with corrupted magic byte -> x;detail=trailer_corrupt, scene unchanged, and a following valid frame applies (resync). (c) trl=1 frame whose len-echo disagrees with header len -> x;detail=trailer_corrupt. (d) capability reply assertion: drain_pty_replies after tgp;q contains enc=b64,bin (b64 first) and feat includes bintrailer. (e) trl=1 not negotiated but sent -> treated per policy (reject as parse_error unknown-trailer) — assert structured error.

### WIRE-5 [P1] Chunk reassembly keying across concurrent uploads / interleaving
- **Decision:** NORMATIVE: Chunk reassembly is keyed by `asset id` (the numeric u32 handle of the asset.add being uploaded), SCOPED to the owning app's namespace token (F1) — keys are (token, asset_id) so two tokens cannot collide or corrupt each other's buffers. Within one token: (1) independent asset ids MAY interleave their chunk streams freely. (2) A single asset id MUST NOT interleave: a second open `more=1` stream for an id that already has an in-progress buffer, OR a format/fmt mismatch against the opener, ABORTS the prior buffer for that id and emits `x;code=parse_error;detail=chunk_interleave` (or `chunk_fmt_mismatch`); the new stream then starts fresh. Caps from WIRE-8 apply to the accumulating buffer. A tokenless/untrusted writer cannot address or abort another token's in-progress upload (F1).
- **Rationale:** Per-id keying is the minimal granularity that supports concurrent independent uploads while forbidding the corruption vector of two streams writing one id. F1 token-scoping is mandatory so cross-app addressing/abort is impossible. F2: the RGP-matching rationale in the finding is dropped — TGP defines this independently; we keep abort-on-mismatch because it is the safe behavior (principle 3), not because RGP does it. Structured error replaces RGP's silent drop.
- **Doc change:** Section 8.7: replace with 'Reassembly is keyed by (namespace token, asset id). Independent asset ids may interleave; a single id may not — a second open stream for an in-progress id, or an fmt mismatch with the opener, aborts the prior buffer and emits x;code=parse_error (detail=chunk_interleave | chunk_fmt_mismatch). Keys are token-scoped: an app cannot abort or address another app token's pending upload (§F1 namespace).'
- **Test:** (a) Interleave chunks of asset id=1 and id=2 (more=1 each, then more=0 each) under one token -> assert both assets present, asset_revision bumped. (b) Open id=1 more=1, then open id=1 more=1 again before close -> assert prior aborted, x;detail=chunk_interleave queued, only the new stream's bytes retained. (c) id=1 chunk fmt=glb then fmt=obj mid-stream -> x;detail=chunk_fmt_mismatch. (d) Two tokens both using asset id=1 -> assert separate buffers, no cross-corruption (each completes independently).

### WIRE-6 [P1] Chunked asset.add vs patch atomicity
- **Decision:** NORMATIVE: Chunk frames are PURE pre-parse buffering and carry NO transaction semantics: a `more=1` chunk frame bumps nothing, applies nothing, and has no txn effect. Only the FINAL frame (more=0) completes reassembly; the fully assembled buffer is then CBOR-decoded as one patch and applied ATOMICALLY (all ops or none), bumping asset_revision once (and scene_revision once if the patch also mutates nodes/transforms) on success. A failure on any chunk (cap overflow, interleave, fmt mismatch, or final-frame decode error) discards the whole buffer and leaves the scene unchanged — no partial asset is ever installed. txn correlation lives on the FINAL frame's header (intermediate chunk frames need no txn); the x/ack reply cites that txn. Chunk frames are NOT required to be alone in a patch, but a chunked asset.add's op set is only evaluated once, at completion.
- **Rationale:** Preserves the §8.6 atomic-patch guarantee for the most expensive op without inventing multi-frame txn correlation: buffering is invisible to the scene until complete (principle 3, no partial state from untrusted input). Generalizes the dirty-split (principle 6): a completed asset upload bumps asset_revision exactly once. F2: independent of RGP chunk semantics.
- **Doc change:** Section 8.7: append 'Atomicity (normative): chunk frames are pure buffering and carry no txn/scene semantics — they bump nothing. The assembled buffer is decoded and applied as a single atomic patch only on the final (more=0) frame, bumping asset_revision once (and scene_revision once if nodes change). Any failure discards the whole buffer; no partial asset is installed. The completing frame carries the txn echoed in ack/x.' Cross-reference §8.6.
- **Test:** (a) Send asset.add in 3 chunks (more=1,1,0); after chunk 1 and 2 assert asset_revision UNCHANGED and asset absent; after chunk 3 assert asset present and asset_revision bumped exactly once. (b) Final-chunk CBOR invalid -> assert no asset installed, asset_revision unchanged, x;parse_error with the final frame's txn. (c) Multi-op final patch (asset.add + node.upsert) completing via chunks -> assert BOTH applied atomically and scene_revision bumped once.

### WIRE-7 [P0] Two len semantics under enc=bin vs enc=b64 conflated
- **Decision:** NORMATIVE: Header field ordering and defaults are fixed. `enc=` MUST appear before `len=` in the header; a `len=` seen before any `enc=` in the same header is a `x;code=parse_error;detail=field_order` and the frame is rejected (control-frame style, no binary state entered). Default when `enc=` is absent = `b64`. ONLY `enc=bin` engages the raw-byte-count binary-read state (apc_end returns BinaryFollows). For `enc=b64`, `len` denotes the base64 CHARACTER count INSIDE the APC; the payload is scanned/terminated by ST as a normal APC (no binary-read state), then base64-decoded. So the parser always knows its read mode from `enc=` before it acts on `len`. `len` is OPTIONAL for enc=b64 (ST delimits); when present it is validated against the actual b64 char count (mismatch -> parse_error).
- **Rationale:** Mandating enc-before-len removes the only path to entering the wrong read mode (principle 3, hardened parsing). Defaulting to b64 keeps the safe, transport-robust path as the no-enc fallback. One field name, two clearly-mode-gated meanings, decided deterministically by enc. F2: independent of RGP.
- **Doc change:** Section 8.2(b): add 'Header field order (normative): `enc=` precedes `len=`; `len` before any `enc` -> x;parse_error;detail=field_order. enc absent defaults to b64. enc=bin: `len` = raw byte count read outside escape-scanning. enc=b64: `len` = base64 char count inside the ST-terminated APC (optional; validated if present); the payload is base64-decoded after the APC closes.'
- **Test:** (a) Header 'tgp;p;len=10;enc=bin' (len before enc) -> assert x;detail=field_order, no binary state entered, no scene change. (b) Header with enc absent + b64 payload in-APC -> assert decoded as b64 patch. (c) enc=bin;len=N -> assert binary-read state entered (BinaryFollows). (d) enc=b64;len mismatching actual char count -> assert x;parse_error. (e) enc=b64 no len, ST-terminated -> assert decoded.

### WIRE-8 [P0] max_msg_mb cap vs chunk reassembly cap and overflow drain
- **Decision:** NORMATIVE: Define two caps, both advertised in §7.1: `max_msg_mb` = max DECODED size of a single message/frame; `max_reasm_mb` = max accumulated size of a single chunk-reassembly buffer (>= max_msg_mb). Overflow handling for enc=bin: if header `len` > the applicable cap, the terminal MUST STILL consume-and-DISCARD exactly `len` bytes (without buffering them, to bound memory) to keep the stream synced, then emit `x;code=cap_exceeded;detail=max_msg|max_reasm`. A second ABSOLUTE hard ceiling `BIN_HARD_CEIL` (a compile-time constant, e.g. 1 GiB, >= max_reasm_mb) caps even the discard loop: if `len` > BIN_HARD_CEIL the terminal declares unrecoverable desync, emits `x;code=cap_exceeded;detail=unrecoverable`, and stops consuming the binary stream (returns to Ground at the header boundary) rather than draining a potentially-fabricated multi-GB count. Chunk total is bounded by max_reasm_mb; per-frame by max_msg_mb. Never leave announced-but-undrained bytes when len <= BIN_HARD_CEIL.
- **Rationale:** An over-cap len that is also a lie is a denial-of-sync vector; draining exactly N (when bounded by the hard ceiling) is the only way to stay synced, but the ceiling prevents an attacker from forcing a multi-GB drain loop (principle 3, bounded resources). Structured cap_exceeded instead of silent drop. Two named caps make the b64-vs-bin and per-frame-vs-stream relationships explicit.
- **Doc change:** Section 7.1: advertise max_msg_mb and max_reasm_mb (and document BIN_HARD_CEIL as an internal absolute). Section 15.2: add 'Overflow (normative): len>cap -> consume-and-discard exactly len bytes (no buffering) then x;cap_exceeded; len>BIN_HARD_CEIL -> declare unrecoverable desync, x;cap_exceeded;detail=unrecoverable, return to Ground without draining. Chunk buffer bounded by max_reasm_mb, per-frame by max_msg_mb.'
- **Test:** (a) enc=bin;len just over max_msg_mb -> assert x;cap_exceeded;detail=max_msg, then send a small valid frame and assert it applies (proves the oversize was drained and stream resynced). (b) len > BIN_HARD_CEIL -> assert x;detail=unrecoverable and that parser is back in Ground (next ESC parsed as escape) WITHOUT having attempted to buffer/drain. (c) chunk stream whose accumulated bytes cross max_reasm_mb -> assert x;cap_exceeded;detail=max_reasm and buffer discarded. (d) assert caps appear in capability reply.

### WIRE-9 [P0] Partial binary frame spanning multiple PTY reads
- **Decision:** NORMATIVE: The binary-read state lives in the Parser and PERSISTS across advance() calls. It holds `remaining: u64` and a capped accumulation `Vec<u8>` (capped at the WIRE-8 cap, with the discard-mode variant for over-cap frames that accumulates nothing and only counts down). Each advance() appends min(remaining, bytes.len()) bytes (or counts them down in discard mode), decrements remaining, and consumes them from the input slice; when remaining reaches 0 the frame is complete -> hand buffer to decoder (WIRE-3) and return to Ground; if the input slice empties first, the state is retained for the next advance(). On terminal EOF/stream close with remaining>0, the partial buffer is DISCARDED; if error reporting is negotiated, emit `x;code=parse_error;detail=truncated` (txn from the header captured at frame start). The accumulation buffer must never exceed the cap regardless of how reads are split.
- **Rationale:** advance() is non-blocking and per-read, so a byte-counted frame WILL straddle reads; an explicit persisted remaining-count + capped buffer is the only correct, deterministic state machine (principle 3, bounded accumulation under cap across reads). Buffering in the Parser (not Term) keeps the byte-count authority co-located with the read state from WIRE-2.
- **Doc change:** Section 8.2(b): add 'Cross-read lifecycle (normative): the binary-read state persists across advance() calls with a remaining counter and a cap-bounded accumulation buffer; bytes append until remaining==0, then the buffer is decoded and the parser returns to Ground. On EOF with remaining>0 the partial is discarded and (if error reporting negotiated) x;parse_error;detail=truncated is emitted with the header txn.'
- **Test:** (a) Split a len=20 frame across three advance() calls (8, 8, 4 bytes) -> assert no decode until the 20th byte, then exactly one patch decoded; assert intermediate &self accessor shows remaining decreasing (20->12->4->0). (b) Header in one advance, raw bytes split across two more -> assert correct reassembly. (c) Feed header + 10 of 20 bytes, then signal EOF -> assert partial discarded, scene unchanged, x;truncated with the header txn. (d) Split an over-cap frame across reads in discard mode -> assert buffer never allocates beyond cap and x;cap_exceeded emitted once.

### WIRE-10 [P0] CBOR decode-error surfacing through the reply channel
- **Decision:** NORMATIVE: Identity/correlation fields (`txn`, and `enc`/`len`) live in the TEXT header and are parsed BEFORE the CBOR body, so they are always known even when the body fails to decode. The decode site returns a Result; the Term layer routes a decode error to queue_reply -> pty_replies, emitting `x;code=parse_error` with the header `txn` (and op index when the failure is op-localized, omitted when the failure is whole-frame). Emission is GATED on the app having negotiated error reporting (capability flag, e.g. `feat=event`/a dedicated `errors` flag); if NOT negotiated, the error is silently dropped (dumb-reader behavior preserved). Replies route only to the owning namespace token (F1). The Result MUST NOT be discarded at the decode site.
- **Rationale:** Putting txn in the text header is what makes the structured-error promise real rather than vapor: a body that fails CBOR decode still has a correlatable txn. Gating on negotiation preserves dumb-reader safety (principle 3) while delivering structured errors to apps that asked (principle 4). F1 token routing prevents cross-app error leakage. F2: independent of RGP's discarded-Result behavior — TGP wires the Result through deliberately.
- **Doc change:** Section 8.2/8.6: state 'txn, enc, len are header (text) fields parsed before the CBOR body.' Section 15.3: add 'Surfacing (normative): the decoder returns a Result routed to the reply channel; on error, emit x;code=parse_error with the header txn (op index when localized), only if the app negotiated error reporting, else drop silently. Errors route only to the owning namespace token.'
- **Test:** (a) With error reporting negotiated: send enc=bin frame with txn=99 and a malformed CBOR body -> assert drain_pty_replies contains tgp;x;txn=99;code=parse_error. (b) Same frame WITHOUT error reporting negotiated -> assert drain_pty_replies is empty (silent drop) and scene unchanged. (c) Decode error where the failing op index is known -> assert x includes op=K. (d) Two tokens; malformed frame from token A -> assert error queued only for token A's reply routing, not token B.

### WIRE-11 [P1] base64 fallback cap and parse-path reconciliation
- **Decision:** NORMATIVE: `max_msg_mb` is defined as the cap on the DECODED payload for BOTH encodings. For enc=b64 the encoded (in-APC) length is bounded at ceil(max_msg_mb * 4 / 3) rounded up to the next multiple of 4 (plus padding); exceeding the encoded bound -> consume-to-ST then `x;code=cap_exceeded;detail=max_msg`. The b64 path flows through the existing APC chunk/ST-scan machinery (so the APC accumulation is independently bounded by the encoded-length cap, NOT only the legacy 256 MiB APC cap — the smaller of the two applies). After the APC closes, base64-decode: a base64 decode error -> `x;code=parse_error;detail=base64`. The decoded bytes then go through the SAME CBOR decode + error path as enc=bin (WIRE-3/WIRE-10), so both encodings share one decoded-size cap and one CBOR error contract. An app that pre-trimmed to max_msg_mb for bin is therefore valid for b64 too (same decoded budget).
- **Rationale:** One logical message must not have two effective size limits or two error stories; anchoring the cap to decoded size and routing both encodings through the same post-decode CBOR path unifies them (principle 5 compact wire with a robust fallback, principle 3 hardened parsing). base64 decode failure becomes a first-class structured error rather than an uncovered mode.
- **Doc change:** Section 7.1/15.2: 'max_msg_mb is the DECODED-payload cap for both enc=bin and enc=b64; for b64 the encoded length is bounded at ceil(cap*4/3) and the in-APC accumulation is bounded by min(that, APC cap).' Section 8.3: 'b64 frames are base64-decoded after the APC closes (decode error -> x;parse_error;detail=base64) then fed to the same CBOR decode/error path as bin, sharing one cap and one error contract.'
- **Test:** (a) enc=b64 frame whose base64 is valid and decodes to a valid patch within max_msg_mb -> assert patch applied. (b) enc=b64 with malformed base64 (bad char/length) -> assert x;parse_error;detail=base64, scene unchanged. (c) enc=b64 whose encoded length exceeds ceil(cap*4/3) -> assert x;cap_exceeded;detail=max_msg and stream resyncs (next frame applies). (d) Same logical CBOR payload sent once as enc=bin and once as enc=b64 (both within cap) -> assert identical resulting scene state (parity across encodings).

## SCEN — Scene model, nodes, transforms, dirty, instancing, ids, patch semantics

### SCEN-1 [P0] Clearing optional node fields under sparse-merge: CBOR null = clear, key-absent = preserve
- **Decision:** node.upsert is a sparse merge with a three-way distinction per optional field, decided by the CBOR map: (a) key absent => field preserved unchanged; (b) key present with CBOR null (major type 7, value 22) => field cleared to its type default; (c) key present with a value => field set to that value. Defaults on clear: parent -> None (node becomes a root, added to roots set; its existing children and animation phase are retained); alt -> None; tint -> opaque white [255,255,255,255] (the identity multiply in the SCEN-11 chain); trs sub-fields are NOT individually nullable (trs is replaced wholesale when present, see note). Required structural fields (id) may never be null. A null on a non-nullable field (id, or the kind-selector key when present) is a parse_error (op rejected, txn atomic-rejected per 8.6) with code=null_not_allowed, detail naming the field. Clearing parent re-roots the node in the same txn's final-state validation (interacts with SCEN-3 cycle check and SCEN-4 ref resolution).
- **Rationale:** CBOR natively distinguishes absent-key from explicit-null at zero wire cost, so we get a clear/preserve/set trichotomy without a side-channel clear:[...] list or a forced-required parent. Re-rooting via parent:null is the only non-destructive detach (remove+re-add would lose children and animation phase, per the finding's own concern). Matches the recommendation; conforms to principle 5 (compact wire) and principle 3 (explicit, hardened: a stray null on a structural field is a structured error, not a silent reinterpretation).
- **Doc change:** §8.6 'Idempotent addressing' bullet: replace 'Omitted fields are preserved.' with: 'node.upsert is a sparse merge over the CBOR op map. For each optional field: key absent = preserve; key present and CBOR null = clear to default (parent->root, alt->none, tint->opaque white); key present with a value = set. parent:null re-roots the node, retaining its children and animation phase. A CBOR null on a non-nullable field (id, kind selector) is rejected: x code=null_not_allowed. trs, when present, is replaced wholesale.' Add a one-line table of per-field clear defaults under §6.1 Node.

### SCEN-2 [P0] Kind transitions on an existing node id are forbidden; kind selectors are mutually exclusive per op
- **Decision:** A node's kind (Group | Mesh | Instanced | Light | Camera) is immutable for the lifetime of its id. An upsert that carries a kind-selector field (mesh / instances / camera / light, or implicitly Group when none is given on first creation) whose implied kind differs from the existing node's kind is rejected: x code=kind_conflict, citing the op index and detail=<existing_kind>-><attempted_kind>. Within a single op the kind-selector fields are mutually exclusive: at most one of {mesh, instances, camera, light} may appear; two or more => x code=kind_conflict;detail=multiple_selectors. On FIRST creation of an id: zero selectors => Group; exactly one selector => that kind. Note: F2 means we do NOT preserve any RGP replace-place kind-morph quirk.

### SCEN-3 [P0] Cycle and self-parent detection at txn commit; hard parent-chain depth cap as defense-in-depth
- **Decision:** At txn commit, after applying all ops to a staged copy and resolving refs (SCEN-4), the terminal validates the parent graph: every node's parent chain must terminate at a root within MAX_PARENT_DEPTH steps (cap = 256, advertised in caps as max_node_depth). A self-parent (A.parent=A) or any cycle (A->B->...->A) => reject the WHOLE txn atomically with x code=cycle, detail=<id-in-cycle>, citing the offending op index (the op that introduced or last touched a node on the cycle). A chain that would exceed MAX_PARENT_DEPTH (even acyclic) => x code=depth_exceeded;detail=<id>. The lazy render-time world-matrix walk additionally carries the same depth cap as a belt-and-suspenders guard, but commit-time validation guarantees it is never hit by committed state. Detection is an iterative visited-set walk (no recursion) so the validator itself cannot stack-overflow.
- **Rationale:** A cycle is a guaranteed render-time hang/stack-overflow reachable from untrusted PTY bytes (principle 3). Commit-time atomic rejection keeps the committed scene always-acyclic so the hot lazy walk needs no per-frame cycle bookkeeping; the depth cap bounds even pathological-but-acyclic chains and is advertised so apps can pre-trim. Matches the recommendation. Not mooted by F2.
- **Doc change:** New §6.2 bullet: 'The committed scene is always acyclic. At txn commit the terminal walks every node's parent chain (iterative, visited-set); a cycle or self-parent => x code=cycle; a chain exceeding max_node_depth (256, advertised) => x code=depth_exceeded. The whole txn is rejected, scene unchanged. The render-time walk also caps depth as defense-in-depth.' Add max_node_depth to the §7.1 caps list and §15.2 resource caps.

(3) Pre-existing chain root->...; then upsert{id:leaf,parent:self-or-ancestor} forming a cycle -> x code=cycle and scene unchanged (leaf's parent still old value). (4) Build a 257-deep chain in one txn -> x code=depth_exceeded. Assert via &self parent/roots accessors + drain_pty_replies; no GPU.

### SCEN-4 [P0] All refs (parent/asset/material) resolve against the txn's final committed state; order-independent; dangling => atomic reject
- **Decision:** A txn is validated as a whole against its FINAL post-apply staged state, making intra-txn references order-independent: a child op may precede its parent op, and a node.upsert{mesh:7} may precede the asset.add{id:7} in the same txn. Resolution rules: (a) parent must name a node that exists in the staged final state (created in this txn or pre-existing AND not removed by a later op in this txn); unresolved => x code=bad_ref;detail=parent:<id>. (b) mesh/asset/material/tex refs must name an asset/material that is COMMITTED in the staged final state — i.e. present pre-txn or fully added (more=0, per SCEN-9) within this txn; an in-flight (more=1) reassembly buffer does NOT satisfy a ref. Unresolved => x code=bad_ref;detail=mesh:<id> (or material:/tex:). (c) A node removed and re-upserted in the same txn resolves to its final state. Any unresolved ref rejects the whole txn atomically (scene unchanged), citing the first offending op index. Within-txn duplicate ids: last-writer-wins for node.upsert merges (each upsert merges onto the running staged node, in op order); asset.add duplicate-of-committed => error (SCEN-9).
- **Rationale:** F2 USER DECISION removes the RGP-adapter ordering concern entirely (this finding's 'RGP adapter' interaction is MOOT). Final-state resolution matches the atomic-frame promise (8.6: 'all ops apply together or not at all') and frees apps from topologically sorting ops — a major usability contract. Forward refs within a txn are exactly the §18.1/§18.3 examples (node.instances{parent:'mol'} before/with the group, segments referencing assets). Matches the recommendation; conforms to principle 3 (structured bad_ref, never a dangling pointer in committed state).
- **Doc change:** §8.6 add bullet 'Reference resolution': 'All references (parent, mesh/asset, material, texture) resolve against the txn's final staged state, so ops are order-independent within a txn (a child may precede its parent). Asset/material refs require a fully-committed (more=0) target; in-flight chunks do not satisfy a ref (§8.7, SCEN-9). Any unresolved reference rejects the whole txn: x code=bad_ref, detail=<kind>:<id>, citing the first offending op index.' ### SCEN-5 [P0] node.remove cascade-deletes the subtree by default; opt-in reparent:root flag
- **Decision:** node.remove{id} deletes the node AND its entire descendant subtree (recursive) by default. The removed nodes are erased from nodes, roots, the dirty set, any viewport that names a removed node as camera or root (see below), and any pending pick/event subscription targeting them. An optional field reparent:'root' (string enum; only 'root' supported in v1) changes the behavior to: detach the node's direct children to the scene root (their world transform is NOT preserved/baked in v1 — they keep their local TRS, now relative to world; documented), then delete only the named node. Removing a node that is a viewport's camera or root: the viewport is NOT auto-deleted; instead the dangling viewport ref is an error at commit (x code=bad_ref;detail=viewport:<vp>;camera|root) UNLESS the same txn also updates/removes that viewport — i.e. viewport refs obey the SCEN-4 final-state rule. Removing a non-existent id is a no-op (no error, no revision bump), matching RGP's delete-one-missing-no-bump behavior. A remove bumps scene_revision once (part of the atomic txn) and marks the removed subtree's former parent dirty.
- **Rationale:** Cascade matches the 'remove the car removes its wheels' intuition in the finding and bounds memory (orphan-leak of 10k nodes is the failure mode of reparent-to-root-by-default). The opt-in reparent flag preserves a subtree when wanted (principle 2: convenience is opt-in). Refusing to silently orphan a viewport's camera/root keeps viewports consistent and reuses the SCEN-4 bad_ref machinery. Matches the recommendation. Not mooted by F2 (scene.clear adapter mapping in the finding is MOOT under F2; RGP stays independent).
- **Doc change:** New §8.6 bullet 'node.remove cascade': 'node.remove deletes the node and its whole descendant subtree by default. reparent:"root" instead detaches direct children to the scene root (local TRS retained, world transform not baked in v1) and removes only the named node. ### SCEN-6 [P0] Single canonical packed instance layout: mat4 f32 LE + RGBA8 tint, explicit count, hard bounds check

NaN/inf in any matrix element => x code=parse_error;detail=instance_nan (reject, do not clamp). Per-instance material handles are NOT in v1 (deferred, §16) — instances share the node's single material. instance_index for picking (§12.4) is the record index 0..count.
- **Rationale:** This is the hot binary path; an unpinned stride/count is a direct OOB-read risk (principle 3) and makes an interoperable codec impossible (principle 5). Fixing mat4 f32 LE column-major matches the renderer's @location instance vertex attributes with zero CPU re-pack and avoids per-record Trs->mat4 math on the hot path. Explicit count + hard count==len/stride check is the bounds gate. Matches the recommendation, with tints made optional for the common single-color case. Not mooted by F2.

### SCEN-7 [P1] node.instances always bumps scene_revision + a dedicated per-node instance-dirty flag; never asset_revision
- **Decision:** Resolves the 6.4/6.5 contradiction in favor of 6.5's intent: any node.instances op (new buffer, same-size content re-upload, or count change) bumps scene_revision once (within the atomic txn) and sets a dedicated per-node instance_dirty flag on that node. If a count change exceeds the node's current GPU instance-buffer capacity, the renderer grows that node's instance buffer as part of consuming instance_dirty — this is still NOT an asset_revision bump (it is per-node GPU-side reallocation, not a shared asset/mesh re-upload). instance_dirty is cleared by the renderer after upload; it is a per-node flag in DirtySet (generalizing the SCEN-10 dirty-flag approach), orthogonal to the node's transform/visibility dirty flag.

Directly generalizes the scene_revision/asset_revision split (principle 6). Matches the recommendation. Not mooted by F2.

### SCEN-8 [P0] Node ids: hard 64-byte cap, printable non-control non-ESC charset; per-app-token namespacing replaces the one-global-namespace collision concern
- **Decision:** Node ids are UTF-8 strings, hard-capped at 64 bytes (the §8.4 'e.g.' is removed; 64 is normative, advertised as max_id_bytes). Charset: the byte sequence MUST be valid UTF-8 AND contain no C0 control bytes (0x00-0x1F), no DEL (0x7F), no C1 range (0x80-0x9F), and no ESC (0x1B) — i.e. nothing that could re-enter the app's stdin as a control sequence when echoed in a §12.5 event report. Violation => x code=bad_id;detail=charset|too_long, op rejected, txn atomic-rejected. Per F1, ids are NOT one global namespace: each id is scoped to the owning app's session/namespace token negotiated at handshake; two apps may both use 'cam' without collision, and a tokenless/untrusted writer cannot address or retarget another token's nodes (cross-token addressing => x code=denied;detail=token). The RGP-adapter-synthesized-id collision concern is MOOT under F2 (RGP is independent legacy with its own code path and its own namespace; TGP does not share a namespace with it). Event reports (§12.5) emit ids verbatim only because the charset guarantees they are control-safe; no escaping needed, but a defense-in-depth assertion rejects any id containing a forbidden byte before it can be queued.
- **Rationale:** Uncontrolled id strings enable memory amplification and — since §12.5 echoes the id back into the app's stdin inside an APC — control/ESC injection (principle 3). A hard cap + control-safe charset closes the injection hole at ingress so the egress path is safe by construction. F1 makes ids token-scoped, which structurally eliminates the app/adapter and app/app collision problem the finding raised (no shared namespace). F2 makes the adapter-prefix half of the recommendation unnecessary — note and drop it.
- **Doc change:** §8.4 'Node ids' bullet: replace 'bounded length, e.g. <=64 bytes' with 'UTF-8, hard cap 64 bytes (max_id_bytes, advertised); forbidden bytes: C0 (0x00-0x1F), DEL (0x7F), C1 (0x80-0x9F), ESC (0x1B). Violation => x code=bad_id.' Replace the §8.4 'Namespace: one global namespace per session' bullet with the F1 per-app-token scoping rule (ids scoped to the handshake token; cross-token addressing => x code=denied). Strike the §4 adapter-id-synthesis text (RGP independent, see clean-break). Add max_id_bytes to §7.1/§15.2 caps.

### SCEN-9 [P1] Chunked asset.add reassembles into an in-flight buffer; immutability and ref-resolution check only committed (more=0) assets
- **Decision:** A chunked asset.add (§8.7, more=1...more=0) reassembles into a per-id in-flight reassembly buffer that is NOT a registered asset. Rules: (a) The duplicate-id immutability check ('add on an existing asset id is an error', §8.4) fires ONLY against fully-committed assets, and ONLY when the final more=0 chunk would commit. The first chunk (more=1) of id 7 does not error even though later chunks reuse id 7. (b) A second chunk for an id with no open in-flight buffer and no committed asset starts a new buffer; a chunk for an id that is ALREADY committed (exists in assets) => x code=dup_asset;detail=<id> immediately (cannot re-open a committed asset; replace via remove+add). (c) Starting a second concurrent more=1 buffer for an id that already has an open in-flight buffer => x code=chunk_conflict (one in-flight buffer per id). (d) node.upsert{mesh:id} and SCEN-4 ref resolution see an in-flight buffer as NOT present (bad_ref) until more=0 commits. (e) asset_revision bumps exactly once, at more=0 commit (not per chunk). (f) Each chunk is bounded by max_chunk_mb and the running reassembly total by max_asset_mb / max_reassembly_mb (§15.2); overflow => x code=cap_exceeded and the in-flight buffer is dropped. (g) An in-flight buffer left open (no more=0) is reclaimable under a reassembly cap/timeout; it never partially registers.
- **Rationale:** Without this, every multi-frame asset would self-error on its second chunk (the contradiction the finding identifies). Treating in-flight bytes as a reassembly buffer distinct from a registered asset resolves it cleanly and makes the immutability rule and mesh-ref resolution both check exactly one thing: committed assets. Matches the recommendation and reuses RGP's existing more=1|0 reassembly model and 64/256 MiB caps (generalized, principle 6). Not mooted by F2 (this is native TGP chunking, not RGP-bridging).
- **Doc change:** §8.7 expand: 'Chunked asset.add reassembles into a per-id in-flight buffer that is not a registered asset. The §8.4 duplicate-id error fires only at more=0 commit and only against committed assets; a chunk targeting an already-committed id => x code=dup_asset; a second open buffer for the same id => x code=chunk_conflict. asset_revision bumps once at more=0. ### SCEN-11 [P1] Fixed color chain baseColor x tint x brightness with sRGB->linear tint decode; Instanced forbids node-level tint; single-instance re-tint via partial update
- **Decision:** One fixed multiply chain for all lit nodes: final_linear = baseColor_linear (texture-sampled or material.base, already linear) * tint_linear * brightness, where tint is sRGB-encoded on the wire (RGBA8 / color=srgb cap) and decoded sRGB->linear before the multiply; alpha multiplies straight through (no sRGB curve on alpha). Multiply (not replace/add) composes predictably with both default and PBR materials and makes the default material a special case (baseColor=white) rather than a separate path. Forbidding a node-level tint on Instanced removes the 'which tint wins' ambiguity. A dedicated single-instance partial update keeps the §12.6 click-highlight cheap (one record, not a full re-upload), reusing the SCEN-7 instance_dirty path. Matches the recommendation. Not mooted by F2.

## Materials, lighting, MSAA, tone-map, theme-tint (MATE)

### MATE-1 [P0] Mixed default-material + PBR nodes in one viewport: tone-map applied to whom?
- **Decision:** Every TGP viewport renders ALL nodes (default-material and PBR) into ONE linear-light offscreen color target, and a single per-viewport tone-map operator (render.tone_map: none/Reinhard/ACES, default none) is applied to the whole resolved linear target uniformly before sRGB-encode and composite. The default material is therefore defined as a LINEAR-light shader (its base/tint/brightness inputs are linearized from sRGB on input, lit in linear, written linear). There is no per-pixel material-class branch and no two-subtarget split: tone-map is unconditionally a whole-viewport stage. With the default operator 'none' (passthrough clamp to [0,1]), a default-only viewport is visually identical to a plain linear render; choosing Reinhard/ACES tone-maps default and PBR pixels identically. The RGP-byte-stability concern in this finding is MOOT under F2 (no adapter, no rgp.wgsl reproduction requirement).
- **Rationale:** F2 removes the only reason to special-case default material (matching legacy rgp.wgsl post-tone-map). With a clean break, the simplest correct rule is one linear pipeline + one whole-viewport tone-map, which is unambiguous regardless of node mix and satisfies principle 6 (generalize, don't special-case) and MATE-9's linear-internal mandate. Defaulting the operator to 'none' means mixing PBR into a viewport never silently alters default-material color unless the app explicitly opts into a tone-map operator.

### MATE-4 [P1] Per-viewport light-count cap exceeded: no defined behavior
- **Decision:** Advertise max_lights in the 7.1 capability reply. This selection never crashes and never produces nondeterministic shading. Going over cap also queues a one-time-per-viewport structured event/error tgp;x;code=cap_exceeded;detail=max_lights (routed only to the owning F1 token, and only if that app opted into error reporting); the patch that pushed it over cap is NOT rejected (lights are dynamic/animated; rejecting a transform patch because an animated light drifted into view would violate principle 1). The over-cap state clears (and may re-fire once) when the count drops back under cap.
- **Rationale:** Matches the finding recommendation and reconciles principle 3 (structured feedback, deterministic) with principle 1 (don't reject app transforms for a soft rendering limit). Deterministic highest-intensity selection avoids the nondeterministic mid-animation shading the finding warns about. F1 scoping is honored: the error routes only to the owning token. Hard-rejecting at node.upsert (an option) is wrong because visibility/animation make the visible count dynamic and per-viewport, not knowable at upsert.
- **Doc change:** Section 7.1 reply example: add max_lights=8 to the caps list. Section 11.3: replace 'a per-viewport light-count cap (advertised in caps)' with the deterministic selection rule (highest-intensity, tie-break by node id), the one-time cap_exceeded event per viewport gated on opt-in error reporting and F1 ownership, and an explicit statement that the patch is NOT rejected. ### LIFE-2 [P0] RIS / DECSTR / CSI 3J effect on the retained scene
- **Decision:** RIS (ESC c) performs a COMPLETE TGP scene teardown across ALL tokens: destroy every viewport, node, asset, material, clip, pending chunk-reassembly buffer, in-progress binary frame, all subscriptions, the explore controllers, the animation clocks, and free all GPU buffers; reset both scene_revision and asset_revision tracking. This is the guaranteed VRAM-recovery path. RIS emits NO TGP error/event/ack to any app (the reset is a user/host recovery action, not an app-addressed event), but it does invalidate all session/namespace tokens so a surviving writer cannot address freed nodes. DECSTR (soft reset) leaves the TGP scene entirely UNTOUCHED (it is a pen/mode soft reset only). CSI 3J (clear scrollback) does NOT touch pinned viewports or scene assets; it follows the inline-anchor rule (see LIFE-3 / LIFE-9): inline viewports whose anchor lines are in the cleared scrollback are evicted like their cells.
- **Rationale:** Directly mirrors the existing ris() in term.rs which already does a full teardown of grids + image placements (the kitty hard requirement) and resets private modes, while soft reset does not. Principle 3 (safe-by-default): RIS must always reclaim up to max_vram_mb so a hostile process cannot pin GPU memory permanently — this is the only guaranteed recovery. The cross-token wipe is intentional: RIS is the user's terminal-wide 'reset everything' and is not per-app. Token invalidation prevents a confused-deputy write to freed ids (F1). F2: no RGP-adapter consideration — RGP scene teardown on RIS is its own untouched legacy path.
- **Doc change:** Edit 15 (Security & robustness) add subsection 15.6 'Reset semantics': 'RIS (ESC c) is the guaranteed VRAM/scene recovery path: it tears down the entire TGP scene (assets, materials, nodes, viewports, clips), cancels all subscriptions/explore/animation, frees all GPU buffers and all pending chunk-reassembly and in-progress binary-frame buffers, and invalidates all session tokens. RIS emits no TGP reply. DECSTR (soft reset) does not affect the TGP scene. CSI 3J clears scrollback only and follows the inline-anchor eviction rule (10.2/§LIFE-3); it never removes pinned viewports or assets.' Also add a row to the 15.2 cap-recovery discussion noting RIS as the bounded-resource escape hatch.

### LIFE-3 [P1] Scrollback eviction of an inline anchor line
- **Decision:** When the last placeholder cell of an inline viewport falls off the bottom of the bounded primary scrollback ring (i.e. all anchor cells are evicted), the terminal DESTROYS that viewport: free its offscreen layer/GPU buffers and remove it from the viewport map. The backing scene nodes/assets are NOT freed (they are shared and may be referenced by other viewports). If the owning app subscribed to lifecycle events, emit one tgp;e;ev=destroyed;vp=<id> to the owning token only; otherwise destroy silently. Inline-viewport lifetime is documented as bounded by scrollback depth. Eviction is per-placeholder-cell: a viewport is destroyed only once NONE of its placeholder cells remain in the live grid or retained scrollback. F3 makes placeholder cells authoritative, so this is a direct consequence — the viewport dies with its cells.
- **Rationale:** F3 binding: placeholder cells are authoritative for position; therefore the viewport's existence tracks its cells, and when the cells are gone the viewport is gone. Principle 3 (bounded resources): without reclaim, a long-running app placing many inline viewports silently leaks VRAM as anchors fall off scrollback — the destroy path caps this. Mirrors the existing O(1) VecDeque pop_front eviction (prompt_marks) and image eviction-on-scrollback already in the codebase. The opt-in destroyed event (principle 2) lets a subscribed app re-place; routing only to the owning token satisfies F1. F2: no RGP placement model involved.
- **Doc change:** Edit 10.2 Inline bullet to add: 'Inline lifetime is bounded by scrollback depth. The placeholder cells are authoritative (F3): when every placeholder cell of an inline viewport has been evicted from the scrollback ring, the terminal destroys the viewport and frees its offscreen layer. Shared scene nodes/assets are not freed. An app subscribed to lifecycle events receives a single tgp;e;ev=destroyed;vp=<id> (owning token only); otherwise eviction is silent.' Add `destroyed` to the ev enum list in 12.5 and add a `lifecycle` event class to the sub granularity note.
- **Test:** Bytes-in tests, constructing Term::new(rows, cols, small_scrollback): (1) Place an inline viewport near the bottom; write enough newlines to push the anchor line beyond rows+scrollback; assert the viewport is removed from the viewport map and an offscreen-layer-freed accessor reflects reclaim, while the backing node still exists in scene.nodes. ### LIFE-4 [P1] DECSTBM scroll-region scrolling vs inline viewports
- **Decision:** Inline viewport placeholder cells are ORDINARY cells: a DECSTBM-bounded scroll moves them exactly as it moves text. The viewport's CellRect is recomputed from the new placeholder-cell positions (F3: cells are authoritative) and the cached layer is re-composited at the new pixel rect (no re-render unless content/camera/size changed). For a viewport whose placeholder cells straddle a scroll-region margin, only the cells inside the region scroll; the cells outside do not — this can split the placeholder run. The viewport's clip_to_scroll_region flag governs the visible portion: when true (default), the portion of the cached layer outside the active scroll region is clipped (not drawn); when false, the layer composites in full at its recomputed rect. Text never scrolls 'through' a viewport because the viewport tracks its own cells. Inline viewports are NOT disallowed inside a DECSTBM region and are never silently downgraded to pinned.
- **Rationale:** F3 binding: placeholder cells authoritative means region scrolls move them like text and the rect follows the cells — this is the only consistent rule. Principle 1 (terminal stays simple): treat placeholder cells as cells, reusing the existing scroll_up/scroll_down grid machinery rather than special-casing viewports. Re-composite-not-re-render reuses the §10.4 cached-layer model and the scene_revision/viewport-dirty split (principle 6). clip_to_scroll_region already exists in the Viewport struct; this gives it precise meaning for the straddle case. Region scrolling is the core pager/editor mechanic (the showcase apps), so correctness here is load-bearing. F2: no RGP relevance.
- **Doc change:** Edit 10.3 (reflow) add a paragraph: 'DECSTBM scroll-region scrolling moves an inline viewport's placeholder cells exactly like text (F3). The viewport CellRect is recomputed from the new cell positions and only the viewport dirty flag is set, so the cached layer is re-composited at the new rect without a re-render. When placeholder cells straddle a scroll-region margin, only cells inside the region scroll; clip_to_scroll_region (default true) clips the cached layer to the active region so nothing bleeds across the margin. Inline viewports are permitted inside DECSTBM regions and are never downgraded.'

### LIFE-5 [P2] GPU device loss / context reset recovery
- **Decision:** The full scene (assets, nodes, world matrices, viewport rects, instance buffers) is mandated CPU-resident (already required for tests). On wgpu device loss the terminal: recreates the device/queue, then forces a complete re-upload of ALL assets/materials/instances and re-creates ALL per-viewport offscreen color+depth+(MSAA) and pick targets by treating the effective asset_revision and every viewport dirty flag as bumped — explicitly IGNORING revision equality for that one recovery pass. CPU-side scene state is NEVER lost. Device loss is NOT a session teardown and emits no TGP error to apps (it is invisible recovery; the app's scene survives). An in-flight explore drag MAY be cancelled by device loss (and only by device loss) with a tgp;e;ev=leave (or drag-cancel) to the owning subscriber; animation clocks resume from saved phase (see LIFE-10). This generalizes the scene_revision/asset_revision dirty split (principle 6) with a 'force-all-dirty' invalidation primitive.
- **Rationale:** Principle 6: the dirty split is the template; device loss needs a force-all-dirty path because equality gating (revision unchanged -> skip upload) otherwise prevents recovery forever. Principle 3 (no permanent broken state): rebuilding from CPU state is the robust recovery. Keeping CPU state authoritative is exactly the testability mandate (all geometry CPU-side). Cancelling a drag only on device loss (not on resize/theme) is the minimal interaction disruption, consistent with LIFE-10. F2: RGP has its own path; not bridged.
- **Doc change:** Add subsection 11.5 'Device loss recovery': 'All scene state is CPU-resident. CPU state is never lost; no TGP error is emitted. Only device loss may cancel an in-flight explore drag (emitting a drag-cancel/leave to the owning subscriber); animation resumes from saved phase (14, §LIFE-10).' Add to 6.5 a note: 'a force-all-dirty invalidation (device loss) bypasses revision-equality gating.'

### LIFE-7 [P1] Event/error replies emitted while no foreground app is reading stdin
- **Decision:** Subscriptions, explore controllers, and terminal-side animation/auto-spin clocks are tied to the lifetime of the owning session token (F1). The terminal cancels all of a token's subscriptions + explore + animation when: (a) the foreground process / PTY input owner changes away from the token owner, or (b) the PTY input side closes (EOF) / the app exits, or (c) the token is invalidated (RIS, LIFE-2). While cancelled, NO tgp;e events are emitted for that token. Additionally, the terminal NEVER emits tgp;e input events (click/hover/enter/leave/drag/wheel/camera) while the terminal window is unfocused; resize/lifecycle reports may still queue. This prevents 'ESC _ tgp;e;... leaking into bash' — events only flow to a live, foreground, focused subscriber on the owning token. Auto-spin and the explore controller stop advancing once their subscriber is gone (no orphan camera motion driving events into a shell prompt).
- **Rationale:** Binding F1 (route only to owning app) + F4 (subscriptions capture within viewport) imply lifetime must track the owner; emitting to a non-owner or a dead reader is the classic mouse-escape-leak bug. Principle 3 (safe-by-default): unconsumed frames must not back up the reply buffer or corrupt another app's command line. Principle 2 (terminal only takes control when asked): when the asker is gone, the terminal relinquishes (stops explore/anim). Gating input events on focus matches the existing report_focus model in term.rs. F2: no RGP relevance.
- **Doc change:** Add subsection 12.7 'Subscription & controller lifetime': 'A token's subscriptions, explore controllers, and animation/auto-spin clocks are cancelled when the foreground PTY input owner changes away from the token owner, when the PTY input side closes (EOF/app exit), or on RIS. ### LIFE-9 [P1] CSI 2J / ED / EL erase vs viewports and the cached layer

### LIFE-10 [P2] Resize / device loss / theme change while explore-dragging or animating

Principle 6: theme re-tint is a viewport-dirty re-composite, not a re-render/reset. ### LIFE-11 [P0] PTY EOF / terminal close mid-binary-frame and mid-chunked-asset
- **Decision:** On PTY EOF / terminal close the parser ABORTS any in-progress binary-length frame (discard the partially-consumed bytes and the awaiting-N-bytes state) and DROPS all pending per-id chunk-reassembly buffers, freeing their memory immediately; no error is emitted (the app is gone). Independently, to harden against a stalled-but-not-EOF stream that could wedge the parser by promising N bytes and never delivering, a max-message duration/quiescence guard (driven by the injectable clock) aborts an in-progress binary read or stalled chunk reassembly after the guard elapses, emitting tgp;x;code=timeout;detail=binary_incomplete to the owning token (if it opted into errors) and freeing the buffers. A complete-but-shorter-than-len read that terminates early (transport framing breaks) emits tgp;x;code=truncated and discards the frame. The binary back-channel apc_end returns Option<BinaryFollow{len,enc}> (per grounding) so the parser knows exactly how many bytes to consume and can detect short reads.
- **Rationale:** Grounding: the APC pre-scanner terminates on ESC/BEL/0x9C and apc_end returns unit, so a binary len=N frame needs a back-channel — apc_end -> Option<BinaryFollow{len,enc}> is the minimal change, and it is what lets EOF/short-read detection work at all. Principle 3 (safe-by-default, bounded, structured errors not crashes/silent drops): EOF must reclaim up-to-64MiB per-id reassembly buffers (the §15.2 cap) and the timeout guards a hostile/stalled stream from pinning the parser. Matches the existing RGP handler's drop-pending-chunked-upload behavior. The structured timeout/truncated errors replace RGP's silent drop. F2: RGP's own chunk path is untouched.
- **Doc change:** Edit 8.2 to state the parser back-channel explicitly: 'On a tgp binary header the APC pre-scanner's apc_end returns Option<BinaryFollow{len,enc}>; the parser then consumes exactly len bytes outside escape scanning.' Add subsection 15.7 'EOF & stall handling': 'On PTY EOF/close the parser aborts any in-progress binary frame and drops all pending per-id chunk-reassembly buffers, freeing memory immediately, with no error emitted. A max-message duration/quiescence guard (injectable clock) aborts a stalled binary read or chunk reassembly, freeing buffers and emitting tgp;x;code=timeout;detail=binary_incomplete to the owning token (if subscribed to errors). A frame that terminates shorter than its declared len emits tgp;x;code=truncated and is discarded.' Add codes timeout and truncated to the 15.3 error table.

### EXPL-1 [P0] [OPEN] Precedence/consumption model for explore + events + raw on one pointer stream
- **Decision:** Per viewport, the three interaction levels resolve by a fixed precedence with mutual exclusion. (1) raw is mutually exclusive with explore and events: a sub that requests raw together with explore or events is rejected with tgp;x code=invalid_sub before any state change. (2) When raw is active it consumes the entire pointer stream for that viewport's cell rect and suppresses explore and events there. (3) When explore+events coexist, gestures are partitioned deterministically: a press followed by release with zero intervening motion (within a small dead-zone) = a click event (also down/up if subscribed); any motion between press and release = an explore gesture (orbit/pan per ExploreOpts) and that motion-bearing gesture does NOT also emit a click; hover/enter/leave always fire regardless of explore. Drag and wheel are consumed by explore when enabled (see EXPL-10); drag events are only forwarded to the app when explore does not own that axis (i.e. orbit/pan disabled for that drag) or in raw mode. This is exactly F4.
- **Rationale:** Directly mandated by USER DECISION F4 (raw mutually exclusive with explore+events; explore consumes drag/wheel; no-move press/release = click; hover/enter/leave always fire). A fixed precedence with a press-moved dead-zone gives one unambiguous owner per gesture, satisfying principle 1 (app-authoritative: terminal only consumes what was opted into) and principle 3 (structured rejection of conflicting sub instead of silent ambiguity).
- **Doc change:** Section 12.2: replace 'Three levels, independently selectable' with a normative precedence subsection 12.2.1 'Gesture arbitration': raw XOR (explore|events) per viewport, validated at sub time (tgp;x invalid_sub on conflict); when explore+events coexist, no-motion press/release = click, motion = explore, hover/enter/leave always fire; define a press-move dead-zone (advertise as caps field e.g. click_deadzone_px, default 3). Cross-reference 12.3 (explore owns drag/wheel) and 12.10/EXPL-10 (wheel ownership).
- **Test:** Drive Parser::advance with: (a) sub requesting raw+events on one vp -> assert no subscription stored and drain_pty_replies contains tgp;x;code=invalid_sub. ### EXPL-3 [P0] [OPEN] Subscription lifecycle on node.remove / viewport destroy / id reuse
- **Decision:** Subscriptions are owned by the namespace token (F1) and bound to a viewport id. (1) vp destroy drops ALL of that viewport's subs and frees its pick target and pick buffer. (2) node.remove silently removes that node from any explicit node-id sub list for that viewport (no error, no event); if the removed node was hovered, synthesize ev=leave first (see EXPL-5). (3) nodes=* is a viewport-wide filter that matches any current node and therefore naturally covers re-created ids. (4) Re-creating a previously-removed specific node id via node.upsert does NOT revive an explicit sub for that id; the app must re-subscribe. (5) A sub naming a node id that does not currently exist is accepted (filters are by id, evaluated at event time) but never matches until/unless that id exists — it is not an error. All sub mutations and the events they produce route only to the owning token.
- **Rationale:** Follows the finding recommendation and principle 3 (no dangling state that resurrects/misroutes events on id recycling). F1 makes ownership explicit: subs and their events are token-scoped, so a recycled id under a different token can never inherit another app's sub. Auto-cleanup keeps terminal state bounded (principle 3) without surprising the app (explicit re-subscribe, principle 1/2).
- **Doc change:** Add Section 12.5.1 'Subscription lifecycle': vp destroy tears down all its subs + frees pick target; node.remove drops that id from explicit subs and synthesizes leave if hovered; nodes=* is a live viewport filter; recreated ids do not revive explicit subs; subs are token-scoped (xref F1/§8.4 namespace). Note that a sub for a not-yet-existing id is valid and dormant.

### EXPL-4 [P0] [OPEN] Pick readback timing/async vs event emission ordering and staleness
- **Decision:** Picking is resolved against a CPU-side last-pick buffer that is refreshed each render of the viewport's pick pass (no synchronous GPU stall on input). Every emitted tgp;e carries the scene_revision the pick buffer was rendered against (field rev=) so the app can detect staleness. If the resolved node id no longer exists in the scene at emit time (removed since the buffer was built), the report is dropped (for click/hover/enter) or, for leave, emitted against the prior node id (see EXPL-5). World-space hit point is computed CPU-side from the pick buffer's stored depth/position so it is testable with no GPU.
- **Rationale:** Follows the finding recommendation; satisfies the testability imperative (geometry/pick kept CPU-side, deterministic) and principle 3 (never emit an event citing a node that no longer exists). Stamping rev= generalizes the scene_revision dirty split (principle 6) into the event channel so apps reconcile against the same revision counter.

### EXPL-5 [P1] [OPEN] Hover/enter/leave state machine across frames, viewports, scene mutation
- **Decision:** Hover state is held per (viewport) as a single current target (node id, instance index) or None. Recompute-on-render-and-on-move prevents stuck app-side highlight/tooltip state (the stated failure). Per-viewport keying matches F1/F4 routing and the overlapping-viewport rule (EXPL-8). Principle 3: deterministic, no missing/duplicate leaves.

### EXPL-6 [P1] [OPEN] Focus loss / pointer leaving terminal mid-drag (explore and raw)

## CAPS

### CAPS-1 [P0] DA1 pairing for the no-hang guarantee
- **Decision:** NORMATIVE: The always-answered no-hang property is realized by app-side pairing PLUS a terminal-side ordering guarantee. (a) The recommended detection handshake is `ESC[c` (DA1) followed by `ESC _ tgp;q;v=N ESC \` — apps SHOULD send them together. (b) The terminal MUST, when both a `tgp;r` and a DA1 reply are pending in the writeback queue, enqueue `tgp;r` strictly BEFORE the DA1 reply. (c) The terminal MUST answer any well-formed `tgp;q` with a `tgp;r` regardless of negotiated version (carry the supported range, see CAPS-6/CAPS-8) — it MUST NOT silently drop a recognized query. (d) Normative app rule: 'DA1 reply observed with no preceding `tgp;r`' means TGP is ABSENT. The terminal cannot enforce that an app paired the queries, so a SECONDARY app-side timeout (recommended default 250ms) is documented as belt-and-suspenders only, not a protocol requirement. The terminal's obligation is purely (b)+(c): always answer, always order tgp;r first.
- **Rationale:** Principle 4 makes detection the one thing the terminal must do well. The terminal cannot make a tokenless/unpaired query un-hang on a NON-TGP terminal (impossible by definition — that terminal emits nothing), but it CAN make detection deterministic on a TGP terminal by guaranteeing tgp;r precedes DA1 on the shared FIFO writeback. That converts 'heard nothing yet' into 'DA1 seen => definitive absence', eliminating the hang against any terminal that answers DA1 at all. Grounded: both replies share pty_replies (term.rs:551), so ordering is a terminal-controlled enqueue-order property, not luck.
- **Doc change:** §7.1 'Always-answered' bullet: replace the parenthetical with a normative MUST list: (1) terminal MUST emit tgp;r for every well-formed tgp;q irrespective of version; (2) when DA1 and tgp;r are both queued, terminal MUST enqueue tgp;r before the DA1 reply; (3) define the app inference 'DA1 reply with no preceding tgp;r == TGP absent' as the canonical detection rule; (4) note a 250ms app-side timeout as a documented SECONDARY safeguard, explicitly NOT a terminal obligation. Add a forward-ref to §7.1.x ordering (CAPS-2).
- **Test:** PTY-in: feed `ESC[c` + `ESC_tgp;q;v=2ESC\` in one advance() call; assert drain_pty_replies() bytes contain `\x1b_tgp;r;` at an index STRICTLY LESS THAN the index of `\x1b[?` (DA1) — proves tgp;r-before-DA1 ordering. Second test: feed a well-formed `tgp;q` with an unsupported v (e.g. v=99); assert a tgp;r is still queued (non-empty, starts with the tgp;r prefix) — proves 'always answer'. Third test: feed `tgp;q` alone (no DA1); assert exactly one tgp;r queued and no DA1 bytes.

### CAPS-2 [P0] tgp;r vs DA1 writeback ordering
- **Decision:** NORMATIVE: Make BOTH halves of the recommendation binding. (a) The terminal MUST preserve FIFO order on the shared pty_replies writeback channel: replies are enqueued in the order their triggering input bytes were fully parsed. (b) Because the terminal cannot reorder across distinct dispatch points without buffering, the canonical app handshake is to send `tgp;q` and `ESC[c` such that the terminal's natural FIFO yields tgp;r first. The terminal additionally enforces a hard invariant: if a single advance() batch contains both a recognized tgp;q and a DA1 request, the terminal enqueues the tgp;r reply BEFORE the DA1 reply even if DA1 was parsed first (special-cased flush ordering for the detection handshake). This makes the ordering deterministic regardless of which order the app emitted the two queries.
- **Rationale:** CAPS-1's inference 'DA1 seen, no tgp;r => absent' is only sound if tgp;r is guaranteed to precede DA1. Pure FIFO alone would require the app to send tgp;q first; mandating the terminal special-case the flush removes that fragile app dependency and makes the guarantee hold for both emission orders. Grounded: pty_replies is a Vec extended in dispatch order (term.rs:551), so the terminal owns enqueue order and can buffer the DA1 reply until the same batch's tgp;r is enqueued.
- **Doc change:** Add §7.1.x 'Reply ordering (normative)': (1) pty_replies is FIFO in parse order; (2) within any advance batch containing both a tgp;q and DA1, tgp;r MUST be enqueued before the DA1 reply; (3) state apps MUST NOT rely on input-emission order for the detection inference because the terminal guarantees tgp;r-first. Cross-link CAPS-1.
- **Test:** PTY-in (DA1 FIRST): `ESC[cESC_tgp;q;v=2ESC\` -> assert index(tgp;r) < index(DA1) in drained replies. PTY-in (tgp;q FIRST): `ESC_tgp;q;v=2ESC\ESC[c` -> assert same ordering (tgp;r first). ### CAPS-4 [P1] Runtime-variable caps (resize / device loss / headless)
- **Decision:** NORMATIVE: Caps are re-queryable AND the terminal pushes a fresh reply on material capability transitions, with tgp;x as the hard backstop. (a) `tgp;q` is valid at any point mid-session and MUST be answered with a fresh tgp;r reflecting current caps (re-negotiation on demand; see CAPS-5 idempotency). (b) On a MATERIAL capability transition — GPU device loss/restore, a headless/SSH transition that changes the renderable budget, or a resize that changes max viable inline cells — the terminal MUST emit an UNSOLICITED `tgp;r` to every app whose session token completed a handshake (F1: routed only to owning tokens; tokenless writers get nothing). The unsolicited reply carries the full current cap set and a monotonically increasing `caps_gen=` counter so the app can detect staleness/ordering. (c) tgp;x cap_exceeded remains the authoritative hard enforcement: an app that pre-trimmed to a now-stale cap still gets a structured error, never a silent drop or crash. Caps are advisory hints; tgp;x is the contract.
- **Rationale:** The advertised-once model goes silently stale on device loss (principle 3 safety + principle 4 reliability). Re-queryability gives the app a pull path; the unsolicited push gives it a signal it would otherwise lack (you can't pre-trim to a budget you weren't told dropped). caps_gen makes the push idempotent/orderable. F1 scopes the push to the owning token so caps changes don't leak across apps. tgp;x stays the backstop per principle 3 (structured errors, bounded resources).
- **Doc change:** §7.1: add 'Caps are runtime-variable' note — tgp;q is re-queryable mid-session; add a `caps_gen=` field to tgp;r. New §7.1.y 'Unsolicited caps push (normative)': terminal MUST emit a fresh tgp;r on device-loss/restore, headless transition, or inline-budget change, routed only to handshaked session tokens (ref F1 § scene-scope), with monotonic caps_gen. §15.2: state tgp;x cap_exceeded is authoritative even when an app pre-trimmed to a prior (now stale) advertised cap.

### CAPS-5 [P1] Concurrent / repeated tgp;q semantics
- **Decision:** NORMATIVE: (a) `tgp;q` is idempotent and ALWAYS answered with a tgp;r reflecting current state (consistent with CAPS-4 re-query). (b) A `tgp;q` MUST NOT be sent while a binary frame for the same session is mid-read; because the binary read state consumes exactly len=N raw bytes (grounded: parser switches to a length-counted read, bypassing ESC/BEL/0x9C scanning), any `ESC _ tgp;q` bytes that land inside an active len=N payload are by definition payload, not a control frame, and are consumed as such — the terminal does NOT scan for queries inside a binary frame. The app is responsible for not interleaving. (c) A repeated tgp;q with a DIFFERING v= re-negotiates the session version per the CAPS-6 rule; a repeated tgp;q with the SAME v= is a pure idempotent re-answer (no state change beyond a possibly-updated caps_gen). (d) Control frames (q/r/e/x/a/vp/sub/anim) are never read in binary-length mode — only the patch (`p`) and chunked asset frames carry len=N — so a tgp;q is always parseable EXCEPT when physically embedded inside an in-flight binary payload (which is malformed app behavior, not a terminal bug).
- **Rationale:** Grounded: the binary back-channel (apc_end returning a BinaryFollow{len,enc}) puts the parser into consume-exactly-N mode, so bytes inside are not APC-scanned (parser.rs apc_chunk uses memchr3 only OUTSIDE that mode). Therefore the terminal cannot rescue a query buried in a binary frame — the only sound rule is to forbid the interleave and make queries idempotent everywhere else. Restricting binary-length mode to p/asset frames keeps q always parseable in normal operation (principle 4).
- **Doc change:** §7.1: add 'tgp;q is idempotent and always answered; a repeat with a new v= re-negotiates (see §7.x), same v= is a no-op re-answer.' §8.2: add normative note that only `p` and chunked `asset.add` frames use len=N binary mode; control frames (q/r/e/x/a/vp/sub/anim) are always text APC. §8.2: add 'Apps MUST NOT emit any other frame (including tgp;q) between a binary header and its len bytes; bytes in that window are consumed as payload.'
- **Test:** PTY-in: send `tgp;q` twice -> assert two tgp;r replies, identical except caps_gen monotone. PTY-in: send `tgp;p;...;len=10ESC\` + 10 raw bytes where bytes 3..8 spell `tgp;q` -> assert NO second tgp;r is produced (the bytes were consumed as patch payload) and exactly len=10 bytes were consumed, parser returned to Ground. ### CAPS-6 [P0] Version negotiation degrade rule at both ends
- **Decision:** NORMATIVE: (a) `v=` is REQUIRED in tgp;q; omission is a parse_error. Because the app has not yet established error opt-in, a tgp;q with malformed/absent v= is STILL answered with a tgp;r carrying the terminal's supported range (vmin/v) and NO negotiated session — i.e. the terminal never silently drops a recognizable tgp;q (ties to CAPS-1/CAPS-8 'always answer'); it MAY additionally emit a tgp;x parse_error. (b) The reply's negotiated version is min(app_max, term_max). (c) If app_max < term_min (app too old), the terminal MUST still reply with a tgp;r whose negotiated `v=` is set to term_min and whose `vmin=` advertises the true minimum, so the app can KNOWINGLY refuse and pick a fallback — never a silent drop. (d) The tgp;r ALWAYS carries both `vmin=` and `v=` (supported range + negotiated), so the app can always compute compatibility (see CAPS-8).
- **Rationale:** The doc's degrade rule was undefined below term_min and on v= omission. Required v= with a non-fatal answer keeps detection reliable (principle 4) without silent drops (principle 3). Replying with term_min when the app is too old converts an ambiguous silence into an actionable 'too new for you' signal, which CAPS-8 needs to distinguish 'TGP present but incompatible' from 'TGP absent'.
- **Doc change:** §7.1 'Versioned' bullet: rewrite normatively — v= REQUIRED (omission=parse_error but still answered with the range); negotiated = min(app_max, term_max); if app_max < term_min reply with v=term_min and vmin=term_min so the app can refuse; tgp;r ALWAYS carries vmin= and v=. §7.2: note unknown future versions degrade to highest mutually understood, consistent with this min() rule.

### CAPS-7 [P0] Error-reporting & event opt-in signaling at handshake
- **Decision:** NORMATIVE: A completed tgp;q/tgp;r handshake (a successfully negotiated session under a per-app token, F1) IS the error-reporting opt-in. (a) Once a session token has a negotiated version, all structured tgp;x errors for that token's patches/ops are emitted, routed ONLY to the owning token (F1). (b) Tokenless or un-handshaked writers (dumb readers, curl|cat) never establish a session, so they never receive tgp;x — preserving the silent-drop default for non-participants (grounded: term.rs:3421 silent-drop is the fall-through). (c) Event reporting (tgp;e) remains separately gated by per-viewport `sub` and feat=event (this is unchanged — error reporting and event reporting are DISTINCT opt-ins). (d) Edge case: a malformed FIRST patch from a token that HAS handshaked still gets a tgp;x (the handshake already armed errors); a malformed patch from a token that has NOT handshaked is silently dropped. There is no separate `errors=1` field — the handshake is the signal.
- **Rationale:** If error reporting needed its own opt-in field, a malformed opt-in attempt would fall back to silent drop and the app couldn't tell 'rejected' from 'applied' — the core RGP improvement evaporates at the boundary. Treating the handshake as the opt-in (option 2) is the only mechanism that is already-established before the first patch can fail. F1 scopes routing to the owning token so errors never leak across apps and dumb readers stay silent (principle 3).
- **Doc change:** §15.3: replace 'when the app negotiated error reporting' with the normative rule: a completed tgp;q/tgp;r handshake under a session token arms structured errors for that token; errors route only to the owning token (ref F1); un-handshaked/tokenless writers get silent drop. ### CAPS-8 [P1] Distinguishing v1-TGP-present from no-TGP
- **Decision:** NORMATIVE: A well-formed tgp;q is ALWAYS answered with a tgp;r that carries the terminal's full supported version RANGE (`vmin=` and `v=`), so the presence of ANY tgp;r unambiguously means 'TGP exists' and the app can compute compatibility locally. (a) The terminal MUST NOT suppress tgp;r for an out-of-range requested version (it replies with the clamped/min version per CAPS-6, never silence). (b) Therefore the app's three-way decision is well-defined: 'no tgp;r before DA1' => TGP ABSENT (use sixel/ASCII); 'tgp;r present, app_max within [vmin..v]' => TGP USABLE; 'tgp;r present but app_max < vmin or app_min > v' => TGP PRESENT BUT INCOMPATIBLE (prompt to upgrade / different fallback). (c) Apps MUST NOT probe the RGP s-query to infer TGP — the two replies are independent and the RGP reply says nothing about TGP (ref CAPS-10).
- **Rationale:** Detection that relies only on 'a tgp;r at all' conflated 'too new/old' with 'absent' when below-min queries were dropped. CAPS-6 already forbids dropping; adding the vmin/v range to every reply makes presence == existence and lets the app pick the correct one of THREE fallback paths the design requires it to choose between (principle 4). Forbidding RGP-probe avoids a false cross-protocol inference (principle 4 reliability).
- **Doc change:** §7.1: state tgp;r ALWAYS carries vmin= and v= (range), and define the canonical app three-way classification (absent / usable / present-but-incompatible). §7.1 reply example: add vmin=1. Note apps MUST NOT use the RGP s-query to detect TGP (cross-ref §4 deprecation per F2 and CAPS-10).

### CAPS-9 [P1] binframe feat vs enc= overlap and transport-corruption failure mode
- **Decision:** NORMATIVE: enc= is the SINGLE source of truth for binary framing; the `binframe` feat token is DROPPED (removed from the frozen v1 set, see CAPS-3). (a) The tgp;r `enc=` list advertises only encodings the terminal believes the LIVE transport can carry; a terminal behind a passthrough that cannot carry raw bytes advertises `enc=b64` only. (b) An app MUST NOT send `enc=bin` unless the reply advertised `bin`; doing so is a parse_error (tgp;x if armed). (d) If a binary frame IS received but fails to decode (CBOR/length mismatch from transport mangling), the terminal MUST emit a tgp;x parse_error (when armed) so the app can downgrade — never silent corruption.
- **Rationale:** The grounding warns raw CBOR contains ESC/BEL/0x9C that corrupt the APC pre-scanner; advertising binframe both as a feat token AND via enc= was redundant and gave conflicting failure modes. Collapsing to enc= (single truth) plus a probe->ack handshake lets the app VERIFY the live transport (tmux passthrough may strip raw bytes after the cap reply was generated) before streaming bulk binary, and a parse_error on mangled binary gives an explicit downgrade signal (principle 3: structured errors, principle 4: app owns fallback).
- **Doc change:** §7.1: remove binframe from feat=; state enc= is the sole binary-framing advertisement and is advertised-only-when-the-transport-is-believed-safe. §8.2: add a normative 'enc=bin probe' — app sends a minimal binary frame, expects tgp;a; no ack => downgrade to b64. §8.2 'Robustness fallback': add that a binary frame failing length/CBOR decode yields tgp;x parse_error (when armed). §15.3: add code=parse_error;detail=binary_decode. ### ANIM-1 [P0] Deterministic injectable monotonic clock drives all terminal-side playback
- **Decision:** All terminal-side clip playback advances off a single injectable monotonic Clock abstraction (trait Clock { fn now(&self) -> Instant-like monotonic instant }). ### ANIM-2 [P0] Playback exclusively owns a playing node's animated TRS channels; conflicting upsert is rejected node_busy unless it carries stop
- **Decision:** While a (clip,node) instance is Playing or Paused, that playback exclusively owns exactly the TRS channels (subset of translation/rotation/scale) the clip animates on each affected node. - **Rationale:** USER DECISION: explicit two-writers conflict rule. Mirrors explore's 'terminal controls one thing, app controls the rest' separation (12.3) and preserves 8.6 atomicity — a silent flicker or one-frame-then-overwrite would violate the atomic-txn guarantee. Channel-granular ownership lets the app still drive untouched channels, honoring principle 1 where it does not conflict. F1 layers token-scoping ahead of the busy check. Not mooted by F2.
- **Doc change:** Section 14: add 'Ownership while playing' — 'A Playing/Paused (clip,node) instance exclusively owns the TRS channels the clip animates on each node. ### ANIM-4 [P0] (clip,node) is the playback handle; Stopped/Playing/Paused state machine; play-while-playing restarts

### ANIM-10 [P0] All TGP frames process in strict PTY receive order; anim sees committed prior patches; anim on unknown node -> x;code=unknown_node
- **Decision:** Every TGP frame (patch p, anim, vp, sub) is processed in strict PTY byte-receive order against the live scene; there is no cross-frame reordering or deferral. Queuing/pending would add hidden state and non-determinism; requiring an ack round-trip would hurt the compact streaming path (principle 5). unknown_node is the structured error (principle 3). ### CAPS-1 [P0] Binary-frame len cap vs txn atomicity: error reply must cite a txn that was never decoded
- **Decision:** Make the TEXT header the authoritative carrier of correlation+framing metadata so an error is always answerable before any payload is decoded. The binary header MUST be `tgp;p;txn=<u32>;enc=bin|b64;len=<N>` with `txn` and `len` mandatory. The parser validates `len <= max_msg_mb` at TEXT-header parse time, BEFORE entering consume-N mode. On a len-over-cap rejection the terminal: (1) still transitions into consume-exactly-N mode and drains/discards exactly N bytes (or to the negotiated stall limit, see CAPS-2) so stream framing stays aligned and the next `tgp;` header re-syncs cleanly; (2) emits `tgp;x;txn=<txn>;code=msg_too_large;detail=len=<N>,cap=<bytes>` (no `op=` field, since no op was ever parsed). `op=` is OPTIONAL on `x` and present only when a specific op index is known. The grounded back-channel: `apc_end` returns `Option<BinaryFollow{len, enc}>`; the framer records `txn` from the parsed header alongside it so the rejection path has the txn without decoding the CBOR.
- **Rationale:** Conforms to principle 3 (structured errors not silent drops) and principle 4 (app owns fallback: a `msg_too_large` with the actual len lets the app re-chunk). The §8.2 example already shows `txn` in the text header; hoisting it makes it survive a payload-level cap so the app's ack/error correlation loop never stalls waiting on a txn it can never hear about. Draining N keeps the byte stream aligned, preventing a cascade of parse errors on subsequent valid frames.
- **Doc change:** §8.2 (Framing): make `txn` and `len` REQUIRED fields of the binary header; add sentence: 'A binary header MUST carry `txn`; the terminal validates `len` against `max_msg_mb` at header-parse time, before entering consume-N mode. On over-cap, the terminal still consumes (and discards) `len` bytes to preserve framing, then re-enters Ground.' §15.3: add `msg_too_large` to the code enum; state that `x` MAY omit `op=` when no op index is knowable (cap fired pre-decode) and that `txn` is always present. Cross-ref CAPS-2 for the bounded-drain interaction.
- **Test:** PTY-bytes-in via `Parser::advance(&mut term, ...)`: (a) send `ESC _ tgp;q;v=2 ESC \` then a header `ESC _ tgp;p;txn=42;enc=bin;len=<max+1> ESC \` followed by max+1 junk bytes; assert `term.drain_pty_replies()` contains `tgp;x;txn=42;code=msg_too_large` with NO `op=`, and assert scene node count unchanged. ### CAPS-2 [P0] Truncation / EOF / stall mid-binary across PTY read chunks has no cap or recovery
- **Decision:** Define an explicit consume-N parser state with two bounds plus a reset rule. (1) Bytes for an in-flight binary frame accumulate against the per-session pending budget (shared with chunk reassembly, CAPS-3). (2) A deterministic INACTIVITY bound expressed in PTY-read-events (not wall time): if `advance` is called K times (default K configurable) while a binary frame remains incomplete and no bytes for it arrived, OR a host-reset/RIS occurs, the frame is aborted. (3) Any control sequence that resets the terminal (RIS `ESC c`, DECSTR) while mid-binary aborts the frame and returns to Ground. On any abort: discard buffered bytes, free the budget, emit `tgp;x;txn=<txn>;code=truncated;detail=<got>/<len>`, return to Ground. The consume-N counter itself prevents an infinite hold: once `len` bytes are consumed the state always exits regardless of content. Drip-feeding is bounded because buffered bytes count against the per-session pending cap (CAPS-3) — a too-large `len` is already rejected at header parse (CAPS-1), so consume-N only ever runs for an under-cap `len`. The deterministic clock for the inactivity bound is the injectable test clock (advance-call count), keeping it GPU-free and testable.
- **Rationale:** Principle 3: a hung `curl` that announces an under-cap `len` then dies must not wedge the parser. Because CAPS-1 already rejects over-cap `len`, the worst case is a single under-cap frame held open; the read-event inactivity bound + host-reset abort guarantee progress. Using advance-call count rather than wall time keeps the rule deterministic and unit-testable, satisfying the testability imperative (the brief flags wall-clock caps as non-deterministic).
- **Doc change:** §8.2 / new §15.2 bullet: 'Mid-binary truncation/stall: a binary frame in consume-N state is aborted (bytes discarded, budget freed, `tgp;x;code=truncated` emitted) on (a) an inactivity bound measured in PTY-read events, or (b) any terminal reset (RIS/DECSTR). The consume-N byte counter guarantees the state exits after exactly `len` bytes.' Add `truncated` to the §15.3 code enum.
- **Test:** (a) Send binary header `len=100`, then `advance` with only 40 bytes, then call `advance` with empty/unrelated input N>K times; assert `tgp;x;code=truncated;detail=40/100` queued and parser back in Ground (a subsequent valid frame commits). (b) Send header `len=100`, 40 bytes, then `ESC c` (RIS); assert frame aborted, `truncated` emitted, pending budget accessor reads 0. (c) Split a valid `len=100` payload across three `advance` calls (40+40+20); assert it reassembles and commits exactly once (no false truncation when bytes keep flowing).

### CAPS-3 [P0] Chunk reassembly cap vs partial allocation: when does an over-cap multi-frame asset tear down
- **Decision:** Adopt the RGP enforcement MODEL (not the RGP code path — F2 means no adapter/shared code) as a TGP-native rule: caps are checked BEFORE accepting each chunk's bytes, with immediate free on breach. Two scopes: a per-asset-id pending cap (`max_asset_bytes`) and a per-session total pending cap (`max_pending_bytes`), both advertised in the caps reply. For each `asset.add` chunk (and each in-flight binary frame, shared budget with CAPS-2): compute `new_total = current + incoming.len()`; if it would exceed either cap, reject the chunk, immediately free ALL buffered bytes for that id, decrement the session total, and emit `tgp;x;txn=<txn>;op=<i>;code=cap_exceeded;detail=chunk_size`. No reservation-on-first-chunk (avoids over-rejecting honest small assets); cumulative check on every chunk instead. An `asset.add` arriving for an id with a pending chunked upload follows §8.4's collision rule. The defaults (64 MiB per-id / 256 MiB session) are starting constants engineering may tune — they are NOT inherited from RGP code, just numerically aligned.
- **Rationale:** Principle 3: checking only at final assembly would permit up to many-frames × per-frame allocation, a parse-time bomb. Cumulative-on-entry with immediate free is the proven-safe shape. F2 forbids reusing the RGP handler's code/quirks, so this is restated as an independent TGP rule that happens to share the numeric constants; the finding's 'mirror RGP exactly' recommendation is honored at the model level only, not as code reuse. Shared pending budget with CAPS-2 means a single accountant covers both partial binary frames and chunked assets.
- **Doc change:** §8.7 (Chunking): replace 'reassembles before parsing' caveat with: 'Cumulative pending size is checked on every chunk before its bytes are accepted, against a per-asset-id cap and a per-session total cap (both advertised). A breach rejects the chunk, immediately frees all buffered bytes for that id, and emits `cap_exceeded`. No memory is reserved ahead of arrival.' §15.2: list `max_asset_bytes` and `max_pending_bytes` (replacing the vague 'max chunk reassembly size'); note this is a TGP-native rule, not the RGP code path (F2).

### CAPS-4 [P0] VRAM cap is whole-session but txn atomicity requires all-or-nothing GPU commit
- **Decision:** Two-phase commit with CPU-side accounting as the single source of truth. Phase 1 (validate): for the whole txn, compute the net VRAM delta CPU-side from declared/parsed sizes — bytes added by `asset.add`/`material.add` (vertex+index+texture footprint, padded to the renderer's alignment) minus bytes freed by `node.remove`/asset replacement within the same txn. VRAM is accounted as CPU-known footprint (post-decode expanded size from CAPS-7), NOT actual GPU residency, so accounting is deterministic and GPU-free-testable. If `session_vram_used + net_delta > max_vram_mb`, reject the ENTIRE txn atomically, emit `tgp;x;txn=<txn>;op=<first-busting-op>;code=vram_exhausted;detail=need=<bytes>,avail=<bytes>`, and commit nothing (nothing was uploaded, so nothing to free). Phase 2 (commit): only on full validation pass do staged assets upload and `asset_revision`/`scene_revision` bump. Instancing counts the instance buffer footprint once per node; a shared asset referenced by many nodes counts once (residency is per-asset, not per-reference).
- **Rationale:** Principle 3 (no partial GPU allocation / leaked buffers) and the §8.6 atomicity guarantee. CPU-side accounting (vs querying GPU residency) is what makes this testable in the no-GPU harness and deterministic. Counting expanded footprint (CAPS-7) closes the gap where a small wire payload expands to huge VRAM. The finding's two-phase recommendation is adopted verbatim; the precise accounting unit (CPU-known expanded footprint, per-asset-once) is the added normative detail.
- **Doc change:** §8.6 (semantics) + §15.2: add 'VRAM accounting is two-phase: a txn's net VRAM delta is computed CPU-side (expanded asset/texture/instance-buffer footprint, shared assets counted once) and validated against `max_vram_mb` before any upload. Over-cap rejects the whole txn (`code=vram_exhausted`) with nothing committed. Upload occurs only after the txn validates.' §6.5: note VRAM accounting keys off the same expanded-size figure used for the `max_verts`/`max_texels` caps.
- **Test:** (a) Set a small `max_vram_mb`; send a single-txn patch with three `asset.add` ops where the 3rd busts the cap; assert `tgp;x;txn=...;op=2;code=vram_exhausted`, assert scene has ZERO assets (whole txn rejected), and a vram-used accessor reads 0. (b) Send a txn that removes a large asset AND adds one of equal size (net delta ~0) when at-cap; assert it commits (delta accounting, not gross). (c) Send a txn referencing the same asset id from two `node.upsert` ops; assert vram-used counts the asset once.

### CAPS-5 [P1] Error-code taxonomy is illustrative, not enumerated
- **Decision:** Pin a CLOSED, versioned `code` enum with stable string values; `detail=` is explicitly free-form and advisory (non-load-bearing — apps MUST NOT branch on `detail`, only on `code`). The v2 enum is: `parse_error` (malformed framing/CBOR/header), `msg_too_large` (len > max_msg_mb, pre-decode), `truncated` (incomplete binary frame aborted), `cap_exceeded` (a resource cap other than VRAM/msg-size; `detail` names which, e.g. max_verts/max_nodes/max_instances/chunk_size), `vram_exhausted` (VRAM two-phase reject), `bad_ref` (op references an unknown node/asset/material/clip/viewport id), `dup_id` (`asset.add`/`material.add` on an existing immutable id, per §8.4), `unknown_op` (op `do` not understood at the negotiated version), `unsupported` (op valid but a feature/format/encoding not negotiated, e.g. unadvertised `fmt`/`enc`), `bad_token` (op addresses a node/viewport owned by a different namespace token, per F1). New codes may be added only with a version bump; apps treat an unknown `code` as a generic fatal-txn error. No numeric aliases in v1 (string codes are compact enough for the control-frame channel and human-debuggable).
- **Rationale:** Principle 4: reliable app-owned fallback REQUIRES a closed, stable code set to branch on; an open set defeats the structured-error promise. Marking `detail` non-load-bearing prevents implementers from smuggling semantics into free text. The enum is the union of every reject path surfaced across CAPS-1..4, CAPS-7, and F1's token isolation (`bad_token`), so the taxonomy and the actual reject sites are the same closed set.
- **Doc change:** §15.3: replace the two illustrative examples with the full closed `code` enum (list above) plus the rule 'codes are stable across a major version; `detail` is free-form/advisory and MUST NOT be parsed for control flow; an unknown `code` is treated as a generic fatal-txn error.' Add `bad_token` and note its F1 origin. Cross-reference each producing section.
- **Test:** One assertion per code, each via `Parser::advance` + `drain_pty_replies`: dup `asset.add` → `dup_id`; `node.upsert parent=<unknown>` → `bad_ref`; op `do=frobnicate` → `unknown_op`; `enc=zstd` (unadvertised) → `unsupported`; an op from token A addressing a node owned by token B → `bad_token`. ### CAPS-6 [P0] Opt-in error reporting has no defined negotiation knob [USER DECISION]
- **Decision:** Errors (`x`) and acks (`a`) are IMPLICITLY enabled for the rest of the session once an app sends a valid `tgp;q` and the terminal replies `tgp;r` — sending a well-formed query proves the writer speaks TGP and reads replies, so it is not a dumb reader to be spammed. An explicit `errors=0` field on `tgp;q` opts OUT (silence retained for apps that want fire-and-forget). Routing is scoped per F1: under namespace tokens, `x`/`a`/`e` route ONLY to the owning token's app; a query with no/!invalid token enables errors only for the default/global namespace it owns. A frame from a writer that never sent a valid `tgp;q` (a raw `tgp;p` from untrusted output) is processed for safety (caps still enforced, scene still protected) but its errors are NOT emitted (no proven listener) — it is dropped silently like a dumb reader, EXCEPT the malformed-tgp-prefix near-miss case is governed by CAPS-8's native rule. The opt-in is the query itself, eliminating the silent-first-failure hole.
- **Rationale:** USER-DECISION-adjacent finding: the brief's core improvement over RGP's silent drop is unreachable without a concrete opt-in. Implicit-on-query (with explicit opt-out) means an app's very FIRST malformed txn gets a diagnostic, which the discarded-Result silent default would swallow. Conforms to F1 (token-scoped routing) and principle 2 (conveniences opt-in — but error reporting is opt-OUT here because proving you speak TGP is itself the opt-in signal, avoiding a second handshake). Adopts the finding's recommendation directly.
- **Doc change:** §7.1: add field `errors` (default 1) to `tgp;q`; document 'A valid query implicitly enables `x`/`a` replies for the session/token for the rest of the session; `errors=0` opts out.' §15.3: replace 'only emitted to apps that opted in' with 'emitted to any session/token that has sent a valid `tgp;q` (unless `errors=0`); writers that never queried receive no replies.' §12.5: note `e` event routing is likewise token-scoped (F1).

### CAPS-7 [P0] Decode/parse-time cap (decompression bomb) has no enforcement locus or units
- **Decision:** Replace the wall-clock 'max decode/parse time' as the PRIMARY guard with a deterministic max-EXPANDED-OUTPUT cap, enforced incrementally DURING decode at each expansion locus, never only at the end. Concrete caps (advertised, see CAPS-9): `max_verts` and `max_indices` per asset, `max_texels` per texture (= width×height×layers×mips), and a derived `max_expanded_bytes` per asset. Enforcement loci: (1) glTF/GLB accessor expansion — before allocating, check declared `count`×componentSize against the cap and bounds-check every accessor/bufferView/index against the actual blob length (reject OOB, reject count that would exceed cap, per §15.5); (2) CBOR decode — cap array/map element counts and nesting depth so a tiny CBOR can't declare a billion-element array; (3) texture decode (KTX2/Basis/PNG) — check declared dimensions against `max_tex_dim`/`max_texels` BEFORE decompressing, and abort if the running output exceeds the cap mid-decompress. On any breach: abort decode, free the partial allocation immediately, reject the txn, emit `tgp;x;code=cap_exceeded;detail=<max_verts|max_indices|max_texels|accessor_oob>`. A wall-clock watchdog MAY exist as a non-test-relied backstop only; no normative behavior or test depends on it.
- **Rationale:** Principle 3 + the testability imperative: wall-clock caps are non-deterministic and untestable in the GPU-free harness, while a declared-count/output-size cap is fully deterministic. A GLB can declare a huge accessor count or a KTX2 can expand far beyond `max_msg_mb` after passing the byte cap — the classic terminal crash vector — so the guard must be on EXPANDED output checked incrementally, with allocation gated on the declared-size check (not discovered after OOM). Adopts the finding's recommendation; the added normative detail is the three explicit enforcement loci and check-before-allocate ordering.
- **Doc change:** §15.2: replace 'max decode/parse time (guard against decompression bombs)' with 'max expanded output (max_verts, max_indices, max_texels per asset) checked incrementally during decode at every expansion point — accessor expansion, CBOR element/depth limits, texture decode — with check-before-allocate ordering. A wall-clock watchdog is an optional non-normative backstop.' §15.5: add CBOR array/map/depth limits and texture-dimension pre-check to the hardened-parsing list; state breaches free partial allocations immediately.
- **Test:** (a) Feed a GLB header declaring an accessor `count` that exceeds `max_verts` while the actual blob is tiny; assert `tgp;x;code=cap_exceeded;detail=max_verts` and zero allocation retained (no OOM). (b) Feed a CBOR patch declaring an array length of billions but truncated; assert `parse_error`/`cap_exceeded` without large allocation. (c) Feed a GLB whose accessor offset+length exceeds the bufferView/blob length; assert `code=cap_exceeded;detail=accessor_oob` (or `parse_error`), txn rejected. (d) A texture declaring dimensions over `max_tex_dim`; assert reject before decompress. All run through `Parser::advance` with no GPU.

### CAPS-10 [P1] node.instances re-upload-per-frame has no rate/backpressure cap and unclear teardown
- **Decision:** Specify last-good retention + intra-frame coalescing now; reserve a rate field for later. (1) Retention: a `node.instances` op whose buffer exceeds `max_instances_per_buffer` (or busts VRAM, CAPS-4) rejects the whole txn atomically AND the node RETAINS its last committed instance buffer — never cleared, never flickered to empty. The emit is `tgp;x;txn=<t>;op=<i>;code=cap_exceeded;detail=max_instances_per_buffer`. (2) Coalescing: multiple `node.instances` ops targeting the same node id within a single render frame (i.e. across patches applied before the next composite) collapse to the LATEST committed buffer — only one upload per node per frame, bumping `scene_revision` once. This bounds VRAM churn from a spammy stream without a hard rate cap. (3) Reserve (do NOT enforce in v1) an advertised `max_instance_upload_bytes_per_sec_session` field for a future hard rate cap; v1 leaves it absent/unenforced so apps don't depend on it yet.
- **Rationale:** Principle 3 + §8.6 atomicity: a single over-cap frame in a live point-cloud stream must leave the prior buffer intact or the viewport visibly empties/flickers unpredictably. Coalescing-to-latest is the natural backpressure given the dirty-split (principle 6): the renderer already re-uploads on `asset_revision`/the changed buffer, so collapsing redundant intra-frame uploads is free and deterministic. Deferring the hard rate cap (per the finding) avoids guessing a constant while still reserving the wire field. Adopts the finding's recommendation.
- **Doc change:** §6.4 (dynamic instances): add 'A rejected `node.instances` op retains the node's last committed instance buffer (no flicker / no empty frame). Multiple `node.instances` for the same node within one render frame coalesce to the latest; one upload per node per frame.' §15.2: list `max_instances_per_buffer` (enforced) and note `max_instance_upload_bytes_per_sec_session` is RESERVED/unenforced in v1. ### VIEW-1 [P1] Inline viewport binding survives ScrollbackLine eviction undefined
- **Decision:** When the last placeholder cell of an inline viewport is evicted from the bounded scrollback ring, the terminal AUTO-DESTROYS that viewport: it frees the viewport's offscreen color+depth targets and pick target, drops the viewport entry from Scene.viewports, and clears the viewport dirty flag. The referenced Camera node and any scene nodes are NOT touched (a viewport owns only its compositing resources, never scene content). Destruction is keyed on placeholder-cell liveness, not on the stored {line,col} hint (consistent with F3/VIEW-12: cells are authoritative). If the owning token's app has an active sub on that viewport, the terminal emits exactly one lifecycle event `tgp;e;vp=<id>;ev=destroyed;reason=evicted` routed ONLY to the owning token (F1); a tokenless/other-token writer that created or addressed it gets nothing. A viewport with zero live placeholder cells is treated as not-rendered for the frame in which the last cell leaves the visible+scrollback set, then destroyed. No `tgp;x` error is emitted for eviction (eviction is normal teardown, not an error).
- **Rationale:** Principle 3 (bounded resources) and the §15.2 VRAM caps require reclaiming offscreen+depth targets when the anchor leaves the ring; keeping orphaned targets leaks the very VRAM the caps promise. Auto-destroy is the only option that reclaims VRAM deterministically. F3 makes placeholder cells authoritative, so eviction must key on cell liveness, not the {line,col} hint. F1 routes the lifecycle event to the owning token only. Emitting a lifecycle event (not an error) lets the app re-create the viewport if it scrolls content back, without spamming dumb readers (§15.3).
- **Doc change:** §10.2 (Inline vs pinned): after the sentence on inline scrolling off-screen (state retained), add: 'An inline viewport is bound to its placeholder cells (§10.2/§12). Scene nodes and the referenced Camera node are not affected. If the owning app (F1 token) has an active sub on the viewport, the terminal emits exactly one `tgp;e;vp=<id>;ev=destroyed;reason=evicted` to that app only; no `tgp;x` is emitted (eviction is normal teardown).' ### VIEW-7 [P2] Cached-layer re-composite is wrong when only the text plane moved under the viewport

The cached depth is stored and blitted in the viewport's own projected depth space at the new screen offset; this is correct precisely because the only other depth participant (text) is a constant-z plane. This invariant is documented as the load-bearing reason cache-recomposite is sound.
