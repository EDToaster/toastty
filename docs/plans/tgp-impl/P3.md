# P3 — Materials & light

Phase 3 adds registered PBR (metal-roughness) materials, hardened PNG/GLB-embedded textures with `max_tex_dim`/`max_texels_per_texture` caps, punctual `Light` nodes with per-viewport replace-not-augment semantics and deterministic over-cap selection, the per-viewport render stages (theme-tint pre-lighting input, tone-map over the whole linear target, MSAA with clamp-down + ack, the always-1x non-resolved/non-tone-mapped pick target), the sRGB-wire / linear-internal / sRGB-encode color pipeline (G7 `color=srgb`), and VRAM accounting for MSAA + resolve + pick targets. All deliverables land in the greenfield `crates/toastty-graphics/src/tgp/*` and `crates/toastty-render/src/tgp/*` trees and never reuse the legacy `rgp/` path (G8 clean break); every state surface stays CPU-side and queryable through `&self` accessors so the whole phase is GPU-free testable. The default material itself was built in P1; P3 extends it with the §11.2 color chain (brightness clamp `[0,8]`), theme-tint input, and registered-light response.

This phase relies on §7.1/§15.2 and advertises/enforces `max_texels_per_texture`. §15.2's "MUST NOT enforce a cap it did not advertise" is satisfied because the cap IS advertised.

This SUPERSEDES the base-spine G1/§8.4 "→ `denied` on cross-token reference" text and the `forbidden→denied` synonym's relevance here. An over-`max_msg_mb` decoded-size breach (out of P3's direct scope but binding on any P3 frame that overflows) emits **`cap_exceeded;detail=max_msg`** per G12.1 (the separate `msg_too_large` code is RESERVED) — P3 never invents a `max_msg`-specific code. `detail=` is advisory/non-load-bearing (G3); tests branch on `code=`.

## P3-T4b — `asset.remove` op: PLAN-DEFINED assets-class removal verb (decode + apply + free + asset_revision bump)

**Deliverable:** `crates/toastty-graphics/src/tgp/patch.rs` (extend the P1 op decoder): decode and apply a NEW op `{do:"asset.remove", id:<u32>}`. This is the assets-class removal verb that §8.4/§8.7 require ("immutable once committed — replace via remove + add") but never name; §8.6's closed op list omits it. **P3-T4b defines it as a PLAN-DEFINED op pending §8.6 ratification** (same standing as the plan-defined light sub-schema / tone_map spellings; flagged in the phase note for the section author to ratify) — the wire spelling `{do:"asset.remove",id:<u32>}` is authoritative-by-this-plan until ratified. Semantics: free the `(token, id)` entry from BOTH the asset table (mesh/texture, P1-T14) AND the material table (P3-T3) — material ids are assets-class and share the asset id namespace (G1/G11 per-token private map), so one removal op covers both. The commit bumps `asset_revision` once (assets-class counter, §8.6) per committed txn, NOT `scene_revision` (no node changed unless a separate op in the same txn does). Removing an id absent from the bearing token's map is a **no-op** (no error, no revision bump) — mirroring §8.6's `node.remove` "missing id is a no-op" convention. CROSS-TOKEN REMOVAL IS UNREPRESENTABLE (addendum G11): under the ratified PRIVATE per-token id map, a frame with `tok=B` naming id 9 resolves ONLY against B's own map; if B never registered 9, the id is simply absent FROM B's map and the removal is the same missing-id NO-OP as any other (token A's `{A,9}` entry is a distinct map key B cannot index, and is left untouched). There is NO cross-token addressing path, so `asset.remove` NEVER emits `code=denied` (G11(a): `denied` is RESERVED, no reachable ingress trigger) and NEVER leaks whether the id exists under another token (G11(b): no existence oracle — the no-op for "absent in my map" is byte-for-byte identical whether or not the id exists elsewhere). `asset.remove` is part of a txn and obeys whole-txn atomicity (§8.6). It does NOT cascade into nodes that reference the removed material/mesh — a `node.upsert{material:N}` that referenced the now-removed id keeps its stale binding until its own next upsert (removal frees the id for re-registration; it does not rewrite node bindings). Expose nothing new GPU; the existing `Term::tgp_material`/`tgp_texture` accessors return `None` after removal.
